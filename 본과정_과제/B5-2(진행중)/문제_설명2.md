# Mini Git 실습 명령어 설명서 (자료구조 도식판)

Task5 Mini Git의 **모든 실습 명령어**를 하나씩 뜯어본 문서입니다.
각 명령은 아래 5단 구성으로 정리했습니다.

1. **명령어** — 입력 형식과 예시
2. **개요** — 이 명령이 무엇을 하는가
3. **알아야 하는 알고리즘 / 개념** — 이해하려면 알아야 할 것
4. **자료구조 도식** — 데이터가 **어디에 어떤 모양으로 저장되고, 어떻게 조회되는지**
5. **프로그램 흐름** — 코드가 실제로 어떤 순서로 도는가

## 0. 공통 시나리오와 전체 구조

### 0-1. 이 문서 전체에서 쓰는 실습 시나리오

아래 명령을 순서대로 친 상태를 기준으로 모든 도식을 그립니다.

```text
mini-git> INIT alice
mini-git> COMMIT "Add login feature"      → C000001
mini-git> COMMIT "Fix login bug"          → C000002
mini-git> BRANCH feature                  → feature 브랜치 생성
mini-git> SWITCH feature
mini-git> COMMIT "Add feature page"       → C000003
mini-git> SWITCH main
mini-git> COMMIT "Update readme"          → C000004
```

이때 만들어지는 커밋 그래프(DAG):

```
                      ┌──────────┐
                      │ C000003  │ ← feature
                      └────┬─────┘
                           │ parents
   ┌──────────┐   ┌────────┴─┐        ┌──────────┐
   │ C000001  │←──│ C000002  │←───────│ C000004  │ ← main
   └──────────┘   └──────────┘        └──────────┘
      (뿌리)
   parents=[]     parents=[C000001]   parents=[C000002]
                                       C000003.parents=[C000002]

화살표 방향 = "자식 → 부모"  (항상 과거 방향으로만 향한다 → 사이클 불가 → DAG)
```

### 0-2. 명령이 지나가는 길

```
사용자 입력  "COMMIT \"Add login feature\""
   │
   ▼
main.py            시작 버튼        sys.exit(main())
   │
   ▼
cli.py  repl()     mini-git> 프롬프트를 무한 반복
   │
   ▼
cli.py  run_command()   shlex 파싱 → 명령어 대문자화 → 인자 개수 검사
   │
   ▼
repository.py  MiniGit   ◀── 핵심 두뇌 (그래프 + 브랜치 + 역색인)
   │
   ├──▶ hashmap.py   직접 만든 해시맵 (저장/조회)
   ├──▶ sorting.py   직접 만든 merge sort (정렬)
   └──▶ models.py    Commit 노드 정의
   │
   ▼
결과 문자열 리스트 → cli.py 가 한 줄씩 print
```

### 0-3. MiniGit이 들고 있는 5개의 저장소 — 전체 지도

#### (가) 왜 저장소가 5개나 필요한가 — 도서관 비유

커밋 하나를 만들면, 사람들이 나중에 던지는 질문은 **다섯 종류**입니다.
질문마다 답을 빨리 주려면 **질문 전용 서랍**이 하나씩 필요합니다.

| 사람이 묻는 질문 | 답해주는 저장소 | 도서관으로 치면 |
|---|---|---|
| "C000002 커밋, 내용이 뭐야?" | `_commits` | **서가** — 청구기호로 책을 꺼내는 곳 |
| "지금 main은 어디까지 왔어?" | `_branches` | **책갈피** — 어느 페이지까지 읽었는지 적은 쪽지 |
| "커밋을 순서대로 보여줘" | `_commit_order` | **입고 대장** — 들어온 순서대로 번호만 적은 장부 |
| "login이 들어간 커밋 찾아줘" | `_keyword_index` | **주제별 색인 카드함** |
| "alice가 쓴 커밋 찾아줘" | `_author_index` | **저자별 색인 카드함** |

> 만약 `_commits` 하나만 있다면?
> "login이 든 커밋 찾아줘"에 답하려면 **서가의 책을 전부 꺼내 한 권씩 펼쳐봐야** 합니다.
> 그래서 색인 카드함을 따로 두는 것입니다.

#### (나) 실제 '책'은 딱 한 군데에만 있다

여기가 5개 저장소를 이해하는 **가장 중요한 포인트**입니다.

```
   _commits        ◀── 여기에만 "진짜 커밋 객체"가 있다 (= 서가)

   _branches       ┐
   _commit_order   ├─ 나머지 넷은 전부 "C000002" 같은
   _keyword_index  │   문자열(= 청구기호)만 들고 있다
   _author_index   ┘
```

색인 카드에는 책 내용이 적혀 있지 않습니다. `"login → 3층 A-12, 3층 B-07"` 처럼
**위치만** 적혀 있죠. 그래서 어느 저장소를 거치든 마지막은 항상 같은 동작으로 끝납니다.

```
   색인에서 청구기호를 얻는다  →  _commits.get("C000002")  →  진짜 커밋을 꺼낸다
```

`SEARCH login` 이 왜 **2단 점프**인지가 여기서 나옵니다.
① 색인 카드함에서 번호를 찾고 → ② 그 번호로 서가에서 책을 꺼냅니다.

#### (다) HEAD는 저장소가 아니라 '지금 내 손가락'

`head_branch`는 서랍이 아니라 **문자열 변수 하나**입니다.
그런데 참조가 2단으로 걸려 있어서 헷갈립니다.

```
   head_branch = "main"                ◀── 내 손가락이 가리키는 건 "브랜치 이름"
        │
        ▼
   _branches["main"] = "C000004"       ◀── 그 브랜치가 가리키는 건 "커밋 번호"
        │
        ▼
   _commits["C000004"] = Commit(...)   ◀── 그제서야 진짜 커밋
```

**왜 손가락이 커밋을 직접 가리키지 않을까?**
커밋할 때마다 손가락을 옮기고 싶지 않기 때문입니다.
`main` 책갈피만 다음 페이지로 옮기면 되고, 내 손가락은 계속 `"main"`이라는 글자에
머물러 있습니다. `SWITCH`가 문자열 한 줄만 바꾸고 끝나는 것도 같은 이유입니다.

#### (라) 커밋 한 번 = 다섯 군데 동시 갱신

`COMMIT "Fix login bug"` 한 줄이 이렇게 퍼집니다.

```
   ① 서가에 책을 꽂는다         _commits["C000002"] = 커밋객체
   ② 입고 대장에 적는다         _commit_order 뒤에 "C000002" 추가
   ③ 책갈피를 옮긴다            _branches["main"] = "C000002"
   ④ 저자 색인 카드에 줄 추가    "alice" → [..., "C000002"]
   ⑤ 주제 색인 카드에 줄 추가    "fix" / "login" / "bug" → [..., "C000002"]
```

④⑤가 **역색인의 핵심 거래**입니다.
검색할 때 고생하기 싫어서, **저장할 때 미리 카드를 써두는 것**이죠.
→ 커밋은 조금 느려지고, 검색은 훨씬 빨라집니다. (시간–공간 트레이드오프)

#### (마) 전체 지도 (코드 관점)

```
┌───────────────────────────── MiniGit 인스턴스 ─────────────────────────────┐
│                                                                            │
│  스칼라 상태                                                                │
│    initialized = True                                                       │
│    author      = "alice"                                                    │
│    head_branch = "main"      ◀── HEAD (브랜치 "이름"을 가리킨다)              │
│    _counter    = 4                                                          │
│                                                                            │
│  ① _commits      HashMap :  hash → Commit 객체      (그래프의 노드 저장소)    │
│  ② _branches     HashMap :  브랜치명 → 커밋 hash     (포인터 테이블)          │
│  ③ _commit_order list    :  [hash, hash, ...]        (생성 순서 = 위상순서)   │
│  ④ _keyword_index HashMap:  단어 → [hash, ...]       (역색인)                │
│  ⑤ _author_index  HashMap:  작성자 → [hash, ...]     (역색인)                │
│                                                                            │
└────────────────────────────────────────────────────────────────────────────┘
```

**핵심 아이디어 한 줄**
> 그래프의 "간선"은 `Commit.parents`에 **문자열 hash로만** 적혀 있습니다.
> 객체를 직접 참조하지 않고 이름표만 들고 있다가, 필요할 때 `_commits.get(hash)`로 **꺼내옵니다**.
> 그래서 해시맵의 O(1) 조회가 이 프로그램의 심장입니다.

```
    Commit(C000002)
    ┌───────────────────────────┐
    │ hash      = "C000002"     │
    │ message   = "Fix login bug"│
    │ author    = "alice"       │
    │ timestamp = "2026-..-.."  │
    │ parents   = ["C000001"] ──┼──▶ (문자열!) 
    └───────────────────────────┘         │
                                          │ _commits.get("C000001")
                                          ▼
                                   Commit(C000001) 객체
```

### 0-4. 직접 만든 HashMap의 내부 모양 (hashmap.py)

모든 저장/조회의 바닥에 이 구조가 깔려 있습니다.

```
HashMap
  _capacity = 4                 서랍장 칸 수
  _size     = 2                 들어 있는 항목 수
  _buckets  = [ ... ]           서랍장

  index 0 │ None
  index 1 │ Entry("login", [C000001,C000002]) ─next─▶ Entry("add", [C000001,C000003]) ─▶ None
  index 2 │ Entry("feature", [C000001,C000003]) ─▶ None
  index 3 │ None
            └────────────── 같은 칸에 여러 개 = 충돌(collision)
                            연결 리스트로 매단다 = 체이닝(chaining)
```

**저장(put) 3단계**

```
key = "login"
  ① _hash("login")   문자열 → 숫자
        v = 0
        for ch in key:  v = (v * 31 + ord(ch)) & 0x7FFFFFFF
        ─ 31을 곱하는 이유: 글자 "순서"가 바뀌면 값이 확 달라지게  ("ab" ≠ "ba")
        ─ & 0x7FFFFFFF : 값이 무한정 커지지 않게 하위 31비트만 남김
  ② _index          숫자 % _capacity  →  서랍 번호
  ③ 그 서랍의 사슬을 훑어 같은 키가 있으면 값 교체, 없으면 사슬 맨 앞에 삽입
```

**조회(get) — 전체를 훑지 않는다**

```
get("login")
   ① 해시 계산 → 서랍 번호 1
   ② 서랍 1의 사슬만 따라간다  (나머지 서랍은 쳐다보지도 않음)
   ③ 키가 같으면 value 반환, 끝까지 없으면 None

   평균 O(1)   ← 사슬이 짧을 때
   최악 O(n)   ← 모든 키가 한 서랍에 몰렸을 때
```

**리사이즈(resize) — 사슬이 길어지는 것을 막는다**

```
조건: (_size + 1) / _capacity > 0.75   (적재율 load factor)

   cap=4, size=3 인 상태에서 하나 더 넣으면 4/4 = 1.0 > 0.75  →  발동

   [ 기존 cap 4 ]              [ 새 cap 8 ]
   0 │ None                     0 │ None
   1 │ login → add     ──재삽입──▶ 1 │ add → login
   2 │ feature                   ...
   3 │ None                      6 │ feature

   ★ capacity가 바뀌면 "숫자 % capacity" 결과가 달라지므로
     기존 항목을 전부 다시 넣어야 한다 (rehash). 비용 O(n).
```

### 0-5. 커밋 노드 = 그래프의 점 (models.py)

```python
@dataclass
class Commit:
    hash: str          # 고유 이름표  예) "C000001"
    message: str       # 검색(SEARCH)의 재료
    author: str
    timestamp: str     # LOG --sort-by=date 의 기준
    parents: list[str] # 부모 hash 목록 = 그래프의 화살표(간선)
```

> **왜 DAG인가?**
> 부모는 언제나 "나보다 먼저 만들어진 커밋"입니다. 새 커밋이 과거 커밋의 부모가 될 수는 없습니다.
> 시간이 한 방향으로만 흐르므로 **되돌아오는 길(사이클)이 생길 수 없고**, 따라서
> 전체 모양은 **DAG(Directed Acyclic Graph)** 가 됩니다.

### 0-6. 공통 규칙

- 명령어는 **대소문자 구분 없음** → `parts[0].upper()`
- 공백 포함 인자는 따옴표로 → `shlex.split()`
  `COMMIT "Add login feature"` → `["COMMIT", "Add login feature"]`
- 인자 개수 불일치 → `Invalid args`
- `INIT` 전 다른 명령 → `Repository not initialized`

## 1. INIT

### 명령어

```text
INIT <user_name>
INIT alice
```

### 개요

저장소를 새로 만듭니다. `main` 브랜치를 생성하고 HEAD를 `main`에 맞추고, 앞으로 만들 커밋의
작성자 이름을 기억합니다. 아직 커밋이 없으므로 `main`이 가리키는 값은 `None`입니다.

```text
Initialized repository for alice
Current branch: main
```

### 알아야 하는 알고리즘 / 개념

- **상태 초기화**: `self.__init__()` 재호출로 기존 저장소를 통째로 리셋 (커밋·브랜치·인덱스 전부 소멸)
- **HEAD의 정체**: HEAD는 커밋을 직접 가리키지 않고 **브랜치 이름을 가리킵니다** → `HEAD → 브랜치 → 커밋` 2단 참조
- **브랜치의 정체**: 폴더도 복사본도 아닌 `이름 → 커밋 hash` 한 줄짜리 매핑

### 자료구조 도식

**INIT 실행 전 (MiniGit() 갓 생성)**

```
initialized = False      author = ""      head_branch = ""      _counter = 0

_commits        HashMap  cap=4  size=0   [None, None, None, None]
_branches       HashMap  cap=4  size=0   [None, None, None, None]
_commit_order   []
_keyword_index  HashMap  cap=4  size=0
_author_index   HashMap  cap=4  size=0
```

**INIT alice 실행 후**

```
initialized = True       author = "alice"      head_branch = "main"      _counter = 0
                                                └──────────┐
                                                   HEAD    │
                                                           ▼
_branches  HashMap  cap=4  size=1
   index 0 │ None
   index 1 │ Entry(key="main", value=None) ─▶ None      ◀── 커밋이 없으니 None
   index 2 │ None
   index 3 │ None
             ▲
             └─ _hash("main") = 3343801,  3343801 % 4 = 1

_commits / _keyword_index / _author_index : 여전히 전부 비어 있음
_commit_order : []
```

**2단 참조를 그림으로**

```
   head_branch                _branches                     _commits
   ┌────────┐   문자열 키    ┌──────────────┐  hash 문자열  ┌──────────┐
   │ "main" │──────────────▶ │ "main" → None│─────────────▶│ (없음)   │
   └────────┘                └──────────────┘               └──────────┘
     HEAD                      포인터 테이블                   노드 저장소
```

### 프로그램 흐름

```
run_command: parts = ["INIT", "alice"]
  ├ len(parts) != 2 ?  →  "Invalid args"
  └ repo.init("alice")
        ├ user_name 비었으면 → "Invalid args"
        ├ self.__init__()              전체 상태 리셋
        ├ initialized = True
        ├ author = "alice"
        ├ head_branch = "main"         ◀── HEAD 설정
        └ _branches.put("main", None)  ◀── 해시 계산 → 서랍 1에 Entry 삽입
```

## 2. COMMIT

> BRANCH/SWITCH보다 COMMIT을 먼저 봐야 나머지 도식이 채워집니다.
> (시나리오 순서상으로도 INIT 다음이 COMMIT입니다.)

### 명령어

```text
COMMIT <message>
COMMIT "Add login feature"
```

### 개요

현재 HEAD를 **부모로 삼는** 새 커밋 노드를 만들어 그래프에 추가하고, 현재 브랜치 포인터를
새 커밋으로 옮기고, **역색인 2종을 갱신**합니다.

```text
Committed C000001: Add login feature
```

### 알아야 하는 알고리즘 / 개념

- **그래프에 노드 추가**: `parents = [현재 HEAD 커밋]`, 첫 커밋이면 `[]` (뿌리 노드)
- **유일 hash 생성**: 일련번호 방식 `C000001`, `C000002` …
  ```python
  while True:
      self._counter += 1
      commit_hash = f"C{self._counter:06d}"
      if not self._commits.contains(commit_hash):
          return commit_hash
  ```
- **역색인(Inverted Index) 갱신**: 검색 비용을 **검색 시점 → 저장 시점으로 옮기는 것**이 핵심
- **브랜치 포인터 전진**: `_branches.put(head_branch, 새 hash)` — 같은 키에 값만 덮어씀

### 자료구조 도식

#### (1) `COMMIT "Add login feature"` — 첫 커밋

```
STEP 1. 부모 찾기
   _current_head() = _branches.get("main") = None    →  parents = []   (뿌리 커밋)

STEP 2. hash 발급
   _counter: 0 → 1        commit_hash = "C000001"

STEP 3. Commit 객체 생성
   ┌────────────────────────────────────┐
   │ hash      = "C000001"              │
   │ message   = "Add login feature"    │
   │ author    = "alice"                │
   │ timestamp = "2026-09-09T10:00:00"  │
   │ parents   = []                     │  ◀── 뿌리라서 빈 리스트
   └────────────────────────────────────┘

STEP 4. 네 군데에 나눠 저장
   ① _commits.put("C000001", 객체)     cap=4 → _hash%4 = 0 번 서랍
   ② _commit_order.append("C000001")   ["C000001"]
   ③ _branches.put("main", "C000001")  기존 Entry의 value만 None → "C000001"
   ④ _add_to_indexes(commit)
        author  : "alice" → ["C000001"]
        keyword : "add" / "login" / "feature" → ["C000001"]
```

**저장 직후 전체 스냅샷**

```
head_branch = "main"   _counter = 1

_commits       cap=4 size=1
   0 │ Entry("C000001", Commit객체) ─▶ None
   1 │ None      2 │ None      3 │ None

_branches      cap=4 size=1
   1 │ Entry("main", "C000001") ─▶ None

_commit_order  ["C000001"]

_author_index  cap=4 size=1
   0 │ Entry("alice", ["C000001"]) ─▶ None       ◀── _hash("alice")%4 = 0

_keyword_index cap=4 size=3
   0 │ None
   1 │ Entry("login", ["C000001"]) ─▶ Entry("add", ["C000001"]) ─▶ None   ★충돌!
   2 │ Entry("feature", ["C000001"]) ─▶ None
   3 │ None
        ▲
        └ "add"와 "login"이 둘 다 %4 == 1 → 같은 서랍에 사슬로 매달림
          (새 항목은 사슬 "맨 앞"에 끼워 넣으므로 login이 앞에 온다)
```

#### (2) `COMMIT "Fix login bug"` — 두 번째 커밋

```
부모 = _branches.get("main") = "C000001"   →   parents = ["C000001"]
hash = "C000002"

그래프가 이렇게 이어진다:
   C000001  ◀───parents───  C000002
   (main이 C000001 → C000002 로 이동)
```

**역색인 갱신 상세** — `_add_index_value`가 하는 일

```
"fix"   : 키가 없음  → 빈 리스트 만들어 put →  "fix"   → ["C000002"]
"login" : 이미 있음  → 기존 리스트에 append →  "login" → ["C000001", "C000002"]   ★
"bug"   : 키가 없음  → 빈 리스트 만들어 put →  "bug"   → ["C000002"]

   ┌ 여기서 리사이즈 발동 ┐
   "fix" 삽입 시점: (size 3 + 1) / cap 4 = 1.0 > 0.75  →  cap 4 → 8 로 확장 후 재삽입
```

```
_keyword_index  cap=8 size=5   (리사이즈 직후)
   0 │ None
   1 │ Entry("add", [C000001]) ─▶ Entry("login", [C000001, C000002]) ─▶ None
   2 │ None      3 │ None
   4 │ Entry("bug", [C000002])
   5 │ Entry("fix", [C000002])
   6 │ Entry("feature", [C000001])
   7 │ None
```

#### (3) `COMMIT "Add feature page"` (feature 브랜치) / `COMMIT "Update readme"` (main)

키워드가 8개가 되면서 한 번 더 리사이즈(8 → 16)가 일어납니다.

```
"update" 삽입 시점: (size 6 + 1) / cap 8 = 0.875 > 0.75  →  cap 8 → 16
```

**최종 `_keyword_index` (cap=16, size=8)**

```
   idx  0 │ None
   idx  1 │ Entry("add",     ["C000001", "C000003"])
   idx  2 │ None      idx 3 │ None
   idx  4 │ Entry("bug",     ["C000002"])
   idx  5 │ Entry("fix",     ["C000002"])
   idx  6 │ Entry("feature", ["C000001", "C000003"])
   idx  7 │ None      idx 8 │ None
   idx  9 │ Entry("update",  ["C000004"]) ─▶ Entry("login", ["C000001","C000002"]) ─▶ None
   idx 10~13 │ None                          ▲
   idx 14 │ Entry("readme",  ["C000004"])    └─ 충돌: update와 login이 둘 다 %16 == 9
   idx 15 │ Entry("page",    ["C000003"])
```

**최종 `_commits` (cap=8, size=4)** — cap 4→8 리사이즈를 한 번 거친 상태

```
   idx 0~3 │ None
   idx 4 │ Entry("C000001", Commit(parents=[]))
   idx 5 │ Entry("C000002", Commit(parents=["C000001"]))
   idx 6 │ Entry("C000003", Commit(parents=["C000002"]))
   idx 7 │ Entry("C000004", Commit(parents=["C000002"]))
```

**최종 `_author_index` (cap=4, size=1)**

```
   idx 0 │ Entry("alice", ["C000001", "C000002", "C000003", "C000004"])
```

**최종 `_commit_order`**

```
   ["C000001", "C000002", "C000003", "C000004"]
      ↑ 이 리스트 순서가 그대로 위상 정렬 순서 (부모가 항상 앞)
```

### 프로그램 흐름

```
repo.commit("Add login feature")
  ├ _is_ready() / message 검사
  ├ parent = _current_head()                      _branches.get(head_branch)
  ├ parents = [] if parent is None else [parent]
  ├ commit_hash = _next_hash()                    _counter += 1 → "C000001"
  ├ Commit(hash, message, author, now, parents) 생성
  ├ _commits.put(hash, commit)         ① 노드 저장     (해시 → 서랍 → 사슬 앞 삽입)
  ├ _commit_order.append(hash)         ② 순서 기록     (LOG용)
  ├ _branches.put(head_branch, hash)   ③ 포인터 전진   (기존 키 value 덮어쓰기)
  └ _add_to_indexes(commit)            ④ 역색인 갱신
        ├ _add_index_value(_author_index,  author.lower(), hash)
        └ for token in message.split():
              _add_index_value(_keyword_index, token.lower(), hash)
```

## 3. BRANCH

### 명령어

```text
BRANCH <branch_name>
BRANCH feature
```

### 개요

**지금 HEAD가 가리키는 커밋**에서 새 브랜치를 만듭니다.
커밋을 복사하는 것이 아니라 **같은 커밋을 가리키는 이름표를 하나 더 다는 것**입니다.

```text
Created branch: feature
```

### 알아야 하는 알고리즘 / 개념

- **브랜치 = 포인터**: `_branches.put(name, 현재 HEAD 커밋 hash)` — 비용 O(1)
  실제 Git이 브랜치를 "싸게" 만드는 이유와 같습니다.
- **그래프 분기(branching)**: 같은 부모를 가리키는 커밋이 둘 이상 생기면 DAG의 갈래가 나뉩니다.
- **중복 검사**: `HashMap.contains()` 평균 O(1)

### 자료구조 도식

**BRANCH feature 실행 전 (C000002까지 커밋된 상태)**

```
head_branch = "main"

_branches  cap=4 size=1
   1 │ Entry("main", "C000002")

그래프:      C000001 ◀── C000002 ◀── main
```

**실행 후 — 노드는 하나도 늘지 않고, 이름표만 하나 늘어난다**

```
_branches  cap=4 size=2
   1 │ Entry("main",    "C000002")
   2 │ Entry("feature", "C000002")    ◀── _hash("feature")%4 = 2

그래프:      C000001 ◀── C000002 ◀── main
                              ▲
                              └────── feature      두 이름표가 같은 커밋을 가리킴
```

**여기서 SWITCH feature 후 커밋하면 갈래가 나뉜다**

```
                     C000003 ◀── feature
                        │
                        ▼ parents
   C000001 ◀── C000002 ◀── C000004 ◀── main

   ★ C000002가 두 자식(C000003, C000004)을 갖게 되는 순간이 "분기"
     C000002 자신은 아무것도 모른다. 자식들이 일방적으로 C000002를 가리킬 뿐.
```

### 프로그램 흐름

```
repo.branch("feature")
  ├ _is_ready()  아니면 → "Repository not initialized"
  ├ 이름 비었으면 → "Invalid args"
  ├ _branches.contains("feature")  →  이미 있으면 "Branch already exists: feature"
  │      └ 해시 계산 → 서랍 2 → 사슬 훑기 → 없음 확인   (평균 O(1))
  ├ _current_head() = _branches.get("main") = "C000002"
  └ _branches.put("feature", "C000002")
```

> 커밋이 하나도 없을 때 BRANCH를 하면 값이 `None`인 브랜치가 생깁니다.
> 그 브랜치에서 첫 커밋을 하면 부모가 없는 뿌리 커밋이 하나 더 생깁니다(숲 형태의 DAG).

## 4. SWITCH

### 명령어

```text
SWITCH <branch_name>
SWITCH feature
```

### 개요

HEAD를 지정한 브랜치로 옮깁니다. **커밋 데이터는 단 1바이트도 변하지 않고**,
"지금 어디에 서 있는지"만 바뀝니다.

```text
Switched to branch: feature
```

### 알아야 하는 알고리즘 / 개념

- **참조 이동 vs 데이터 이동**: 그래프의 노드/간선은 그대로 두고 **진입점만** 바꾸는 연산
- **존재 검사**: 없는 브랜치면 `Unknown branch: <name>`

### 자료구조 도식

```
── SWITCH 전 ──                          ── SWITCH feature 후 ──

head_branch = "main"                     head_branch = "feature"
     │                                        │
     ▼                                        ▼
_branches                                _branches           (내용 그대로!)
   1 │ "main"    → "C000002"                1 │ "main"    → "C000002"
   2 │ "feature" → "C000002"                2 │ "feature" → "C000002"

_commits, _commit_order, 인덱스 : 전혀 변하지 않음
```

**바뀌는 것은 문자열 변수 하나뿐**

```
   head_branch : "main"  ──────▶  "feature"
                 └ 이 한 글자 묶음이 바뀌면
                   다음 COMMIT의 부모(_current_head)와
                   포인터 전진 대상(_branches.put(head_branch, ...))이 통째로 달라진다
```

### 프로그램 흐름

```
repo.switch("feature")
  ├ _is_ready() 확인
  ├ _branches.contains("feature") 아니면 → "Unknown branch: feature"
  └ head_branch = "feature"      ◀── 이 한 줄이 전부
```

## 5. LOG (기본)

### 명령어

```text
LOG
```

### 개요

커밋 목록을 출력합니다. **단순 최신순이 아니라, 부모가 항상 자식보다 먼저 나오도록** 출력합니다.
즉 **위상 정렬(topological order)** 성격의 출력입니다.

```text
C000001 | alice | 2026-09-09T10:00:00 | parents=- | Add login feature
C000002 | alice | 2026-09-09T10:01:00 | parents=C000001 | Fix login bug
C000003 | alice | 2026-09-09T10:02:00 | parents=C000002 | Add feature page
C000004 | alice | 2026-09-09T10:03:00 | parents=C000002 | Update readme
```

### 알아야 하는 알고리즘 / 개념

- **위상 정렬(Topological Sort)**: DAG의 노드를 "간선 방향을 거스르지 않는 순서"로 나열
  일반적으로는 Kahn's algorithm(진입차수 0부터 제거) 또는 DFS 역순
- **이 구현의 트릭**: 위상 정렬을 따로 돌리지 않고 `_commit_order`(생성 순서)를 그대로 씁니다.
  **부모는 항상 자식보다 먼저 만들어지므로** 생성 순서 자체가 이미 유효한 위상 정렬 순서입니다.
  → O(V+E) 재계산 불필요, O(n)에 해결
- **DAG가 아니면 위상 정렬 불가**: 사이클이 있으면 "누가 먼저"인지 정할 수 없습니다.

### 자료구조 도식

**조회 경로 — 리스트를 순회하며 해시맵에서 객체를 꺼낸다**

```
_commit_order  (list, 순서 보존)
   ┌─────────┬─────────┬─────────┬─────────┐
   │C000001  │C000002  │C000003  │C000004  │
   └────┬────┴────┬────┴────┬────┴────┬────┘
        │         │         │         │
        │  _commits.get(hash)  평균 O(1) × n번
        ▼         ▼         ▼         ▼
   ┌─────────────── _commits (cap=8) ───────────────┐
   │ idx4 Entry("C000001", Commit)                  │
   │ idx5 Entry("C000002", Commit)                  │
   │ idx6 Entry("C000003", Commit)                  │
   │ idx7 Entry("C000004", Commit)                  │
   └────────────────────────────────────────────────┘
        │
        ▼  _format_commit(commit)
   "C000001 | alice | ... | parents=- | Add login feature"
```

**"생성 순서 = 위상 순서"인 이유를 그래프 위에 겹쳐 보기**

```
   출력 순서:   1️⃣        2️⃣        3️⃣        4️⃣
              C000001 → C000002 → C000003   C000004

   간선(자식→부모)을 확인하면
      C000002 → C000001 :  부모(1️⃣)가 자식(2️⃣)보다 앞 ✅
      C000003 → C000002 :  부모(2️⃣)가 자식(3️⃣)보다 앞 ✅
      C000004 → C000002 :  부모(2️⃣)가 자식(4️⃣)보다 앞 ✅

   모든 간선이 "앞 → 뒤"를 만족 → 유효한 위상 정렬
```

> 왜 항상 성립하는가? 커밋 생성 시점에 부모는 **이미 `_commit_order`에 들어 있는 hash**뿐입니다.
> 미래의 커밋을 부모로 지정할 방법이 없으므로, append 순서는 언제나 위상 순서입니다.

### 프로그램 흐름

```
repo.log(sort_by=None)
  ├ _is_ready() 확인
  ├ commits = _all_commits()
  │     └ for h in _commit_order:      순서 보존 리스트를 순회
  │           c = _commits.get(h)      해시맵에서 실제 객체 복원
  │           if c is not None: result.append(c)
  ├ 비어 있으면 → "No commits"
  └ [_format_commit(c) for c in commits]
```

## 6. LOG --sort-by=date

### 명령어

```text
LOG --sort-by=date
```

### 개요

커밋을 **timestamp 오름차순**으로 정렬해 출력합니다.
`sorted()` / `list.sort()` 사용이 금지되어 있으므로 직접 구현한 merge sort를 씁니다.

### 알아야 하는 알고리즘 / 개념

- **Merge Sort (병합 정렬)** — 분할 정복
  - 시간복잡도 **평균 / 최악 모두 O(n log n)** (퀵 정렬은 평균 O(n log n), 최악 O(n²))
  - 공간복잡도 O(n) — 합칠 새 리스트가 필요
  - **안정 정렬(stable)**: `_merge`에서 `compare(...) <= 0` 일 때 **왼쪽을 먼저** 넣기 때문
- **비교 함수 주입(Comparator Injection)**: 정렬 코드는 그대로, `compare`만 바꿔 끼움
  ```python
  def _compare_by_date(left, right):
      r = _compare_text(left.timestamp, right.timestamp)
      return r if r != 0 else _compare_text(left.hash, right.hash)   # 동률은 hash로
  ```
  규칙: 왼쪽이 먼저면 음수, 같으면 0, 오른쪽이 먼저면 양수
- **동률 처리(tie-break)**: timestamp가 같으면 hash로 → 결과가 흔들리지 않음(결정적)

### 자료구조 도식

**메모리에서 벌어지는 일 — 원본은 그대로, 새 리스트가 만들어진다**

```
입력 (list, _commit_order 순서)
   [ C1, C2, C3, C4 ]        ← Commit 객체 4개의 참조
        │
        │ merge_sort(items, compare)   ※ items[:] 복사본을 반환, 원본 불변
        ▼
   ┌── 분할(divide) ─────────────────────────────┐
   │        [C1, C2, C3, C4]                     │
   │          ╱          ╲                       │
   │    [C1, C2]        [C3, C4]                 │
   │      ╱  ╲            ╱  ╲                   │
   │   [C1]  [C2]      [C3]  [C4]   ← len<=1 이면 재귀 종료
   └─────────────────────────────────────────────┘
                     │
   ┌── 병합(conquer) ────────────────────────────┐
   │   [C1] + [C2] ─_merge─▶ [C1, C2]            │
   │   [C3] + [C4] ─_merge─▶ [C3, C4]            │
   │   [C1,C2] + [C3,C4] ─_merge─▶ [C1,C2,C3,C4] │
   └─────────────────────────────────────────────┘

   재귀 깊이 log n,  각 층에서 n개를 훑음  →  O(n log n)
```

**`_merge`의 투 포인터 동작 — 안정성이 생기는 지점**

```
left  = [ A(10:00), B(10:02) ]        right = [ C(10:00), D(10:05) ]
         ▲li=0                                  ▲ri=0
result = []

step1  compare(A, C) → timestamp 동일(0) → hash로 tie-break
       ★ 만약 완전 동률이라 0이 나오면 "<= 0" 이므로 왼쪽(A) 먼저
       → 원래 앞 조각의 순서가 보존된다 = 안정 정렬
       result=[A],  li=1

step2  compare(B(10:02), C(10:00)) → 양수 → 오른쪽 C
       result=[A, C],  ri=1

step3  compare(B(10:02), D(10:05)) → 음수 → 왼쪽 B
       result=[A, C, B],  li=2  (left 소진)

step4  left가 바닥 → right 남은 [D] 를 통째로 이어 붙임
       result=[A, C, B, D]
```

**정렬 기준을 바꾸는 지점은 딱 한 곳**

```
   merge_sort( commits , ────────────────► compare 함수
                                             ├ _compare_by_date    (timestamp → hash)
                                             ├ _compare_by_author  (author → hash)
                                             ├ _compare_text       (문자열 사전순)
                                             └ _compare_path_text  (경로 문자열)
   ★ 정렬 "엔진"은 하나, "자(기준)"만 갈아 끼운다
```

### 프로그램 흐름

```
cli._run_log: "--sort-by=date".split("=", 1)[1] → "date"
  └ repo.log(sort_by="date")
        ├ commits = _all_commits()                   _commit_order → _commits.get
        ├ commits = merge_sort(commits, _compare_by_date)
        │      ├ len <= 1 → items[:] 반환 (재귀 종료)
        │      ├ mid = len//2, 좌/우 재귀
        │      └ _merge(left, right, compare)  투 포인터로 합치기
        └ [_format_commit(c) for c in commits]
```

## 7. LOG --sort-by=author

### 명령어

```text
LOG --sort-by=author
```

### 개요

작성자 이름 기준으로 정렬합니다. **정렬 엔진은 date와 완전히 동일하고, 비교 함수만 다릅니다.**

### 알아야 하는 알고리즘 / 개념

- **같은 알고리즘 + 다른 비교 기준** — 전략 패턴(Strategy Pattern)의 가장 단순한 형태
- **대소문자 무시 비교**: `left.author.lower()` 로 정규화 후 비교
- **동률 처리**: 작성자가 같으면 hash 사전순

```python
def _compare_by_author(left, right):
    r = _compare_text(left.author.lower(), right.author.lower())
    return r if r != 0 else _compare_text(left.hash, right.hash)
```

### 자료구조 도식

**같은 자료, 다른 자(尺)**

```
                       ┌─ _compare_by_date ──▶ [ C1, C2, C3, C4 ]  (시간순)
   [C1,C2,C3,C4] ──────┤
     동일한 리스트      └─ _compare_by_author ▶ [ C1, C2, C3, C4 ]  (작성자순)
                                                  ▲
                          시나리오는 작성자가 모두 alice 이므로
                          author 비교가 전부 0 → hash tie-break으로 결정
                          + 안정 정렬이라 원래 순서도 그대로 유지
```

**작성자가 여럿일 때의 동작**

```
입력   [ C1(alice), C2(Bob), C3(alice), C4(bob) ]

  ① author.lower() 로 정규화 →  alice, bob, alice, bob
  ② merge_sort 로 정렬        →  alice 그룹 먼저, bob 그룹 나중
  ③ 그룹 내부는 hash 사전순    →  C1, C3  /  C2, C4

출력   [ C1(alice), C3(alice), C2(Bob), C4(bob) ]
            └── "Bob"과 "bob"이 같은 그룹으로 묶인다 (lower 정규화의 효과)
```

### 프로그램 흐름

```
cli._run_log: parts[1].startswith("--sort-by=")  →  sort_by = "author"
  └ repo.log(sort_by="author")
        └ merge_sort(commits, _compare_by_author)   ◀── 함수 참조만 교체
```

> `--sort-by=` 뒤에 date/author 이외의 값이 오면 `Invalid args`.

## 8. PATH

### 명령어

```text
PATH <commit1> <commit2>
PATH C000003 C000004
```

### 개요

두 커밋 사이의 **최단 경로**를 출력합니다. 커밋–부모 연결을 **무방향 간선**으로 보고,
**간선 수가 가장 적은 경로**를 찾습니다. 없으면 `No path`.

```text
C000003->C000002->C000004
```

### 알아야 하는 알고리즘 / 개념

- **BFS (너비 우선 탐색)**
  - 가까운 곳부터 한 겹씩 넓혀 가므로 **목적지에 처음 닿은 깊이 = 최단 거리**
  - 가중치 없는 그래프의 최단 경로는 BFS로 (가중치가 있으면 Dijkstra)
  - 이 구현은 큐에 **경로 전체**를 담고 `_neighbors`가 매번 전체를 훑으므로 O(V+E)보다 무겁습니다(학습용)
- **왜 무방향인가**: 다른 브랜치의 두 커밋은 부모 방향으로만 가면 절대 못 만납니다.
  **공통 조상까지 내려갔다가 다시 자식 방향으로 올라와야** 만납니다.
- **자식 찾기의 비대칭성**: 부모는 `commit.parents`에 적혀 있지만, 자식은 역방향 간선이 저장돼 있지
  않아 **전체 순회**로 찾아야 합니다.
- **tie-break**: 최단 경로가 여러 개면 `a->b->c` 문자열 사전순 최소
- **사이클 방지**: `if _contains(path, neighbor): continue`

### 자료구조 도식

#### (1) 저장된 간선은 "단방향"인데, 탐색은 "양방향"

```
저장된 것 (parents, 단방향)          _neighbors()가 만들어내는 것 (양방향)

   C000003 ──▶ C000002                 C000003 ◀──▶ C000002
   C000004 ──▶ C000002                 C000004 ◀──▶ C000002
   C000002 ──▶ C000001                 C000002 ◀──▶ C000001

   ▲ 자식→부모만 저장                    ▲ 부모 + 자식을 합쳐 이웃 목록 생성
```

**`_neighbors("C000002")` 가 만들어지는 과정**

```
   ① 부모 방향 : commit.parents 를 그대로 읽음         →  ["C000001"]          O(1)
   ② 자식 방향 : _commit_order 전체를 훑으며
                 "parents에 C000002가 들어 있는" 커밋을 수집
                    C000001.parents = []           ✗
                    C000002.parents = [C000001]    ✗
                    C000003.parents = [C000002]    ✓
                    C000004.parents = [C000002]    ✓   →  ["C000003","C000004"]   O(n)
   ③ 합쳐서 merge_sort(_compare_text) 로 사전순 정렬
                 →  ["C000001", "C000003", "C000004"]
                     ▲ 사전순으로 정렬해 두면 같은 길이의 경로 중
                       사전순으로 작은 경로가 먼저 큐에 들어간다
```

#### (2) BFS 큐의 상태 변화 — `PATH C000003 C000004`

큐에는 노드가 아니라 **지나온 경로 전체**가 들어갑니다.

```
초기
  queue          = [ [C000003] ]
  visited_depths = [ (C000003, 0) ]
  found_depth    = None

─── 라운드 0 : depth 0 ───────────────────────────────────
  꺼냄 path=[C000003]  current=C000003  depth=0
  목적지 아님 → 이웃 확인
  _neighbors(C000003) = [C000002]
      C000002 : 경로에 없음, 방문 기록 없음 → 기록 (C000002,1), 큐에 push

  queue = [ [C000003], [C000003,C000002] ]
                        ▲ 새로 들어온 경로
  visited_depths = [ (C000003,0), (C000002,1) ]

─── 라운드 1 : depth 1 ───────────────────────────────────
  꺼냄 path=[C000003,C000002]  current=C000002  depth=1
  목적지 아님 → 이웃 확인
  _neighbors(C000002) = [C000001, C000003, C000004]   (사전순)
      C000001 : 경로에 없음 → 기록 (C000001,2), push [C000003,C000002,C000001]
      C000003 : 이미 경로에 있음 → skip  ◀── 사이클 방지
      C000004 : 경로에 없음 → 기록 (C000004,2), push [C000003,C000002,C000004]

  queue = [ ..., [C000003,C000002,C000001], [C000003,C000002,C000004] ]

─── 라운드 2 : depth 2 ───────────────────────────────────
  꺼냄 [C000003,C000002,C000001]  current=C000001  목적지 아님 → 이웃 확장
  꺼냄 [C000003,C000002,C000004]  current=C000004  ★목적지!
       found_depth = 2,  found_paths = [ [C000003,C000002,C000004] ]

─── 라운드 3 : depth 3 ───────────────────────────────────
  꺼낸 경로의 depth(3) > found_depth(2)  →  break   ◀── 더 볼 필요 없음

결과
  found_paths = [ [C000003, C000002, C000004] ]
  merge_sort(found_paths, _compare_path_text) → 첫 번째 선택
  출력: "C000003->C000002->C000004"
```

**경로를 통째로 담는 구조의 장단점**

```
   장점 : 도착 즉시 경로를 알 수 있다 (부모 추적 배열이 필요 없음)
          같은 길이의 경로를 여러 개 모으기 쉽다
   단점 : 같은 접두사가 중복 저장되어 메모리를 더 쓴다
          [C1]      [C1,C2]      [C1,C2,C3]      ← C1이 세 번 저장됨
```

**탐색 대상 자료구조 요약**

```
   queue          list[list[str]]        아직 살펴볼 경로들 (queue_index로 앞에서부터 소비)
   visited_depths list[tuple[str,int]]   (커밋, 최소 도달 깊이)  ※ 선형 탐색 O(n)
   found_paths    list[list[str]]        최단 길이로 목적지에 닿은 경로들
   found_depth    int | None             최단 깊이. 이보다 깊어지면 중단
```

### 프로그램 흐름

```
repo.path("C000003", "C000004")
  ├ 두 hash 존재 확인 → 없으면 "Unknown commit: <hash>"
  ├ start == end 면 → [start]
  ├ found_paths = _shortest_paths(start, end)
  │     while queue_index < len(queue):
  │       ├ path 꺼내기, current = path[-1], depth = len(path)-1
  │       ├ found_depth 보다 깊으면 break              ◀ 최단만 수집
  │       ├ current == end 면 found_paths에 담고 continue
  │       └ for neighbor in _neighbors(current):       (부모+자식, 사전순)
  │             ├ 이미 이 경로에 있으면 skip           (사이클 방지)
  │             ├ 더 짧게 도달한 적 있으면 skip        (최단 아님)
  │             └ queue.append(path + [neighbor])
  ├ 비었으면 → "No path"
  ├ ordered = merge_sort(found_paths, _compare_path_text)
  └ "->".join(ordered[0])
```

## 9. ANCESTORS

### 명령어

```text
ANCESTORS <commit_hash>
ANCESTORS C000004
```

### 개요

해당 커밋에서 **부모 방향으로 도달 가능한 모든 조상**을 빠짐없이 출력합니다.
조상이 없으면 `No ancestors`.

```text
C000002
C000001
```

### 알아야 하는 알고리즘 / 개념

- **DFS (깊이 우선 탐색), 스택 기반 반복 구현**
  - 재귀 대신 `stack` 리스트 + `pop()` → LIFO → 깊이 우선 (스택 오버플로 없음)
  - `pop(0)`으로 바꾸면 BFS가 됩니다. **조상 "집합"을 구하는 게 목적이라 어느 쪽이든 결과는 같습니다.**
- **방문 처리(visited)의 필요성**: 병합된 갈래가 같은 조상으로 다시 모이면 중복 방문이 폭발합니다.
  여기서는 `result` 리스트 자체를 방문 표시로 겸용 (`_contains`)
- **방향 있는 탐색**: PATH와 달리 **부모 방향으로만** (자식은 조상이 아님)
- **도달 가능성(reachability)**: "이 노드에서 갈 수 있는 모든 노드" 전형 문제

### 자료구조 도식

#### 스택 상태 변화 — `ANCESTORS C000004`

```
초기
   commit  = _commits.get("C000004")          해시맵 조회 O(1)
   parents = ["C000002"]
   stack   = [ C000002 ]        ◀── 자기 자신은 조상이 아니므로 제외
   result  = [ ]

─── 반복 1 ───────────────────────────────
   pop → C000002
   result에 없음 → result = [C000002]
   _commits.get("C000002").parents = ["C000001"] → push
   stack = [ C000001 ]

─── 반복 2 ───────────────────────────────
   pop → C000001
   result에 없음 → result = [C000002, C000001]
   C000001.parents = []  → push 없음
   stack = [ ]

─── 종료 ────────────────────────────────
   stack이 비었으므로 반복 종료
   출력:  C000002
          C000001
```

#### 병합 커밋이 있을 때 방문 처리가 왜 필요한가

```
가상의 그래프 (M은 부모가 둘인 병합 커밋)

          ┌── B ──┐
   A ◀────┤       ├──── M          M.parents = [B, C]
          └── C ──┘                 B.parents = [A],  C.parents = [A]

방문 처리 없이 ANCESTORS M 을 하면
   stack: [B, C] → pop C → push A → pop A ... → pop B → push A → pop A (중복!)
   A를 두 번 방문. 갈래가 k개면 2^k 규모로 폭발.

방문 처리(result에 이미 있으면 continue)를 두면
   A는 딱 한 번만 처리됨 →  O(V + E)
```

#### 사용하는 자료구조

```
   stack   list[str]     아직 안 가본 조상 hash들.  pop() = 맨 뒤에서 꺼냄 → DFS
   result  list[str]     방문 완료 목록 + 최종 출력 목록 (이중 역할)
   _commits HashMap      hash → Commit 을 O(1)로 꺼내 parents를 읽는 통로

   ★ result를 리스트로 쓰기 때문에 _contains가 O(n) 선형 탐색입니다.
     HashMap이나 set을 썼다면 O(1)이 됩니다. (개선 포인트)
```

### 프로그램 흐름

```
repo.ancestors("C000004")
  ├ _commits.contains(hash) 아니면 → "Unknown commit: C000004"
  ├ result = [], stack = []
  ├ 시작 커밋의 parents를 stack에 push        ◀ 자기 자신 제외
  ├ while stack:
  │     ├ current = stack.pop()               (LIFO → DFS)
  │     ├ _contains(result, current) 이면 continue   (중복 방문 방지)
  │     ├ result.append(current)
  │     └ _commits.get(current).parents 를 전부 push
  └ result 비었으면 "No ancestors", 아니면 result
```

## 10. SEARCH (키워드)

### 명령어

```text
SEARCH <keyword>
SEARCH login
```

### 개요

메시지에 그 단어가 들어간 커밋을 찾습니다. **커밋을 전부 훑지 않고**,
커밋할 때 미리 만들어 둔 `단어 → 커밋 목록` 서랍에서 바로 꺼냅니다.

```text
C000001 | alice | ... | Add login feature
C000002 | alice | ... | Fix login bug
```

### 알아야 하는 알고리즘 / 개념

- **역색인 (Inverted Index)**
  - 정방향: `문서 → 그 문서의 단어들`
  - **역방향: `단어 → 그 단어를 가진 문서들`** ← 검색 엔진의 기본 자료구조
- **시간복잡도 비교** (커밋 n개, 커밋당 평균 토큰 m개, 결과 k개)
{1번째: x 커밋해쉬
2번쨰: y 커밋해쉬
  | 방식 | 검색 비용 |
  |---|---|
  | 전체 순회 | O(n × m) — 모든 커밋의 모든 단어 확인 |
  | 역색인 | **O(1) + O(k)** — 해시맵 조회 1번 + 결과 출력 |

  → **커밋이 아무리 많아져도 검색 비용은 결과 개수에만 비례**합니다.
  대신 저장 공간과 커밋 시점의 비용이 늘어납니다(시간–공간 트레이드오프).
- **정규화(normalization)**: `lower()`로 통일해야 `Login`과 `login`이 같은 키가 됩니다.
- **직접 만든 HashMap**: 체이닝 충돌 해결 + 적재율 0.75 리사이즈 (0-4절 참고)

### 자료구조 도식

#### (1) 정방향 vs 역방향 — 같은 데이터를 뒤집어 놓은 것

```
정방향 (_commits)                        역방향 (_keyword_index)

C000001 → "Add login feature"            "add"     → [C000001, C000003]
C000002 → "Fix login bug"                "login"   → [C000001, C000002]
C000003 → "Add feature page"             "feature" → [C000001, C000003]
C000004 → "Update readme"                "fix"     → [C000002]
                                         "bug"     → [C000002]
"login이 든 커밋?"                        "page"    → [C000003]
 → 4개 전부 열어서 확인 O(n×m)            "update"  → [C000004]
                                         "readme"  → [C000004]

                                        "login이 든 커밋?"
                                         → 서랍 하나 열면 끝 O(1)
```

#### (2) 저장 시점 — COMMIT이 인덱스를 채우는 과정

```
COMMIT "Fix login bug"   (hash = C000002)
            │
            ▼  message.split()
      ["Fix", "login", "bug"]
            │
            ▼  각각 lower()
      ["fix", "login", "bug"]
            │
            ▼  _add_index_value(_keyword_index, token, "C000002")
   ┌──────────────────────────────────────────────────────────┐
   │ "fix"   : get → None  →  빈 리스트 put  →  ["C000002"]     │
   │ "login" : get → ["C000001"]  →  append  →  ["C000001","C000002"]  ★
   │ "bug"   : get → None  →  빈 리스트 put  →  ["C000002"]     │
   └──────────────────────────────────────────────────────────┘
     ▲ 리스트 "객체"를 꺼내 append 하므로 다시 put 할 필요가 없다
       (get이 참조를 돌려주기 때문)
```

#### (3) 조회 시점 — `SEARCH login` 의 2단 점프

```
   "login"
      │
      │ ① _keyword_index.get("login")
      │      _hash("login") % 16 = 9  →  서랍 9만 확인
      ▼
   ┌─ _keyword_index 서랍 9 ────────────────────────────────────┐
   │ Entry("update", ["C000004"]) ─next─▶ Entry("login", [...]) │
   │        ▲ 키 불일치, 다음                    ▲ 키 일치! 값 반환   │
   └────────────────────────────────────────────────────────────┘
      │
      ▼  hashes = ["C000001", "C000002"]
      │
      │ ② 각 hash마다 _commits.get(hash)      ← 2단 점프
      ▼
   ┌─ _commits (cap=8) ───────────────────────┐
   │ 서랍 4 → Commit(C000001)                  │
   │ 서랍 5 → Commit(C000002)                  │
   └───────────────────────────────────────────┘
      │
      ▼  _format_commit
   "C000001 | alice | ... | Add login feature"
   "C000002 | alice | ... | Fix login bug"

   ★ 훑은 커밋 수 = 결과 개수 2개.  나머지 C000003, C000004는 건드리지도 않음
```

#### (4) 이 구조의 한계

```
   SEARCH log        →  "log" 키가 없음  →  "No commits"
                        ("login"은 찾지 못한다. 토큰 "완전 일치"만 지원)

   SEARCH "login,"   →  구두점이 붙은 토큰은 별개 키가 된다
                        (message.split()은 공백으로만 자르므로)

   부분 문자열 검색이 필요하면 n-gram 인덱스,
   구두점 제거가 필요하면 정규화 단계 강화가 필요합니다.
```

### 프로그램 흐름

```
cli._run_search: "--author=" 로 시작하지 않음 → 키워드 검색
  └ repo.search_keyword("login")
        ├ _is_ready() / keyword 검사
        ├ hashes = _keyword_index.get("login")     ◀ 평균 O(1), 순회 없음
        └ _format_hashes(hashes)
              ├ None 또는 빈 목록 → "No commits"
              ├ 각 hash → _commits.get(hash) 로 Commit 복원
              └ _format_commit 으로 한 줄씩
```

## 11. SEARCH --author=

### 명령어

```text
SEARCH --author=<name>
SEARCH --author=alice
```

### 개요

특정 작성자가 쓴 커밋을 찾습니다. **방식은 키워드 검색과 완전히 같고, 보는 서랍만 바뀝니다.**

### 알아야 하는 알고리즘 / 개념

- **최소 2종 인덱스 요구사항**: `keyword → hash 목록`, `author → hash 목록`
  같은 역색인 구조를 키 종류만 달리해 재사용
- **옵션 파싱**: `split("=", 1)` — maxsplit을 1로 두는 이유는 이름 안에 `=`가 있어도
  **첫 번째 `=`에서만** 자르기 위해서
- **인덱스 갱신 위치**: COMMIT 시점에 `commit.author.lower()` 키로 한 번 등록

### 자료구조 도식

#### 두 인덱스는 쌍둥이 구조 — 키의 종류만 다르다

```
┌─────────── _keyword_index (cap=16, size=8) ───────────┐
│  키: 메시지 토큰                                        │
│  "add" → [C000001, C000003]                            │
│  "login" → [C000001, C000002]     ... 총 8개 키          │
└────────────────────────────────────────────────────────┘

┌─────────── _author_index (cap=4, size=1) ─────────────┐
│  키: 작성자 이름                                        │
│  서랍 0 │ Entry("alice", ["C000001","C000002",         │
│                            "C000003","C000004"])       │
│  서랍 1~3 │ None                                        │
└────────────────────────────────────────────────────────┘
      ▲ _hash("alice") % 4 = 0
        키가 하나뿐이라 리사이즈가 한 번도 일어나지 않았다
```

#### 옵션 파싱과 조회 경로

```
   입력 문자열       "--author=alice"
        │
        │ startswith("--author=")  → 작성자 검색으로 분기
        ▼
   split("=", 1)  →  ["--author", "alice"]
        │                            └─ [1] 을 취함
        ▼
   repo.search_author("alice")
        │
        │ author.lower() → "alice"
        ▼
   _author_index.get("alice")   서랍 0 → 사슬 1칸 → 값 반환   O(1)
        │
        ▼  ["C000001","C000002","C000003","C000004"]
        │
        │  각각 _commits.get(hash)
        ▼
   4줄 출력
```

#### 왜 `split("=", 1)` 인가

```
   "--author=a=b"

   split("=")     →  ["--author", "a", "b"]   ✗  이름이 잘려버림
   split("=", 1)  →  ["--author", "a=b"]      ✓  첫 = 에서만 자름
```

### 프로그램 흐름

```
cli._run_search: query.startswith("--author=")
  ├ author = query.split("=", 1)[1]        →  "alice"
  └ repo.search_author("alice")
        ├ hashes = _author_index.get("alice")     ◀ 평균 O(1)
        └ _format_hashes(hashes)
```

## 12. exit / quit

### 명령어

```text
exit
quit
```

### 개요

REPL을 종료합니다. `Ctrl+C`(KeyboardInterrupt), `Ctrl+D`(EOFError)로도 조용히 끝납니다.

### 알아야 하는 알고리즘 / 개념

- **REPL (Read–Eval–Print Loop)**: 읽고 → 실행하고 → 출력하기를 반복하는 대화형 구조
- **종료 신호를 `None`으로 표현**
  - `list` → 화면에 출력할 문장들
  - `None` → "프로그램을 끝내라"
- **예외를 이용한 정상 종료**: `EOFError` / `KeyboardInterrupt` 를 잡아 `return 0`
- **종료 코드**: `main.py`의 `sys.exit(main())` — 0이면 정상 종료

### 자료구조 도식

**저장소 객체의 수명 — 이것이 상태가 유지되는 이유**

```
   repl() 시작
      repo = MiniGit()          ◀── 딱 한 번 생성
         │
         │  이 참조 하나가 while 루프 전체에서 살아 있다
         ▼
   ┌─────────────────────────────────────────────┐
   │  while True:                                │
   │     line = input("mini-git> ")              │
   │     output = run_command(repo, line)  ──────┼─▶ 같은 repo에 계속 접근
   │     if output is None: return 0             │
   │     for row in output: print(row)           │
   └─────────────────────────────────────────────┘
         │
         │  repo가 살아 있으므로 _commits, _branches, 인덱스가 모두 유지
         ▼
   프로그램 종료 → 메모리에서 사라짐  (파일에 저장하지 않는 in-memory 구현)
```

**반환값이 흐르는 통로**

```
   run_command 반환값
      ├ []          →  아무것도 출력하지 않음 (빈 줄 입력)
      ├ ["...", ..] →  for row in output: print(row)
      └ None        →  return 0   ◀── 종료 신호
                          │
                          ▼
                     main() 반환값
                          │
                          ▼
                     sys.exit(0)   프로세스 종료 코드
```

### 프로그램 흐름

```
repl()
  ├ repo = MiniGit()          저장소를 한 번만 만들어 계속 재사용
  └ while True:
        ├ line = input("mini-git> ")
        │     ├ EOFError           → print(); return 0
        │     └ KeyboardInterrupt  → print(); return 0
        ├ output = run_command(repo, line)
        ├ output is None → return 0        ◀ exit / quit
        └ for row in output: print(row)
```

## 13. 자료구조 관점 총정리

### 13-1. 명령어 × 자료구조 매트릭스

| 명령어 | 읽는 자료구조 | 쓰는 자료구조 | 핵심 알고리즘 | 복잡도 |
|---|---|---|---|---|
| `INIT` | — | `_branches`, 스칼라 전부 | 상태 초기화 | O(1) |
| `COMMIT` | `_branches` | `_commits`, `_commit_order`, `_branches`, `_keyword_index`, `_author_index` | 노드 추가 + 역색인 갱신 | O(m) |
| `BRANCH` | `_branches` | `_branches` | 포인터 추가 | O(1) 평균 |
| `SWITCH` | `_branches` | `head_branch` | 포인터 이동 | O(1) 평균 |
| `LOG` | `_commit_order`, `_commits` | — | 위상 정렬(생성순으로 대체) | O(n) |
| `LOG --sort-by=date` | 〃 | — | Merge Sort (안정) | O(n log n) |
| `LOG --sort-by=author` | 〃 | — | Merge Sort (비교함수 교체) | O(n log n) |
| `PATH` | `_commits`, `_commit_order` | — | BFS + 사전순 tie-break | O(V+E) 이상 |
| `ANCESTORS` | `_commits` | — | DFS (스택) | O(V+E) |
| `SEARCH` | `_keyword_index`, `_commits` | — | 해시 조회 | O(1) + O(k) |
| `SEARCH --author=` | `_author_index`, `_commits` | — | 해시 조회 | O(1) + O(k) |
| `exit` / `quit` | — | — | REPL 종료 | O(1) |

### 13-2. 최종 메모리 스냅샷 (시나리오 전부 실행 후)

```
┌──────────────────────────── MiniGit ────────────────────────────┐
│ initialized=True  author="alice"  head_branch="main"  _counter=4│
├─────────────────────────────────────────────────────────────────┤
│ _commits  HashMap cap=8 size=4                                  │
│   4 │ "C000001" → Commit(parents=[])                            │
│   5 │ "C000002" → Commit(parents=["C000001"])                   │
│   6 │ "C000003" → Commit(parents=["C000002"])                   │
│   7 │ "C000004" → Commit(parents=["C000002"])                   │
├─────────────────────────────────────────────────────────────────┤
│ _branches HashMap cap=4 size=2                                  │
│   1 │ "main"    → "C000004"     ◀── HEAD가 가리키는 브랜치        │
│   2 │ "feature" → "C000003"                                     │
├─────────────────────────────────────────────────────────────────┤
│ _commit_order list                                              │
│   ["C000001", "C000002", "C000003", "C000004"]                  │
├─────────────────────────────────────────────────────────────────┤
│ _keyword_index HashMap cap=16 size=8                            │
│    1 │ "add"     → [C000001, C000003]                           │
│    4 │ "bug"     → [C000002]                                    │
│    5 │ "fix"     → [C000002]                                    │
│    6 │ "feature" → [C000001, C000003]                           │
│    9 │ "update"  → [C000004] ─▶ "login" → [C000001, C000002]    │
│   14 │ "readme"  → [C000004]                                    │
│   15 │ "page"    → [C000003]                                    │
├─────────────────────────────────────────────────────────────────┤
│ _author_index HashMap cap=4 size=1                              │
│    0 │ "alice"   → [C000001, C000002, C000003, C000004]         │
└─────────────────────────────────────────────────────────────────┘
```

### 13-3. "저장 vs 조회" 한 장 요약

```
                    ┌──────────── 저장(WRITE) ────────────┐
   COMMIT 한 번에    │ ① 노드    _commits.put(hash, obj)   │
   5곳을 갱신 ──────▶│ ② 순서    _commit_order.append      │
                    │ ③ 포인터  _branches.put(head, hash) │
                    │ ④ 작성자  _author_index  append     │
                    │ ⑤ 단어들  _keyword_index append × m │
                    └─────────────────────────────────────┘
                                    │
                     저장 때 미리 정리해 둔 덕분에
                                    ▼
                    ┌──────────── 조회(READ) ─────────────┐
   LOG        ──────▶│ _commit_order 순회 → _commits.get   │ O(n)
   LOG --sort ──────▶│ 위 + merge_sort                     │ O(n log n)
   SEARCH     ──────▶│ 인덱스 get 1회 → _commits.get × k   │ O(1)+O(k)
   ANCESTORS  ──────▶│ _commits.get 로 parents 따라 DFS    │ O(V+E)
   PATH       ──────▶│ parents + 자식 역추적으로 BFS        │ O(V+E)~
                    └─────────────────────────────────────┘
```

## 14. 과제 목표 자가 점검 (스스로 답해보기)

1. **커밋 그래프가 왜 DAG인가?**
   부모는 항상 먼저 만들어진 커밋이므로 간선이 과거 방향으로만 향하고, 사이클이 생길 수 없다.

2. **부모가 먼저 출력되는 로그를 어떻게 만드는가?**
   위상 정렬이 필요하다. 이 구현에서는 커밋 생성 순서(`_commit_order`)가 이미 유효한 위상 정렬
   순서이므로 그대로 사용한다.

3. **두 커밋 사이 최단 경로는 어떻게 찾는가?**
   부모/자식을 무방향 간선으로 보고 BFS. 가중치가 없으므로 처음 도달한 깊이가 최단 거리다.

4. **모든 조상은 어떻게 탐색하는가?**
   부모 방향으로만 스택 기반 DFS. `result`를 방문 표시로 겸용해 중복을 막는다.

5. **직접 구현한 정렬의 복잡도는?**
   Merge Sort — 평균/최악 모두 O(n log n), 공간 O(n).

6. **그 정렬은 안정 정렬인가?**
   그렇다. `_merge`에서 비교 결과가 0(동률)일 때 `<= 0` 조건에 걸려 왼쪽(원래 앞쪽) 조각을
   먼저 넣기 때문이다.

7. **역색인의 동작 원리는?**
   저장 시점에 `단어 → 커밋 목록` 매핑을 미리 만들어 두고, 검색 시점에는 해시 조회 한 번으로
   후보를 바로 꺼낸다.

8. **역색인이 전체 순회보다 왜 빠른가?**
   전체 순회는 O(n×m)이지만 역색인은 해시 조회 O(1) 후 결과 개수 k에만 비례한다.
   커밋이 늘어나도 검색 비용이 늘지 않는다.

### 보너스 — 면접/구술에서 나올 만한 질문

- **HashMap의 적재율을 0.75로 잡는 이유는?**
  너무 높으면 사슬이 길어져 조회가 O(n)에 가까워지고, 너무 낮으면 메모리를 낭비하며
  리사이즈가 잦아진다. 0.75는 시간–공간의 경험적 균형점이다.

- **`ANCESTORS`의 `result`를 리스트 대신 HashMap으로 바꾸면?**
  `_contains`의 O(n) 선형 탐색이 O(1)이 되어 전체가 O(V+E)로 확실히 떨어진다.

- **`_neighbors`가 매번 전체를 훑는 문제를 어떻게 개선하나?**
  COMMIT 시점에 `_children_index` (부모 hash → 자식 hash 목록) 역색인을 하나 더 만들어 두면
  자식 조회도 O(1)이 된다. 역색인 아이디어를 그래프 간선에 그대로 적용하는 것이다.

- **커밋 hash를 SHA 기반으로 바꾸면 무엇이 달라지나?**
  내용이 같으면 같은 hash가 나오므로 중복 저장을 피할 수 있고, 무결성 검증이 가능해진다.
  대신 충돌 확률(사실상 0)과 계산 비용을 고려해야 한다.
