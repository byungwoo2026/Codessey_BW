## 0. 기준 시나리오

이 문서의 모든 예시는 아래 한 세션의 결과입니다.

```text
INIT alice
COMMIT "Add login feature"
COMMIT "Add logout feature"
BRANCH feature
SWITCH feature
COMMIT "Fix login bug"
SWITCH main
COMMIT "Update readme"
```

만들어지는 커밋 그래프는 다음과 같습니다.

```text
C000001  Add login feature
   |
C000002  Add logout feature        <- 여기서 갈라짐
   |\
   | \
   |  C000003  Fix login bug       (feature 브랜치)
   |
   C000004  Update readme          (main 브랜치)
```

`C000002`에서 갈라져 나온 `C000003`과 `C000004`가 이 문서의 핵심 예시입니다. 두 커밋은 부모 자식 관계가 아니라 형제 관계이므로, 리스트로는 표현할 수 없는 구조입니다.

### 1. 커밋 그래프를 구현하고, Git의 커밋 구조가 왜 DAG인지 설명할 수 있다

**해답**

커밋 하나가 노드이고, 각 커밋이 들고 있는 `parents` 목록이 간선입니다. 커밋은 만들어질 때 "그 시점의 HEAD"를 부모로 기록하는데, 부모는 반드시 자신보다 먼저 존재하던 커밋입니다. 따라서 간선은 항상 과거 방향으로만 향하고, 되돌아오는 길이 만들어질 수 없습니다. 방향이 있고(Directed) 순환이 없으므로(Acyclic) DAG입니다.

**설명**

DAG의 세 조건을 코드에서 확인하면 이렇습니다.

| 조건 | 코드에서 보장되는 방식 |
| --- | --- |
| 노드 | `Commit` 객체 하나가 노드 하나 |
| 방향 있는 간선 | `parents`는 "내가 가리키는 부모"만 담는다. 부모는 자식을 모른다 |
| 순환 없음 | 부모는 이미 존재하는 커밋만 될 수 있다. 미래 커밋을 부모로 지정하는 경로가 아예 없다 |

트리가 아니라 그래프인 이유도 여기 있습니다. `C000002`처럼 자식이 둘 이상일 수 있고, 병합 커밋을 만든다면 부모도 둘이 될 수 있습니다. 부모가 둘인 노드는 트리 정의에 어긋나므로 일반 그래프로 다뤄야 합니다.

**근거 코드**

- [models.py](mini_git/models.py) — `parents: list[str]` 필드가 간선
- [repository.py:94](mini_git/repository.py:94) `commit()` — `parent = self._current_head()`로 현재 HEAD를 부모로 삼는 부분

**확인**

```text
mini-git> LOG
C000001 | alice | ... | parents=- | Add login feature
C000002 | alice | ... | parents=C000001 | Add logout feature
C000003 | alice | ... | parents=C000002 | Fix login bug
C000004 | alice | ... | parents=C000002 | Update readme
```

`C000003`과 `C000004`가 똑같이 `parents=C000002`인 것이 갈라짐의 증거입니다.

### 2. 부모가 먼저 출력되는 로그를 만들기 위해 어떤 접근이 필요한지 설명할 수 있다

**해답**

위상 정렬이 필요합니다. 다만 이 구현에서는 별도의 정렬 알고리즘을 돌리지 않고, 커밋이 만들어진 순서를 그대로 기록해 두었다가 그 순서로 출력합니다. 부모는 항상 자식보다 먼저 만들어지므로 생성 순서 자체가 이미 유효한 위상 정렬 순서이기 때문입니다.

**설명**

위상 정렬의 조건은 "모든 간선 u -> v에 대해 u가 v보다 먼저 나온다"입니다. 여기서 간선은 자식 -> 부모 방향이므로, 부모가 자식보다 앞서면 조건을 만족합니다.

`COMMIT`을 실행할 때마다 `_commit_order` 리스트 뒤에 hash를 덧붙입니다. 그리고 커밋은 반드시 부모가 존재한 뒤에야 만들어집니다. 즉 리스트에 부모가 먼저 들어가고 자식이 나중에 들어가는 것이 구조적으로 보장됩니다.

일반적인 위상 정렬 알고리즘(칸 알고리즘, DFS 기반)을 쓴다면 진입 차수를 세거나 후위 순회를 해야 하지만, 이 경우에는 삽입 순서가 그 결과와 같으므로 O(n)에 끝납니다. 저장 시점에 이미 순서를 지켜서 넣었기 때문입니다.

**근거 코드**

- [repository.py:128](mini_git/repository.py:128) `log()` — `_commit_order`를 그대로 순회
- [repository.py:94](mini_git/repository.py:94) `commit()` — `self._commit_order.append(commit.hash)`

**확인**

위 `LOG` 출력에서 `C000001`이 `C000002`보다, `C000002`가 `C000003`과 `C000004`보다 먼저 나옵니다.

### 3. 두 커밋 사이의 최단 경로를 찾는 방법을 설명할 수 있다

**해답**

BFS(너비 우선 탐색)를 사용합니다. 단, 부모 자식 연결을 방향 없는 선으로 취급합니다.

**설명**

`C000003`에서 `C000004`로 가는 길을 생각해 보면, 두 커밋은 서로 조상 관계가 아닙니다. 부모 방향으로만 움직여서는 절대 만날 수 없습니다. 공통 조상인 `C000002`까지 내려갔다가 다시 자식 방향으로 올라와야 합니다. 그래서 이웃을 구할 때 부모와 자식을 모두 포함시킵니다.

BFS를 쓰는 이유는 간선 수가 가장 적은 경로를 찾기 위해서입니다. BFS는 출발점에서 가까운 순서대로 넓혀 나가므로, 목적지에 처음 도달한 깊이가 곧 최단 거리입니다.

동점 처리도 필요합니다. 같은 길이의 경로가 여러 개일 수 있으므로 하나를 찾아도 즉시 멈추지 않고, 같은 깊이까지는 계속 모읍니다. 그다음 각 경로를 `hash1->hash2` 문자열로 만들어 사전순으로 정렬하고 첫 번째를 고릅니다.

경로가 아예 없으면 `No path`를 출력합니다. 커밋 그래프가 서로 이어지지 않은 덩어리로 나뉘어 있을 때 발생합니다.

**근거 코드**

- [repository.py:224](mini_git/repository.py:224) `path()` — 입력 검사와 동점 경로 선택
- [repository.py:333](mini_git/repository.py:333) `_shortest_paths()` — BFS 본체
- [repository.py:382](mini_git/repository.py:382) `_neighbors()` — 부모와 자식을 모두 이웃으로 수집

**확인**

```text
mini-git> PATH C000003 C000004
C000003->C000002->C000004

mini-git> PATH C000001 C000004
C000001->C000002->C000004
```

`C000003 -> C000004`가 공통 조상 `C000002`를 거쳐 가는 것이 방향을 무시한다는 증거입니다.

### 4. 특정 커밋의 모든 조상을 탐색하는 방법을 설명할 수 있다

**해답**

시작 커밋의 부모들을 스택에 넣고, 하나씩 꺼내면서 그 커밋의 부모들을 다시 스택에 넣기를 반복합니다. 스택이 빌 때까지 돌면 도달 가능한 모든 조상을 방문하게 됩니다. 스택을 쓰므로 DFS입니다.

**설명**

핵심은 방문 여부 확인입니다. 그래프가 갈라졌다 합쳐지면 같은 조상에 여러 경로로 도달할 수 있습니다. 이미 결과 목록에 있는 커밋은 건너뛰어야 중복 출력과 무한 반복을 막을 수 있습니다.

BFS로 구현해도 결과 집합은 같습니다. "모두 방문"이 목적이라 순서가 중요하지 않기 때문입니다. 스택 대신 큐를 쓰면 세대별로 출력되고, 지금처럼 스택을 쓰면 한 갈래를 끝까지 따라간 뒤 다음 갈래로 넘어갑니다.

시간복잡도는 커밋 수 n, 간선 수 e에 대해 O(n + e)입니다. 각 커밋을 한 번씩만 방문하기 때문입니다.

**근거 코드**

- [repository.py:186](mini_git/repository.py:186) `ancestors()`

**확인**

```text
mini-git> ANCESTORS C000004
C000002
C000001

mini-git> ANCESTORS C000001
No ancestors
```

`C000001`은 최초 커밋이라 부모가 없으므로 `No ancestors`가 나옵니다.

### 5. 정렬 알고리즘을 직접 구현하고 평균/최악 시간복잡도를 설명할 수 있다

**해답**

merge sort(병합 정렬)를 직접 구현했습니다. 평균과 최악 모두 O(n log n)이고, 추가 공간을 O(n)만큼 사용합니다.

**설명**

동작은 세 단계입니다.

```text
1) 분할 : 리스트를 절반으로 계속 쪼갠다        -> 깊이 log n 단계
2) 정복 : 크기가 1이 되면 그 자체로 정렬 완료
3) 병합 : 정렬된 두 조각을 앞에서부터 비교하며 합친다 -> 각 단계마다 O(n)
```

각 단계에서 원소를 한 번씩 훑으므로 단계당 O(n)이고, 단계 수가 log n이므로 곱해서 O(n log n)입니다. 중요한 점은 입력이 이미 정렬되어 있든 거꾸로 되어 있든 분할 횟수가 똑같다는 것입니다. 그래서 최선, 평균, 최악이 모두 O(n log n)으로 같습니다.

퀵 정렬과 비교하면 이 차이가 분명해집니다.

| 알고리즘 | 평균 | 최악 | 추가 공간 | 안정성 |
| --- | --- | --- | --- | --- |
| merge sort | O(n log n) | O(n log n) | O(n) | 안정 |
| quick sort | O(n log n) | O(n²) | O(log n) | 불안정 |

퀵 정렬은 피벗이 계속 한쪽으로 치우치면 O(n²)까지 나빠집니다. 커밋 로그처럼 이미 시간순으로 정렬된 데이터를 다시 시간순으로 정렬하는 상황은 정확히 그 최악 케이스에 해당합니다. 그래서 merge sort를 선택했습니다.

비교 기준을 바꿔 끼울 수 있게 만든 점도 요구사항입니다. `merge_sort(items, compare)` 형태로 비교 함수를 인자로 받기 때문에, 정렬 코드는 그대로 두고 `_compare_by_date`나 `_compare_by_author`만 갈아 끼우면 됩니다.

**근거 코드**

- [sorting.py:19](mini_git/sorting.py:19) `merge_sort()` — 분할과 재귀
- [sorting.py:40](mini_git/sorting.py:40) `_merge()` — 병합
- [repository.py:435](mini_git/repository.py:435) `_compare_by_date()`, `_compare_by_author()` — 갈아 끼우는 비교 기준

### 6. 직접 구현한 정렬이 안정 정렬인지 여부를 설명할 수 있다

**해답**

안정 정렬입니다. 비교 결과가 같을 때(0) 항상 왼쪽 조각의 원소를 먼저 넣기 때문입니다.

**설명**

안정 정렬이란 값이 같은 원소들의 원래 순서가 정렬 후에도 유지되는 것을 말합니다.

`_merge()`의 판정 조건이 핵심입니다.

```python
if compare(left[left_index], right[right_index]) <= 0:
    result.append(left[left_index])
```

`<` 가 아니라 `<=` 라는 점이 중요합니다. 비교 결과가 0, 즉 동점일 때 왼쪽을 먼저 넣습니다. 그리고 `merge_sort()`에서 `left`는 `items[:mid]`, 즉 원본에서 앞쪽에 있던 조각입니다. 따라서 동점이면 원래 앞에 있던 원소가 그대로 앞에 남습니다.

만약 조건을 `< 0`으로 바꾸면 동점일 때 오른쪽을 먼저 넣게 되어 순서가 뒤집히고, 안정성이 깨집니다.

다만 이 구현에서는 안정성에 기대지 않고 한 단계 더 안전하게 만들었습니다. `_compare_by_date`와 `_compare_by_author`는 1차 기준이 같을 때 hash를 2차 기준으로 비교합니다.

```python
date_result = _compare_text(left.timestamp, right.timestamp)
if date_result != 0:
    return date_result
return _compare_text(left.hash, right.hash)
```

이렇게 하면 동점 자체가 사라지므로 결과가 항상 똑같이 재현됩니다. 커밋을 빠르게 여러 개 만들면 timestamp가 초 단위까지 같아질 수 있는데, 그때도 출력이 흔들리지 않습니다.

### 7. 역색인의 동작 원리를 설명할 수 있다

**해답**

커밋을 만드는 시점에 "단어 -> 그 단어를 포함한 커밋 hash 목록" 표를 미리 만들어 둡니다. 검색할 때는 그 표에서 키 하나만 조회하면 답이 나옵니다.

**설명**

이름이 역색인(inverted index)인 이유는 방향이 뒤집혀 있기 때문입니다.

```text
정방향 : 커밋 -> 그 커밋에 들어 있는 단어들
역방향 : 단어 -> 그 단어가 들어 있는 커밋들   <- 이것이 역색인
```

책 뒤에 붙은 찾아보기와 같은 구조입니다. 책을 처음부터 넘기며 단어를 찾는 대신, 찾아보기에서 단어를 보고 페이지 번호로 바로 넘어가는 방식입니다.

`COMMIT`이 실행될 때 색인을 갱신하는 과정은 세 단계입니다.

```text
1) 메시지를 공백 기준으로 자른다      "Add login feature" -> ["Add", "login", "feature"]
2) 소문자로 정규화한다                -> ["add", "login", "feature"]
3) 각 단어를 키로 해서 커밋 hash를 목록에 덧붙인다
```

기준 시나리오를 처리하고 나면 키워드 인덱스가 이렇게 쌓입니다.

```text
"add"     -> [C000001, C000002]
"login"   -> [C000001, C000003]
"logout"  -> [C000002]
"feature" -> [C000001]
"fix"     -> [C000003]
"bug"     -> [C000003]
"update"  -> [C000004]
"readme"  -> [C000004]
```

작성자 인덱스도 같은 방식으로 하나 더 만듭니다.

```text
"alice" -> [C000001, C000002, C000003, C000004]
```

이 표 자체를 직접 만든 `HashMap`에 담기 때문에, 키 조회도 평균 O(1)입니다.

**근거 코드**

- [repository.py:274](mini_git/repository.py:274) `_add_to_indexes()` — 커밋 시점에 색인 갱신
- [repository.py:156](mini_git/repository.py:156) `search_keyword()` — 조회는 `self._keyword_index.get(...)` 한 줄

**확인**

```text
mini-git> SEARCH login
C000001 | alice | ... | Add login feature
C000003 | alice | ... | Fix login bug

mini-git> SEARCH nothing
No commits
```

`C000002`의 "logout"은 `login` 검색에 걸리지 않습니다. 역색인은 단어 단위 완전 일치로 동작하며 부분 문자열 검색이 아니기 때문입니다. 이는 실제 검색 엔진의 기본 색인과 같은 성질입니다.

### 8. 역색인이 전체 순회 검색보다 빠른 이유를 시간복잡도 관점에서 설명할 수 있다

**해답**

전체 순회는 커밋 수에 비례해 O(n × m)이지만, 역색인 조회는 커밋 수와 무관하게 평균 O(1) + O(k)입니다. (n = 커밋 수, m = 메시지 단어 수, k = 실제 결과 개수)

**설명**

두 방식을 나란히 두면 이렇습니다.

| 구분 | 전체 순회 | 역색인 |
| --- | --- | --- |
| 검색 1회 비용 | O(n × m) | O(1) + O(k) |
| 커밋 1회 비용 | O(1) | O(m) |
| 커밋이 10배 늘면 | 검색도 10배 느려짐 | 검색 속도 그대로 |

핵심은 **비용을 옮겼다**는 점입니다. 검색할 때 하던 일을 커밋할 때로 앞당겨 놓았습니다.

커밋 10,000개, 메시지당 단어 5개인 상황을 가정하면 이렇게 차이 납니다.

```text
전체 순회 : 10,000개 커밋 x 5단어 = 50,000번 비교
역색인    : 서랍 1번 조회 + 결과 개수만큼 출력
```

이 교환이 이득인 이유는 호출 빈도가 다르기 때문입니다. 커밋은 한 번 만들고 끝이지만 검색은 수십 번 반복됩니다. 한 번 치르는 비용을 늘리고 여러 번 치르는 비용을 줄인 셈입니다.

대신 대가도 있습니다.

- 메모리를 더 씁니다. 색인 표를 따로 들고 있어야 합니다
- 커밋할 때 할 일이 늘어납니다
- 부분 문자열 검색은 안 됩니다. `log`로 `login`을 찾을 수 없습니다

`SEARCH --author=`도 같은 구조입니다. 작성자로 커밋을 훑으면 O(n)이지만, 색인이 있으면 조회 한 번입니다.

## 2부. 기능 요구 사항 점검

`문제.md` 4장의 요구사항을 항목별로 확인합니다.

### CLI 공통 규칙

| 요구사항 | 구현 | 위치 |
| --- | --- | --- |
| 명령어 대소문자 구분 안 함 | `parts[0].upper()`로 통일 후 비교 | [cli.py](mini_git/cli.py) `run_command()` |
| 공백 포함 인자를 따옴표로 처리 | `shlex.split()` 사용 | [cli.py](mini_git/cli.py) `run_command()` |
| 옵션 표기 통일 | `--sort-by=`, `--author=`를 `split("=", 1)`로 분리 | [cli.py](mini_git/cli.py) `_run_log()`, `_run_search()` |
| 표준 에러 메시지 | `Invalid args`, `Unknown branch:`, `Unknown commit:` | cli.py와 repository.py 전반 |

`shlex.split()`을 쓰는 이유는 따옴표 처리 때문입니다. `COMMIT "Add login feature"`를 단순히 공백으로 자르면 4조각이 되지만, `shlex`는 따옴표를 인식해 `["COMMIT", "Add login feature"]` 2조각으로 잘라 줍니다. 따옴표를 닫지 않으면 `ValueError`가 발생하므로 `Invalid args`로 처리합니다.

확인 결과입니다.

```text
mini-git> init bob
Initialized repository for bob
Current branch: main
mini-git> commit "hello world"
Committed C000001: hello world
mini-git> COMMIT
Invalid args
mini-git> HELLO
Unknown command: HELLO
mini-git> LOG --sort-by=size
Invalid args
```

소문자 `init`, `commit`이 정상 동작하고, 인자 개수가 틀리면 `Invalid args`가 나옵니다.

### 커밋 그래프

| 요구사항 | 구현 |
| --- | --- |
| hash, message, author, timestamp, parents 필드 | `Commit` 데이터클래스에 5개 모두 정의 |
| 부모 0개 이상 | 최초 커밋은 `parents=[]`, 이후는 `[부모hash]` |
| DAG 구조 | 부모는 항상 기존 커밋이므로 순환 불가 |
| hash로 빠른 조회 | 직접 구현한 `HashMap`에 `hash -> Commit` 저장 |
| hash 세션 내 유일 | 증가 카운터 기반 `C000001` 형식 |

hash 유일성은 `_next_hash()`가 담당합니다. 카운터를 1씩 올려가며 만들고, 만에 하나 이미 존재하는 값이면 다음 번호로 넘어갑니다. 카운터는 되돌아가지 않으므로 한 세션 안에서 중복이 발생할 수 없습니다.

### 역색인

요구된 최소 2종을 모두 구현했습니다.

```text
_keyword_index : keyword -> commit_hash 목록
_author_index  : author  -> commit_hash 목록
```

키워드 추출은 요구된 최소 기준을 그대로 따릅니다. 메시지를 공백으로 분리하고, 소문자로 정규화한 뒤 키로 저장합니다.

### 정렬 알고리즘 직접 구현

`sorted()`와 `list.sort()`를 사용하지 않았습니다. 다음 명령으로 확인할 수 있습니다.

```bash
grep -rn "sorted(\|\.sort(" mini_git/ main.py
```

주석에서 금지 API를 언급한 부분만 검색되고, 실제 호출은 없습니다. 비교 기준 교체는 `merge_sort(items, compare)`의 두 번째 인자로 처리합니다.

## 3부. 명령어별 실습 결과

`문제.md` 5장에 나열된 명령을 순서대로 실행한 결과입니다.

### 저장소 및 브랜치 관리

```text
mini-git> INIT alice
Initialized repository for alice
Current branch: main
mini-git> COMMIT "Add login feature"
Committed C000001: Add login feature
mini-git> COMMIT "Add logout feature"
Committed C000002: Add logout feature
mini-git> BRANCH feature
Created branch: feature
mini-git> SWITCH feature
Switched to branch: feature
mini-git> COMMIT "Fix login bug"
Committed C000003: Fix login bug
mini-git> SWITCH main
Switched to branch: main
mini-git> COMMIT "Update readme"
Committed C000004: Update readme
```

여기서 짚을 점은 `BRANCH`가 커밋을 복사하지 않는다는 것입니다. 브랜치는 "특정 커밋을 가리키는 이름표"일 뿐입니다. `BRANCH feature`를 실행한 시점에 `main`과 `feature`는 똑같이 `C000002`를 가리킵니다. 이후 각자 커밋하면서 갈라집니다.

`SWITCH` 역시 데이터를 바꾸지 않고 `head_branch` 값만 바꿉니다.

### 커밋 로그 및 탐색

```text
mini-git> LOG
C000001 | alice | 2026-09-04T13:22:37 | parents=- | Add login feature
C000002 | alice | 2026-09-04T13:22:37 | parents=C000001 | Add logout feature
C000003 | alice | 2026-09-04T13:22:37 | parents=C000002 | Fix login bug
C000004 | alice | 2026-09-04T13:22:37 | parents=C000002 | Update readme

mini-git> PATH C000003 C000004
C000003->C000002->C000004

mini-git> ANCESTORS C000004
C000002
C000001

mini-git> PATH C000001 C999999
Unknown commit: C999999
```

출력 형식은 자유이므로 `hash | author | timestamp | parents | message` 형태로 정했습니다. `parents`를 함께 출력하면 그래프 구조가 눈으로 확인되어 설명하기 좋습니다.

### 검색 및 정렬

```text
mini-git> SEARCH login
C000001 | alice | ... | Add login feature
C000003 | alice | ... | Fix login bug

mini-git> SEARCH --author=alice
C000001 | alice | ... | Add login feature
C000002 | alice | ... | Add logout feature
C000003 | alice | ... | Fix login bug
C000004 | alice | ... | Update readme

mini-git> LOG --sort-by=date
mini-git> LOG --sort-by=author
```

이 시나리오에서는 `--sort-by=date`와 `--sort-by=author`의 결과가 기본 `LOG`와 같습니다. 이유는 두 가지입니다.

- 커밋을 연달아 만들어 timestamp가 초 단위까지 모두 같습니다. 동점이므로 2차 기준인 hash 순으로 정렬되고, hash는 생성 순서와 같습니다
- `INIT`으로 설정한 작성자가 한 명뿐이라 작성자 기준으로도 전부 동점입니다

정렬이 동작하지 않는 것이 아니라, 동점 처리 규칙(hash 순)이 그대로 적용된 결과입니다. 여러 작성자를 만들려면 `INIT`을 다시 실행해야 하는데 그러면 저장소가 초기화되므로, 이 구조에서는 한 세션에 한 명만 존재합니다.

## 4부. 예상 추가 질문

### 파이썬 dict가 이미 해시맵인데 왜 직접 만들었나요

`dict`를 쓰면 한 줄로 끝나지만, 그러면 해시 함수가 어떻게 위치를 정하는지, 충돌이 나면 어떻게 되는지가 보이지 않습니다. 직접 구현하면 문자열이 서랍 번호로 바뀌는 과정, 같은 칸에 여러 개가 들어갈 때의 사슬 구조, 붐빌 때 크기를 늘리는 처리까지 눈으로 확인할 수 있습니다.

### 왜 hash 값에 31을 곱하나요

문자열을 숫자로 바꿀 때 글자 순서가 결과에 반영되도록 하기 위해서입니다. 단순히 글자 코드를 더하기만 하면 `"ab"`와 `"ba"`가 같은 값이 되어 충돌이 늘어납니다. 31은 홀수 소수이면서 컴파일러가 시프트 연산으로 최적화하기 좋아 관례적으로 쓰입니다.

### 충돌이 나면 어떻게 되나요

서로 다른 키가 같은 서랍 번호를 받는 것을 충돌이라 합니다. 이 구현은 체이닝 방식으로, 같은 서랍 안에서 `Entry`를 연결 리스트로 이어 붙입니다. 조회할 때는 그 사슬만 따라가며 키를 비교합니다. 사슬이 길어지면 느려지므로, 채움 비율이 0.75를 넘으면 서랍 수를 2배로 늘리고 전부 다시 담습니다. 이때 서랍 수가 바뀌어 나머지 연산 결과도 바뀌므로 재배치가 필요합니다.

### 해시맵의 O(1)은 항상 보장되나요

평균의 이야기입니다. 최악의 경우 모든 키가 한 서랍에 몰리면 O(n)이 됩니다. 그래서 해시 함수가 값을 골고루 흩어 놓는 것과, 채움 비율을 관리하는 것이 둘 다 필요합니다.

### PATH는 왜 부모 방향만 보지 않나요

부모 방향으로만 이동하면 조상 관계인 두 커밋만 이어집니다. `C000003`과 `C000004`처럼 갈라진 형제 커밋은 서로의 조상이 아니므로 영원히 만날 수 없습니다. 공통 조상까지 내려갔다가 다시 올라가야 하므로, 간선을 방향 없는 것으로 취급해야 합니다.

### ANCESTORS는 DFS인데 PATH는 왜 BFS인가요

목적이 다르기 때문입니다. `ANCESTORS`는 "빠짐없이 모두 방문"이 목적이라 순서가 상관없고, 스택이든 큐든 결과 집합이 같습니다. 반면 `PATH`는 "가장 짧은 경로"를 찾아야 하는데, DFS는 깊이 먼저 내려가므로 먼저 찾은 경로가 최단이라는 보장이 없습니다. BFS는 가까운 곳부터 넓혀 가므로 처음 도달한 깊이가 곧 최단 거리입니다.

### 병합 커밋은 지원되나요

`Commit.parents`가 리스트이므로 자료 구조는 부모가 둘인 커밋을 담을 수 있고, `ANCESTORS`와 `PATH`도 부모가 여러 개인 경우를 그대로 처리합니다. 다만 `MERGE` 명령 자체는 과제 요구사항이 아니어서 구현하지 않았습니다. 명령만 추가하면 탐색 코드는 수정 없이 동작합니다.

### 왜 LOG에 위상 정렬 알고리즘 코드가 없나요

삽입 순서가 이미 위상 정렬 순서이기 때문입니다. 커밋은 부모가 존재한 뒤에만 만들어지므로, 만들어진 순서대로 기록해 두면 부모가 항상 자식보다 앞에 옵니다. 별도 정렬 없이 O(n)에 조건을 만족합니다.
