## 목표 1. 커밋 그래프를 구현하고, Git의 커밋 구조가 왜 DAG인지 설명할 수 있다

### 한 줄 답

> **부모는 항상 나보다 먼저 만들어진 커밋이므로 화살표가 과거 방향으로만 향하고, 따라서 사이클이 생길 수 없다.**

### 설명

**DAG = Directed Acyclic Graph (방향성 비순환 그래프)**

| 용어 | 이 코드에서 |
|---|---|
| **G**raph (그래프) | 커밋들이 서로 연결된 구조 |
| **D**irected (방향성) | 화살표에 방향이 있다 — 자식 → 부모 |
| **A**cyclic (비순환) | 출발점으로 되돌아오는 고리가 없다 |

**노드와 간선**

```
   노드(점)  = 커밋 하나          Commit 객체
   간선(선)  = parents 목록       "나의 부모는 누구다"

   Commit
   ┌──────────────────────────────┐
   │ hash      "C000002"          │  ← 노드의 이름표
   │ message   "2번째"            │
   │ author    "KY"               │
   │ timestamp "2026-09-09 11:05" │
   │ parents   ["C000001"]  ──────┼──▶  간선. 부모의 이름표를 적어둔다
   └──────────────────────────────┘
```

**왜 사이클이 불가능한가**

```
   커밋을 만드는 순간, 부모로 지정할 수 있는 것은
   "이미 만들어져 있는 커밋"뿐이다.

   아직 만들지 않은 미래의 커밋은 이름표조차 없으므로 부모가 될 수 없다.
        ↓
   화살표는 언제나 "나중에 만든 것 → 먼저 만든 것" 방향
        ↓
   되돌아오는 길이 생길 수 없다  =  비순환(Acyclic)
```

**분기와 병합이 있어도 DAG는 유지된다**

```
                     ┌── C000004 ◀── dev
                     │
   C000001 ◀ C000002 ◀ C000003
                     │
                     └── C000005 ◀── main

   C000003이 자식을 둘 가져도(분기),
   병합 커밋이 부모를 둘 가져도(merge),
   모든 화살표는 여전히 과거를 향한다  →  여전히 DAG
```

**트리가 아니라 DAG인 이유**

```
   트리 : 부모가 반드시 1개
   DAG  : 부모가 0개(뿌리), 1개(보통), 2개 이상(병합)  모두 가능

   → 병합 커밋 때문에 트리로는 표현할 수 없다
```

**구현 방식**

```
   _commits  HashMap :  hash → Commit 객체      (노드 저장소)
   Commit.parents    :  부모 hash 목록          (간선)

   ★ 객체를 직접 참조하지 않고 "이름표(문자열)"로만 연결한다
     필요할 때 _commits.get(hash) 로 평균 O(1)에 꺼낸다
```

### 구술용 답변

> 커밋 하나가 노드이고, 각 커밋이 가진 `parents` 목록이 간선입니다.
> 커밋을 만들 때 부모로 지정할 수 있는 것은 이미 존재하는 커밋뿐이라서,
> 간선은 항상 나중에 만든 커밋에서 먼저 만든 커밋 쪽으로만 향합니다.
> 되돌아오는 간선이 만들어질 방법이 없으므로 사이클이 생길 수 없고, 그래서 DAG입니다.
> 병합 커밋은 부모를 둘 이상 가질 수 있어 트리가 아니라 DAG로 봐야 하며,
> 저는 `parents`를 리스트로 두어 이 경우까지 표현할 수 있게 했습니다.
> 구현은 `hash → Commit` 해시맵에 노드를 저장하고, 간선은 부모의 hash 문자열로만 참조합니다.

## 목표 2. 부모가 먼저 출력되는 로그를 만들기 위한 접근을 설명할 수 있다

### 한 줄 답

> **위상 정렬이 필요하지만, 커밋 생성 순서 자체가 이미 유효한 위상 정렬 순서라서 그대로 사용했다.**

### 설명

**요구사항**

```
   단순 최신순 나열이 아니라,
   "부모 커밋이 항상 자식 커밋보다 먼저" 출력되어야 한다
```

**이것이 곧 위상 정렬(Topological Sort)**

```
   위상 정렬 = DAG의 노드를 "간선 방향을 거스르지 않는 순서"로 나열하는 것

   일반적인 구현
     · Kahn 알고리즘  : 진입차수 0인 노드부터 차례로 제거
     · DFS 후위순회 역순
     · 둘 다 O(V + E)
```

**이 구현이 택한 방법 — 계산하지 않는다**

```python
self._commit_order.append(commit.hash)   # COMMIT 할 때마다 뒤에 붙이기
...
for commit_hash in self._commit_order:   # LOG 할 때 앞에서부터 순회
    commit = self._commits.get(commit_hash)
```

**왜 그래도 되는가 — 증명**

```
   커밋 X를 만드는 시점에,
   X의 부모로 지정할 수 있는 것은 "이미 _commit_order에 들어 있는 hash"뿐이다.

   즉 X의 모든 부모는 X보다 앞 인덱스에 있다.
        ↓
   append 순서는 언제나 "부모가 자식보다 앞"을 만족한다
        ↓
   _commit_order 는 이미 유효한 위상 정렬 결과다
```

**실제로 확인**

```
   _commit_order  =  [C000001, C000002, C000003, C000004, C000005]
                        1️⃣        2️⃣        3️⃣        4️⃣        5️⃣

   간선 검사
     C000002 → C000001    1️⃣ 이 2️⃣ 보다 앞   ✅
     C000003 → C000002    2️⃣ 가 3️⃣ 보다 앞   ✅
     C000004 → C000003    3️⃣ 이 4️⃣ 보다 앞   ✅
     C000005 → C000003    3️⃣ 이 5️⃣ 보다 앞   ✅

   모든 간선이 "앞 → 뒤"  →  유효한 위상 정렬
```

**왜 리스트가 따로 필요한가**

```
   해시맵은 순서를 보존하지 않는다.
   칸 번호가 해시 계산으로 정해지므로, 0번 칸이 첫 커밋이라는 보장이 없다.

   실제로 커밋 4개 시점의 _commits (칸 8개)
     [4] C000001   [5] C000002   [6] C000003   [7] C000004
      ▲ 4번 칸부터 시작. 순서를 읽어낼 수 없다

   → "만든 순서"는 리스트가 따로 챙긴다
```

**비용 비교**

```
   위상 정렬을 매번 계산  :  O(V + E)
   _commit_order 순회     :  O(n)          ← 이 구현
```

### 구술용 답변

> 부모가 자식보다 먼저 나와야 하므로 위상 정렬이 필요합니다.
> 다만 이 구현에서는 별도의 위상 정렬 알고리즘을 돌리지 않았습니다.
> 커밋을 만들 때 부모로 지정할 수 있는 것은 이미 생성된 커밋뿐이므로,
> 생성 순서를 기록한 `_commit_order` 리스트가 그 자체로 유효한 위상 정렬 순서이기 때문입니다.
> 해시맵은 순서를 보존하지 않아서, 순서는 별도의 리스트로 관리했습니다.
> 만약 커밋을 임의 순서로 주입받는 구조였다면 Kahn 알고리즘이나 DFS 기반 위상 정렬을
> O(V+E)로 수행해야 했을 것입니다.

## 목표 3-1. 두 커밋 사이의 최단 경로를 찾는 방법을 설명할 수 있다

### 한 줄 답

> **간선을 무방향으로 보고 BFS를 수행한다. 가중치가 없으므로 목적지에 처음 도달한 깊이가 최단 거리다.**

### 설명

**왜 무방향으로 봐야 하는가**

```
                     ┌── C000004
                     │
   C000001 ◀ C000002 ◀ C000003
                     │
                     └── C000005

   C000004와 C000005는 형제 관계다.
   부모 방향으로만 가면 서로 만날 수 없다.
        ↓
   공통 조상까지 내려갔다가 다시 자식 방향으로 올라와야 한다
        ↓
   부모·자식 양쪽을 모두 이웃으로 취급한다 = 무방향 간선
```

```
   C000004 ──부모 방향──▶ C000003 ──자식 방향──▶ C000005
                              공통 조상
```

**왜 BFS인가**

```
   BFS는 가까운 곳부터 한 겹씩 넓혀 나간다

     0걸음   C000004
     1걸음   C000003
     2걸음   C000002,  C000005   ← 목적지 발견
     3걸음   C000001

   → 목적지에 "처음" 닿은 깊이가 곧 최단 거리
   → 모든 간선의 비용이 1(가중치 없음)이므로 BFS로 충분
     가중치가 있었다면 Dijkstra가 필요
```

```
   DFS를 쓰면 한 갈래를 끝까지 파고들다 목적지를 만나는데,
   그것이 최단이라는 보장이 없다.
```

**이 구현의 특징 — 큐에 경로 전체를 담는다**

```
   일반적인 BFS :  큐 = [C000003, C000002, C000005]           (노드만)
   이 구현      :  큐 = [[C000004, C000003],
                        [C000004, C000003, C000002],
                        [C000004, C000003, C000005]]           (경로 전체)

   장점 : 도착하는 순간 경로가 완성되어 있다 (부모 추적 배열 불필요)
          같은 길이의 경로를 여러 개 모으기 쉽다
   단점 : 같은 접두사가 중복 저장되어 메모리를 더 쓴다
```

**세 가지 가지치기**

| 조건 | 목적 |
|---|---|
| 이웃이 현재 경로에 이미 있으면 건너뜀 | 사이클 방지 (왔던 길 되돌아가기) |
| 그 커밋에 더 짧게 도달한 기록이 있으면 건너뜀 | 최단이 될 수 없는 경로 제거 |
| 현재 깊이 > 발견된 최단 깊이면 중단 | 불필요한 탐색 종료 |

**동점 처리**

```
   최단 경로가 여러 개면
     경로를 "hash1->hash2->hash3" 문자열로 만들어 사전순 최소를 선택

   _neighbors 가 이웃을 hash 사전순으로 정렬해 반환하는 것도 같은 목적
```

**이웃 목록 만들기 — 비대칭 비용**

```
   부모 방향 :  commit.parents 를 그대로 읽음                 O(1)
   자식 방향 :  전체 커밋을 훑어 "부모에 나를 가진 것" 검색    O(n)  ★ 병목

   → 역방향 간선이 저장돼 있지 않기 때문
```

**복잡도**

```
   이론적 BFS      :  O(V + E)
   이 구현         :  _neighbors 가 매 호출마다 O(n) → 실질 O(n²)

   개선안 : COMMIT 시점에 "부모 hash → 자식 hash 목록" 색인을 함께 만들면
            자식 조회도 O(1)이 되어 O(V+E)로 회복된다
```

### 구술용 답변

> 서로 다른 브랜치의 두 커밋은 부모 방향으로만 이동해서는 만날 수 없습니다.
> 공통 조상까지 내려갔다가 다시 자식 방향으로 올라와야 하므로,
> 부모와 자식을 모두 이웃으로 보는 무방향 그래프로 취급했습니다.
> 간선에 가중치가 없으므로 BFS로 최단 경로를 구합니다.
> BFS는 가까운 곳부터 한 겹씩 넓히므로, 목적지에 처음 도달한 깊이가 곧 최단 거리입니다.
> 큐에는 노드가 아니라 지나온 경로 전체를 담아, 도착 즉시 경로를 복원할 수 있게 했습니다.
> 최단 경로가 여러 개인 경우에는 경로를 문자열로 만들어 사전순 최소를 선택합니다.
> 다만 자식은 역방향 간선이 저장돼 있지 않아 전체 순회로 찾아야 하고, 이 부분이 병목입니다.
> 자식 색인을 미리 만들어 두면 O(V+E)로 개선할 수 있습니다.

## 목표 3-2. 특정 커밋의 모든 조상을 탐색하는 방법을 설명할 수 있다

### 한 줄 답

> **부모 방향으로만 진행하는 스택 기반 DFS이며, 방문 검사로 중복을 막는다.**

### 설명

**PATH와의 차이**

```
   PATH       :  양방향 (부모 + 자식),  최단 경로 하나,      BFS
   ANCESTORS  :  단방향 (부모만),       도달 가능한 전부,    DFS
```

**동작 방식**

```
   ① 시작 커밋의 부모들을 스택에 올린다   (자기 자신은 조상이 아니므로 제외)
   ② 스택 맨 위에서 하나 꺼낸다
   ③ 이미 결과에 있으면 건너뛴다          ★ 중복 방지
   ④ 결과에 추가한다
   ⑤ 그 커밋의 부모들을 다시 스택에 올린다
   ⑥ 스택이 빌 때까지 반복
```

**추적 예시 — `ANCESTORS C000004`**

```
   준비    스택 [C000003]          결과 []
   1회차   꺼냄 C000003  →  결과 [C3]        부모 C2 push   스택 [C2]
   2회차   꺼냄 C000002  →  결과 [C3,C2]     부모 C1 push   스택 [C1]
   3회차   꺼냄 C000001  →  결과 [C3,C2,C1]  부모 없음      스택 []
   종료
```

**★ 방문 검사가 필요한 이유**

```
   병합 커밋이 있으면 여러 갈래가 같은 조상으로 다시 모인다

          ┌── B ──┐
   A ◀────┤       ├──── M          M.parents = [B, C]
          └── C ──┘                 B.parents = [A],  C.parents = [A]

   방문 검사가 없으면 A를 B 경로로 한 번, C 경로로 또 한 번 방문한다
   갈래가 k번 합쳐지면 방문 횟수가 2^k 규모로 폭발한다

   검사가 있으면 각 노드를 한 번씩만 처리  →  O(V + E)
```

**중복은 스택에서 발생하고, 꺼낼 때 걸러진다**

```
   push 할 때는 검사하지 않는다  →  같은 hash가 스택에 여러 번 올라갈 수 있다
   pop 한 직후에 검사한다        →  결과 목록에는 중복이 들어가지 않는다

   push 시점에 검사해도 되지만, 그 사이 다른 갈래가 처리했을 수 있으므로
   최종 관문은 pop 시점에 두는 것이 안전하다
```

**DFS와 BFS 중 무엇을 써도 되는가**

```
   목적이 "조상 집합 전체"이므로 방문 순서는 결과에 영향을 주지 않는다
   stack.pop()   → LIFO → DFS
   queue.pop(0)  → FIFO → BFS
   집합은 동일하다
```

**현재 구현의 한계와 개선안**

```
   결과 목록이 리스트라서 방문 검사가 선형 탐색이다
       for item in result: if item == value: return True     O(n)
       → 전체가 최악 O(n²)

   해시맵이나 set으로 바꾸면 검사가 평균 O(1)  →  전체 O(V+E)
```

### 구술용 답변

> 커밋 카드에 부모 hash가 적혀 있으므로, 부모 방향으로만 따라 올라가는 그래프 탐색입니다.
> 재귀 대신 스택을 사용한 반복형 DFS로 구현했고, 스택이 빌 때까지 꺼내고 부모를 다시 넣는 방식입니다.
> 핵심은 방문 검사입니다. 병합 커밋이 있으면 여러 갈래가 같은 조상으로 다시 모이는데,
> 검사가 없으면 같은 커밋을 중복 방문해 갈래 수에 대해 지수적으로 느려집니다.
> 검사를 두면 각 노드를 한 번씩만 처리하므로 O(V+E)입니다.
> 목적이 조상 집합 전체를 구하는 것이라 DFS든 BFS든 결과는 같습니다.
> 현재는 방문 검사를 리스트 선형 탐색으로 했는데, 해시맵으로 바꾸면 더 개선할 수 있습니다.

## 목표 4. 정렬 알고리즘을 직접 구현하고, 평균/최악 복잡도와 안정성을 설명할 수 있다

### 한 줄 답

> **merge sort를 구현했다. 평균·최악 모두 O(n log n), 공간 O(n), 안정 정렬이다.**

### 설명

**왜 직접 구현했나**

```
   과제 조건 : sorted() 와 list.sort() 사용 금지
```

**왜 merge sort를 골랐나**

| | merge sort | quick sort |
|---|---|---|
| 평균 | O(n log n) | O(n log n) |
| **최악** | **O(n log n)** | O(n²) |
| 공간 | O(n) | O(log n) |
| **안정성** | **안정** | 불안정 |

```
   최악에서도 성능이 무너지지 않고, 안정 정렬이라는 점이 결정적이었다
```

**동작 원리 — 분할 정복**

```
   ① 분할 : 반으로 쪼갠다 (길이 1이 될 때까지 재귀)
   ② 정복 : 정렬된 두 묶음을 앞에서부터 비교하며 합친다

                  [A, B, C, D]
                  ╱          ╲
             [A, B]        [C, D]
             ╱    ╲        ╱    ╲
          [A]    [B]    [C]    [D]      ← 길이 1이면 이미 정렬됨
             ╲    ╱        ╲    ╱
             [A, B]        [C, D]       ← 합치기
                  ╲          ╱
                  [A, B, C, D]
```

**왜 O(n log n)인가**

```
   분할 깊이  :  n을 계속 반으로  →  log₂n 단계
   각 단계    :  전체 n개를 한 번씩 훑으며 병합  →  O(n)

   log n 단계 × n개 = O(n log n)

   8개 기준
     1단계  [8]                       훑는 양 8
     2단계  [4][4]                    훑는 양 8
     3단계  [2][2][2][2]              훑는 양 8
     4단계  [1]×8                     훑는 양 8
            깊이 3 = log₂8            총 8 × 3 = 24
```

**입력에 상관없이 항상 같은 이유**

```
   merge sort는 무조건 반으로 나눈다  →  분할이 데이터에 의존하지 않는다
   quick sort는 피벗 값에 따라 나뉜다 →  최악에는 한쪽으로 쏠려 O(n²)
```

**★ 안정 정렬인 근거 — 코드의 한 줄**

```python
if compare(left[left_index], right[right_index]) <= 0:
    result.append(left[left_index])     # ← 동점(0)일 때 왼쪽을 먼저
else:
    result.append(right[right_index])
```

```
   왼쪽 묶음은 원래 배열에서 앞에 있던 조각이다
        ↓
   동점일 때 왼쪽을 먼저 넣으면, 동점자의 원래 순서가 보존된다
        ↓
   안정 정렬(stable)

   만약 <= 가 아니라 < 였다면 동점일 때 오른쪽이 먼저 나가서 불안정 정렬이 된다
```

**비교 기준 주입 — 엔진 하나로 네 곳에서 재사용**

```
   merge_sort(항목들, compare)
                        │
                        ├─ _compare_by_date      LOG --sort-by=date
                        ├─ _compare_by_author    LOG --sort-by=author
                        ├─ _compare_text         PATH의 이웃 사전순 정렬
                        └─ _compare_path_text    PATH의 경로 사전순 선택

   compare 규약 : 왼쪽 우선이면 음수, 동점이면 0, 오른쪽 우선이면 양수
```

**동률 처리(tie-break)**

```
   _compare_by_date   : timestamp 같으면  → hash 사전순
   _compare_by_author : author 같으면     → hash 사전순
   author는 lower()로 정규화 → "Park"과 "park"을 같은 그룹으로

   → 같은 입력에 항상 같은 출력 (결정적)
```

### 구술용 답변

> `sorted()` 사용이 금지되어 merge sort를 직접 구현했습니다.
> 반으로 분할한 뒤 정렬된 두 묶음을 병합하는 분할 정복 방식이고,
> 분할 깊이가 log n, 각 단계마다 n개를 훑으므로 평균·최악 모두 O(n log n)입니다.
> 병합용 새 리스트가 필요해 공간복잡도는 O(n)입니다.
> quick sort는 평균은 같지만 피벗이 치우치면 최악 O(n²)이 되는데,
> merge sort는 데이터와 무관하게 항상 반으로 나누므로 성능이 보장됩니다.
> 안정 정렬입니다. 병합할 때 비교 결과가 0인 동점 상황에서 `<= 0` 조건으로 왼쪽 값을 먼저 넣는데,
> 왼쪽은 원래 앞에 있던 조각이므로 동점자의 원래 순서가 그대로 유지됩니다.
> 비교 함수를 인자로 주입받게 만들어, 정렬 엔진 하나로 날짜순·작성자순·문자열순을 모두 처리합니다.

## 목표 5. 역색인의 동작 원리와, 순회 검색보다 빠른 이유를 설명할 수 있다

### 한 줄 답

> **저장 시점에 `단어 → 커밋 목록` 매핑을 미리 만들어 두고, 검색 시점에는 해시 조회 한 번으로 후보를 얻는다. 검색 비용이 전체 데이터 양이 아니라 결과 개수에만 비례한다.**

### 설명

**정방향 vs 역방향**

```
   정방향 (_commits)                      역방향 (_keyword_index)
   커밋 → 그 커밋의 단어들                 단어 → 그 단어를 가진 커밋들

   C000001 → "Add login feature"          "add"     → [C000001, C000003]
   C000002 → "Fix login bug"              "login"   → [C000001, C000002]
   C000003 → "Add feature page"           "feature" → [C000001, C000003]
   C000004 → "Update readme"              "fix"     → [C000002]
                                          "bug"     → [C000002]
   "login이 든 커밋?"                      "page"    → [C000003]
   → 4개를 전부 열어 확인                   "update"  → [C000004]
                                          "readme"  → [C000004]

                                          "login이 든 커밋?"
                                          → 서랍 하나만 열면 끝
```

**저장 시점 — COMMIT이 색인을 채운다**

```
   COMMIT "Fix login bug"   (hash = C000002)
        │
        ▼  message.split()
   ["Fix", "login", "bug"]
        │
        ▼  각각 lower() 로 정규화       ← "Login"과 "login"을 같은 키로
   ["fix", "login", "bug"]
        │
        ▼  각 단어를 키로 hash를 추가
   "fix"   : 키 없음 → 새 목록 생성 → ["C000002"]
   "login" : 키 있음 → 목록에 추가   → ["C000001", "C000002"]
   "bug"   : 키 없음 → 새 목록 생성 → ["C000002"]
```

```
   최소 2종 인덱스 (과제 요구사항)
     keyword → commit_hash 목록
     author  → commit_hash 목록
```

**검색 시점 — 2단 점프**

```
   SEARCH login

   ① 단어 → 이름표      _keyword_index.get("login")
                        해시 계산 → 해당 서랍 하나만 확인
                        → ["C000001", "C000002"]

   ② 이름표 → 커밋      _commits.get("C000001"), _commits.get("C000002")
                        → 카드 2장

   ★ 훑은 커밋 수 = 결과 개수.  나머지 커밋은 건드리지도 않는다
```

**★ 시간복잡도 비교**

```
   n = 전체 커밋 수
   m = 커밋당 평균 토큰 수
   k = 검색 결과 개수
```

| 방식 | 비용 | 의미 |
|---|---|---|
| 전체 순회 | **O(n × m)** | 모든 커밋의 모든 단어를 확인 |
| 역색인 | **O(1) + O(k)** | 해시 조회 1회 + 결과만큼 카드 꺼내기 |

```
   전체 순회 : 커밋이 늘어나면 검색도 그만큼 느려진다
   역색인    : 커밋이 10배로 늘어도 결과 개수가 같으면 검색 시간은 그대로

   커밋 10,000개 / 결과 2개인 경우
     전체 순회 : 10,000개 × 단어 수 만큼 비교
     역색인    : 서랍 1번 + 카드 2장
```

**왜 O(1)인가 — 해시맵 덕분**

```
   문자열 키 → 해시 함수 → 서랍 번호 → 그 서랍만 확인

   _hash(key) : value = (value * 31 + ord(ch)) & 0x7FFFFFFF
                31을 곱해 글자 순서가 바뀌면 결과도 달라지게 한다
   _index     : 해시값 % capacity

   충돌은 체이닝(연결 리스트)으로 해결
   적재율이 0.75를 넘으면 capacity를 2배로 늘리고 전부 재삽입
   → 사슬 길이를 상수로 유지 → 조회 평균 O(1), 최악 O(n)
```

**공짜가 아니다 — 트레이드오프**

```
   얻는 것 : 검색이 O(n×m) → O(1)+O(k)
   내는 것 : ① 커밋 시점 비용 증가 (단어 수 m 만큼 색인 갱신)
             ② 저장 공간 증가 (색인 자체가 메모리를 차지)

   "검색을 빠르게 만드는 비용을 저장 시점으로 옮긴 것"

   → DB에서 인덱스를 많이 만들면 SELECT는 빨라지고
     INSERT/UPDATE는 느려지는 것과 정확히 같은 이유
```

**현재 구현의 한계**

```
   SEARCH log     → "login"을 찾지 못함.  토큰 완전 일치만 지원
   SEARCH "bug,"  → 구두점이 붙으면 다른 키로 취급 (split은 공백으로만 자름)

   개선안 : 부분 문자열 검색은 n-gram 색인,
            구두점 제거는 정규화 단계 강화
```

### 구술용 답변

> 역색인은 정방향 매핑을 뒤집은 자료구조입니다.
> 원래는 커밋이 어떤 단어를 갖는지 저장되어 있는데, 이를 뒤집어
> 단어가 어떤 커밋에 등장하는지를 미리 만들어 둡니다.
> 커밋할 때 메시지를 공백으로 쪼개고 소문자로 정규화한 뒤,
> 각 단어를 키로 해서 커밋 hash를 목록에 추가합니다. 작성자도 같은 방식으로 색인합니다.
> 검색할 때는 해시맵에서 그 단어의 서랍 하나만 열어 후보 hash 목록을 얻고,
> 각 hash로 커밋 객체를 꺼내면 끝입니다.
> 전체 순회는 커밋 수 n과 커밋당 토큰 수 m에 비례해 O(n×m)이지만,
> 역색인은 해시 조회 O(1) 이후 결과 개수 k에만 비례합니다.
> 즉 커밋이 아무리 늘어나도 검색 비용은 결과 개수에만 좌우됩니다.
> 대신 커밋 시점 비용과 저장 공간이 늘어나는 트레이드오프가 있습니다.

## 부록 B. 예상 추가 질문과 답변

**Q. 해시맵 적재율을 0.75로 잡은 이유는?**
> 너무 높으면 충돌 사슬이 길어져 조회가 O(n)에 가까워지고, 너무 낮으면 메모리를 낭비하며
> 리사이즈가 잦아집니다. 0.75는 Java HashMap 등이 채택한 경험적 균형점입니다.

**Q. 리사이즈할 때 왜 전부 다시 넣어야 하나?**
> 서랍 번호가 `해시값 % capacity`로 정해지는데, capacity가 바뀌면 같은 키의 번호도 바뀝니다.
> 옛 자리에 두면 조회가 영영 찾지 못하므로 전체 재삽입(rehash)이 필요합니다.

**Q. 2배씩 늘리는 이유는?**
> 리사이즈 횟수가 log n번으로 억제되고, 총 재삽입 비용이 약 2n이라
> 삽입 1회당 분할상환하면 상수 시간이 됩니다.

**Q. 커밋 hash를 일련번호로 만든 이유는? SHA로 바꾸면?**
> 과제 요구는 "세션 내 유일"뿐이라 일련번호로 충분하고 구현이 단순합니다.
> SHA 기반으로 바꾸면 내용이 같은 커밋이 같은 hash를 갖게 되어 중복 저장을 피할 수 있고
> 무결성 검증도 가능해집니다. 대신 계산 비용이 늘어납니다.

**Q. PATH가 느린 이유와 개선 방법은?**
> 커밋이 부모만 기억하고 자식은 기억하지 않아, 자식을 찾을 때마다 전체를 순회합니다.
> COMMIT 시점에 `부모 hash → 자식 hash 목록` 색인을 함께 만들면 O(1)로 개선됩니다.
> 역색인 아이디어를 그래프 간선에 그대로 적용하는 것입니다.

**Q. MERGE를 구현하지 않았는데 부모가 둘인 경우는?**
> `parents`를 리스트로 두고 모든 탐색을 반복문으로 작성해, 병합 커밋이 추가되어도
> 탐색 코드를 수정할 필요가 없습니다. 다만 병합이 생기면 여러 갈래가 같은 조상으로 모이므로
> 방문 검사가 없으면 탐색이 지수적으로 늘어납니다.
