시연 준비 — 이 순서대로 입력하세요

폴더에서 python main.py 실행 → 아래 명령을 한 줄씩(복사해서 한꺼번에 붙여넣지 말기) 입력합니다.

init "Alice"
status
commit "Initial commit"
branch feature
switch feature
commit "Add login feature"
user Bob
commit "Fix login bug"
switch main
user Alice
commit "Add payment feature"

입력 후 커밋 그래프는 아래 모양이 됩니다. 이 그림 하나로 항목 1의 모든 시연을 설명할 수 있습니다.

주의 ① 한 줄씩 입력 — 시각이 초 단위로 찍힙니다. 명령을 한꺼번에 붙여넣으면 모든 커밋의 시각이 같아져서 LOG --sort-by=date 결과가 LOG와 똑같이 보입니다. 한 줄씩 입력하면 정상입니다.
주의 ② user·status·index·help는 과제 요구에 없는 보조 명령입니다. INIT은 저장소 전체를 초기화하기 때문에, 한 저장소에서 작성자를 바꾸려고 user Bob을 만들었다고 말하면 됩니다(git config user.name과 같은 역할).
주의 ③ “No path” 시연은 프로그램을 다시 시작해서 따로 합니다(항목 1의 4번 참고). hash 번호가 c001부터 다시 시작되어 깔끔합니다.

항목 1 — 동작 시연 (6문항)

PASS 기준은 “요구한 출력이 화면에 나온다”입니다. 각 문항마다 입력 → 기대 출력 → 눈으로 확인할 곳을 적었습니다.

항목 1 · 1/6

INIT <user_name> 실행 후 main 브랜치/HEAD/현재 사용자 설정이 정상적으로 초기화되어 있는가?

핵심 답네. INIT 하면 main 브랜치가 만들어지고, HEAD가 main을 가리키고, 작성자가 설정됩니다. 첫 줄 출력으로 세 가지를 바로 보여 줍니다.
mini-git> init "Alice"
Initialized repository.
Current branch: main          <- main 브랜치 생성 + HEAD가 main
Current user: Alice           <- 현재 사용자(author)
mini-git> status              (보조 명령: 내부 상태 확인)
User: Alice
Current branch: main
HEAD commit: (no commits yet) <- 아직 커밋이 없어서 가리키는 곳이 없음
Branches: main
Total commits: 0
  • INIT 전에 다른 명령을 치면 막힙니다: Repository not initialized. Run INIT <user_name> first
  • init(소문자)도 동작 — 명령어는 대소문자 구분 없음

근거: repository.py init() — branches["main"] = None, head = "main", author = user_name

항목 1 · 2/6

BRANCH <name> 생성 후 SWITCH <name>로 전환되며, 이후 COMMIT이 해당 브랜치에 반영되는가?

핵심 답네. branch feature → switch feature → commit 하면 feature 브랜치만 앞으로 나아가고, main은 그대로입니다. log의 브랜치 표시로 증명합니다.
mini-git> branch feature
Created branch: feature
mini-git> switch feature
Switched to branch: feature
mini-git> commit "Add login feature"
[feature c002] Add login feature      <- 대괄호 안에 브랜치 이름이 찍힌다
...
mini-git> switch main
mini-git> commit "Add payment feature"
[main c004] Add payment feature
mini-git> log   (일부)
commit c004 (Alice, ...) [HEAD -> main]    <- main 끝 = c004, parents: c001
commit c003 (Bob, ...)   [feature]         <- feature 끝 = c003, parents: c002
  • 확인 포인트: c004의 부모는 c001(c003이 아님) → main에서 만든 커밋이 feature 쪽에 섞이지 않았다는 증거
  • status로도 확인: switch 후 Current branch와 HEAD commit이 바뀝니다 (main→c004, feature→c003)
  • 없는 브랜치 전환은 Unknown branch: nope, 같은 이름 재생성은 Branch already exists: feature

근거: repository.py create_branch()(이름표 추가) · switch()(HEAD 이동) · commit()(현재 브랜치 이름표만 새 커밋으로 이동)

항목 1 · 3/6

LOG가 “부모 커밋이 자식 커밋보다 먼저” 출력되도록 동작하는가?

핵심 답네. 시간순이 아니라 위상 정렬(Kahn 알고리즘)로 출력해서, 모든 커밋의 부모가 항상 위쪽에 먼저 나옵니다.
mini-git> log        (요약 표시 — 실제로는 커밋마다 3줄: commit / parents / message)
commit c001 (Alice, 09:00:00)               parents: -
commit c002 (Alice, 09:01:00)               parents: c001
commit c004 (Alice, 09:03:00) [HEAD -> main] parents: c001
commit c003 (Bob,   09:02:00) [feature]      parents: c002
  • 검증 방법: 각 커밋의 parents: 에 적힌 hash가 이미 위에서 나왔는지만 보면 됩니다 (c003의 부모 c002 ✓ / c004의 부모 c001 ✓)
  • 일부러 보여 줄 포인트: c004가 c003보다 위에 있습니다. 시간으로는 c003(09:02)이 더 먼저 만들어졌는데도요 → 시간순 나열이 아니라는 증거 (비교: log --sort-by=date 는 c003이 c004 앞)

근거: graph.py topological_order() — 자세한 원리는 항목 3의 2번

항목 1 · 4/6

PATH <a> <b>가 경로가 있으면 최단 경로를, 없으면 No path를 출력하는가?

핵심 답네. 부모-자식 연결을 방향 없는 선으로 보고 BFS로 최단 경로를 찾고, 이어지지 않으면 No path를 출력합니다.
(경로 있음 — 시연 A에서)
mini-git> path c003 c004
Path: c003 -> c002 -> c001 -> c004     <- 갈라진 브랜치: 공통 조상 c001을 거쳐 감
mini-git> path c001 c003
Path: c001 -> c002 -> c003
mini-git> path c001 c999
Unknown commit: c999                   <- 없는 커밋은 No path가 아니라 에러

“No path”는 프로그램을 다시 시작해서 이렇게 시연합니다 (뿌리 커밋이 2개인 상태를 만든다):

init "Alice"
branch dev            <- 첫 커밋 전에 브랜치를 만든다
commit "Root one"     <- [main c001] 부모 없음
switch dev
commit "Root two"     <- [dev c002]  부모 없음 (c001과 이어지지 않음)
path c001 c002
No path
  • 왜 이렇게 해야 No path가 나오나: 보통의 커밋은 항상 이전 커밋과 이어져서 모두 한 가족입니다. 뿌리가 둘이어야 이어지지 않는 두 덩어리가 생깁니다.
  • “c003→c004 경로가 왜 길이 3이죠?” → 두 끝 커밋은 서로 조상이 아니라서, c001까지 내려갔다가 다시 올라와야 합니다.

근거: graph.py shortest_path() · cli.py _cmd_path()(None이면 “No path”)

항목 1 · 5/6

ANCESTORS <hash>가 모든 조상을 빠짐없이 출력하는가?

핵심 답네. 부모 방향으로 BFS를 하면서 이미 본 커밋은 건너뛰어, 모든 조상을 한 번씩만 가까운 순서로 출력합니다.
mini-git> ancestors c003
Ancestors of c003 (2):
- c002: Add login feature (Alice)      <- 부모
- c001: Initial commit (Alice)         <- 부모의 부모
mini-git> ancestors c004
Ancestors of c004 (1):
- c001: Initial commit (Alice)         <- c003/c002는 다른 브랜치라 조상이 아님
mini-git> ancestors c001
No ancestors                           <- 뿌리 커밋은 조상이 없다
  • 확인 포인트: c003의 조상은 c002, c001 두 개 — 그림에서 화살표를 따라가면 정확히 일치
  • 자기 자신은 조상이 아니라서 결과에 넣지 않습니다.

항목 1 · 6/6

SEARCH <keyword> / SEARCH --author=<name> / LOG --sort-by=date|author가 요구사항대로 동작하는가?

핵심 답네. 검색은 전체를 훑지 않고 역색인에서 바로 꺼내고, 정렬은 sorted() 없이 직접 만든 병합 정렬로 날짜순·작성자순을 처리합니다.
mini-git> search login
Found 2 commits:
- c002: Add login feature (Alice)
- c003: Fix login bug (Bob)
mini-git> search LOGIN              <- 대소문자 무시, 같은 결과
mini-git> search "add login"        <- 여러 단어는 모두 포함(AND)
Found 1 commit:
- c002: Add login feature (Alice)
mini-git> search --author=bob
Found 1 commit:
- c003: Fix login bug (Bob)

mini-git> log --sort-by=date        <- 오래된 것부터: c001, c002, c003, c004
mini-git> log --sort-by=author      <- Alice 3개(c001,c002,c004) 다음 Bob(c003)
  • 키워드·작성자 모두 소문자로 맞춰서 저장하므로 --author=ALICE로도 찾아집니다.
  • 동률(같은 작성자)은 LOG 순서를 유지합니다 → 병합 정렬이 안정 정렬이라서 (항목 3의 4번)
  • 없는 키워드: No commits found / 잘못된 정렬 기준: Invalid args
알고 있어야 당황하지 않는 점 — 검색은 단어 단위로 일치합니다. search log는 “login”이 있어도 No commits found입니다(키워드는 공백으로 쪼갠 단어 전체가 키). 요구사항의 최소 기준(공백 분리 + 소문자)을 그대로 따른 것입니다.

근거: index.py search_keyword(), search_author() · sorting.py merge_sort() · repository.py log()

항목 2 · 1/5

커밋 저장소/브랜치/HEAD/사용자 정보를 어떤 구조로 분리했고, 각 책임을 설명할 수 있는가?

핵심 답커밋은 CommitGraph(hash→Commit 해시맵), 브랜치는 {이름: 커밋 hash} dict, HEAD는 현재 브랜치의 이름, 사용자는 문자열 하나로 따로 두고, 이 넷을 Repository가 묶어서 관리합니다. 화면 출력은 cli.py가 맡습니다.
정보어디에자료구조책임
커밋 저장소graph.py CommitGraphdict[hash → Commit]커밋 보관·조회, 그래프 알고리즘
브랜치Repository.branchesdict[이름 → hash | None]“이 이름은 이 커밋을 가리킨다” 이름표
HEADRepository.headstr (브랜치 이름)지금 올라타 있는 브랜치
사용자Repository.authorstr새 커밋의 작성자
역색인index.py InvertedIndexdict 2개키워드/작성자 → 커밋 목록
hash 발급models.py HashGenerator정수 카운터겹치지 않는 hash 발급

포인터 구조 (시연 그래프 기준):

HEAD"main"
→
branches["main"]"c004"
→
Commit c004parents=["c001"]
  • HEAD가 hash가 아니라 브랜치 “이름”인 이유: COMMIT 때 branches[head] = 새 hash 한 줄로 브랜치만 옮기면 HEAD는 자동으로 따라갑니다. HEAD에 hash를 넣으면 매번 둘 다 고쳐야 합니다.
  • BRANCH는 커밋을 복사하지 않습니다. branches[새 이름] = branches[head] — 같은 커밋을 가리키는 이름표가 하나 더 생길 뿐입니다.
  • 의존 방향은 한 줄: cli → repository → (graph/index/sorting/models). Repository에는 print가 없고(값을 돌려주거나 에러를 던짐) 문장으로 바꾸는 일은 cli.py만 하므로 로직과 화면이 분리됩니다.
  • INIT은 _reset()으로 graph·index·branches·head·author를 새로 만듭니다(단, hash 발급기는 유지 → 항목 2의 2번).
솔직한 설명 — 브랜치·HEAD·사용자는 별도 클래스가 아니라 Repository의 필드입니다. 각각 dict 하나·문자열 하나라 클래스까지 만들면 과하다고 판단했고, 길고 독립적인 그래프·인덱스·정렬만 클래스/파일로 분리했습니다.

근거: repository.py 클래스 docstring과 __init__/_reset · README “프로젝트 구조”

항목 2 · 2/5

커밋 hash로 빠르게 조회하기 위해 어떤 키-값 구조를 사용했고, 중복/충돌을 어떻게 방지했는지 설명할 수 있는가?

핵심 답파이썬 dict(해시맵)에 hash → Commit으로 저장해서 평균 O(1)에 찾습니다. 중복은 증가 카운터(c001, c002…)로 아예 안 생기게 하고, add()에서 한 번 더 검사하는 이중 방어입니다.
  • 왜 빠른가: 리스트는 처음부터 하나씩 비교(O(N)), dict는 키를 계산해 칸 번호로 바로 접근(평균 O(1)). self._commits[hash]
  • 1차 방어 — 발급 방식: HashGenerator의 카운터는 늘기만 하고 줄지 않아서 같은 번호가 두 번 나올 수 없습니다. INIT을 다시 해도 발급기는 유지해서 세션 전체에서 유일합니다. (1000번째부터는 c1000처럼 자릿수가 늘어남)
  • 2차 방어 — 저장 시 검사: CommitGraph.add()가 이미 있는 hash면 ValueError, 존재하지 않는 부모를 가리켜도 ValueError.
  • 카운터를 고른 이유: 과제가 “증가 카운터/난수 모두 허용, 중복만 없으면 됨”이라고 했고, 카운터는 충돌 검사·재시도가 필요 없고 사람이 입력하기도 쉽습니다. (대신 약점은 항목 4의 4번)
  • 입력할 때 hash 대소문자는 구분하지 않습니다 (C003도 가능).

근거: models.py HashGenerator.next_hash() · graph.py add() · 테스트 test_hashes_are_unique_even_across_init, test_hash_generator_never_repeats, test_graph_rejects_duplicates_and_unknown_parents

항목 2 · 3/5

커밋이 추가될 때 역색인(author/keyword)을 어떤 시점에, 어떤 방식으로 갱신하도록 설계했는지 설명할 수 있는가?

핵심 답COMMIT 명령 안에서, 커밋을 저장하고 브랜치를 옮긴 직후에 index.add(commit)를 한 번 호출합니다. 전체를 다시 만들지 않고 새 커밋 한 개분만 추가하는 증분 갱신입니다.

Repository.commit()의 순서:

① hash 발급부모=브랜치 끝
→
② graph.add그래프에 저장
→
③ 브랜치 이동이름표 → 새 커밋
→
④ index.add역색인 갱신
  • keyword 인덱스: 메시지를 split() → 단어마다 lower() → 단어 → [hash…] 목록에 추가. 한 메시지에 같은 단어가 두 번이어도 그 커밋은 한 번만 등록(seen 집합).
  • author 인덱스: 작성자 이름을 lower()해서 작성자 → [hash…]에 추가.
  • 한 함수가 두 인덱스를 같이 갱신 → 한쪽만 갱신되는 실수가 없습니다. INIT도 graph와 index를 같이 새로 만들어 서로 어긋나지 않습니다.
  • 비용: COMMIT 때 단어 수만큼 일을 더 하는 대신(쓰기 비용), 검색이 빨라집니다(읽기 이득) — 항목 3의 5번.

시연: index 명령(보조)으로 실제 내용을 보여 줄 수 있습니다.

mini-git> index
[keyword index]
  initial -> c001
  add -> c002, c004
  login -> c002, c003
  ...
[author index]
  alice -> c001, c002, c004
  bob -> c003

항목 2 · 4/5

LOG, PATH, ANCESTORS에서 사용하는 그래프 탐색 로직을 어떻게 재사용 가능하게 구성했는지 설명할 수 있는가?

핵심 답세 알고리즘(위상 정렬·조상 탐색·최단 경로)을 모두 CommitGraph 한 클래스에 모으고, CLI·Repository에 의존하지 않는 순수 계산으로 만들었습니다. 같은 데이터(_commits, _children)와 같은 뼈대(큐 + visited/거리표)를 쓰고, “어떤 선을 따라갈지”는 neighbors() 한 곳에 뽑아 뒀습니다.
  • 독립성: graph.py는 models만 import합니다. 그래서 그래프만 만들어 알고리즘을 바로 호출·테스트할 수 있습니다(단위 테스트가 실제로 그렇게 합니다).
  • 역할 분담: 입력 검사(없는 hash → Unknown commit)는 Repository._resolve, 출력 모양은 cli.py, 알고리즘은 graph.py.
  • 공통 뼈대: ① 리스트를 큐로 쓰되 pop(0)(느림) 대신 front 위치 번호만 앞으로 밀기 ② 이미 본 것은 visited/distance dict로 중복 방지.
  • 한 곳 수정으로 정의 변경: PATH가 “부모+자식(무방향)”인 정의는 neighbors()에만 있습니다 → 정의가 바뀌면 이 함수 중심으로 고치면 됩니다(항목 4의 2번).
  • 검증: 단순 무식한(brute force) 방법과 결과를 비교하는 테스트로 ANCESTORS·PATH가 맞는지 확인했습니다.
솔직한 설명 — ANCESTORS와 PATH의 BFS 반복문이 각각 한 번씩 따로 있습니다(뼈대는 같지만 함수 하나로 합치진 않았습니다). “공통 BFS 함수 하나를 만들고 이웃을 돌려주는 함수만 바꿔 끼우는 방식으로 더 합칠 수 있다”가 개선점이라고 답하면 됩니다.

항목 3 · 1/5

커밋 그래프가 왜 DAG여야 하는지, 사이클이 생기면 어떤 문제가 발생하는지 설명할 수 있는가?

핵심 답커밋은 이미 있는 커밋만 부모로 가리키고 부모는 항상 먼저 만들어지므로, 화살표가 과거로만 뻗어서 되돌아오는 길(순환)이 없는 방향 그래프 = DAG입니다. 순환이 있으면 “내가 내 조상”이 되어 부모-먼저 순서를 정할 수 없고 탐색이 끝나지 않습니다.

DAG (정상)

c001
←
c002
←
c003

자식→부모로만 이동. 어디로 가도 뿌리에서 끝남.

순환 (불가능해야 함)

A
→
B
→
C
→
A

A의 조상을 따라가면 다시 A. 끝이 없음.

순환이 생기면 생기는 문제 3가지

  • LOG 불가능: “A가 B보다 먼저, B도 A보다 먼저”라서 부모-먼저 순서가 존재하지 않습니다. Kahn 알고리즘에서는 대기 부모 수가 0이 안 되는 커밋이 남고, 우리 코드는 len(queue) != len(_order)로 이를 감지해 에러를 냅니다(안전장치).
  • 탐색 무한 반복: ANCESTORS/PATH에서 visited가 없으면 제자리를 계속 돕니다.
  • 의미 모순: 커밋이 자기 자신의 조상이 될 수 없습니다. 히스토리는 시간이 한 방향으로만 흐릅니다.

우리 코드가 순환을 막는 방법

  • CommitGraph.add()가 “부모는 이미 들어 있는 커밋이어야 한다”를 검사 → 새 커밋은 아무도 가리키지 않는 새 점이라 순환을 만들 수 없음.
  • 기존 커밋의 부모를 바꾸는 명령이 없음(커밋은 한번 만들면 불변).
  • (참고) 진짜 Git은 커밋 hash 계산에 부모 hash가 들어가서, 순환은 수학적으로 불가능합니다.
“트리가 아니라 왜 DAG죠?”

병합(merge) 커밋은 부모가 2개라 트리가 아닙니다. 그래서 부모를 리스트(parents)로 저장합니다. 이번 CLI에는 merge 명령이 없어 모양은 트리처럼 나오지만, 데이터 구조와 알고리즘은 부모가 여러 개인 경우도 처리하고 단위 테스트로 검증했습니다.

근거: graph.py 상단 docstring “왜 커밋 그래프는 DAG인가?” · add() · topological_order() 마지막 검사

항목 3 · 2/5

LOG에서 “부모가 먼저” 조건을 만족시키기 위해 어떤 접근(예: 위상 정렬 성격의 출력)을 적용했는지 설명할 수 있는가?

핵심 답위상 정렬(Kahn 알고리즘)을 썼습니다. “아직 출력 안 된 부모가 0개”인 커밋부터 꺼내 출력하고, 그 자식들의 대기 부모 수를 1씩 줄이는 걸 반복합니다. 시간복잡도는 O(V+E)입니다.

Kahn 알고리즘 5단계

  • ① 커밋마다 “기다리는 부모 수”(= len(parents))를 센다
  • ② 기다리는 부모가 0개인 커밋(뿌리)을 큐에 넣는다
  • ③ 큐에서 하나 꺼내 출력하고, 그 커밋의 자식들의 대기 수를 1 줄인다
  • ④ 대기 수가 0이 된 자식은 큐에 넣는다 (부모가 2개인 병합 커밋은 두 부모가 다 나온 뒤에야 0이 됨)
  • ⑤ 큐가 빌 때까지 반복

시연 그래프로 따라가 보기 (정답은 실제 LOG 출력과 같습니다):

단계꺼낸 커밋대기 수가 0이 된 자식큐 상태출력 누적
시작——[c001]—
1c001c002, c004[c002, c004]c001
2c002c003[c004, c003]c001, c002
3c004—[c003]c001, c002, c004
4c003—[ ]c001, c002, c004, c003
  • 왜 “시간순으로 정렬”로는 안 되나: 시간은 부모-먼저를 구조로 보장하지 못합니다(같은 초에 만든 커밋, 시계 오차, 다른 곳에서 가져온 커밋). 위상 정렬은 시간을 안 보고 화살표(부모 정보)만으로 순서를 보장합니다.
  • 실제 확인: 위 표 결과에서 c004(09:03)가 c003(09:02)보다 먼저 나옵니다 — 시간순이 아니라는 증거.
  • 큐는 pop(0)(느림) 대신 위치 번호 front를 앞으로 밀어서 O(1)로 꺼냅니다.

항목 3 · 3/5

PATH에서 최단 경로를 찾기 위해 어떤 알고리즘(예: BFS)을 선택했고, 간선을 무방향으로 정의한 이유를 설명할 수 있는가?

핵심 답BFS입니다. 모든 간선의 비용이 1로 같아서, 가까운 곳부터 한 겹씩 퍼지는 BFS가 처음 도착한 길이 곧 최단입니다. 간선을 무방향으로 보는 이유는, 갈라진 두 브랜치 끝은 서로의 조상이 아니라서 방향대로는 길이 없고 공통 조상까지 내려갔다 올라와야 만나기 때문입니다.
c003feature 끝
→
c002
→
c001공통 조상
→
c004main 끝
  • 왜 BFS: 간선 비용이 모두 같음 → BFS가 최단 보장. (DFS는 최단을 보장하지 않고, 비용이 다를 때 쓰는 다익스트라는 과함.)
  • 왜 무방향: 부모 방향으로만 가면 c003→c004는 No path가 됩니다(둘은 조상-자손이 아님). 과제도 “커밋-부모 연결을 무방향 간선으로 간주”라고 정의했습니다. 구현은 neighbors() = 부모 + 자식.
  • 구현 2단계: ① 도착점에서 BFS로 모든 커밋의 거리표 distance 계산 ② 출발점에서 “거리가 1 작은 이웃” 중 hash가 가장 작은 쪽으로 한 걸음씩 이동 → 최단 경로가 여러 개일 때 h1->h2->… 사전순 최소 경로가 됩니다.
  • 욕심쟁이(greedy) 선택이 맞는 이유: 최단 경로는 모두 같은 개수의 커밋을 지나므로, 앞 칸부터 작은 hash를 고르면 전체 문자열도 가장 작습니다.
  • 이어지지 않으면 거리표에 출발점이 없어서 None → CLI가 No path 출력. 시간복잡도 O(V+E).
참고 — 이 CLI로 만든 그래프는 트리 모양이라 최단 경로가 하나뿐입니다. “사전순 최소” 규칙은 병합 커밋이 있는 단위 테스트(brute force와 비교)로 확인했습니다.

항목 3 · 4/5

정렬 알고리즘의 평균/최악 시간복잡도와 안정 정렬 여부를 설명할 수 있는가?

핵심 답직접 구현한 병합 정렬이고, 평균·최악 모두 O(n log n), 추가 메모리 O(n), 안정 정렬입니다.
항목병합 정렬 (우리 구현)비교: 퀵 정렬
평균O(n log n)O(n log n)
최악O(n log n) — 입력 순서와 무관O(n²)
추가 메모리O(n) (합칠 때 새 리스트)O(log n) 정도

  • 왜 n log n: 반으로 쪼개면 log n 층, 각 층에서 모든 원소를 한 번씩 합치므로 층당 n → n × log n.

  • 비교 기준 교체: key 함수만 바꿔 한 코드로 처리 — key=lambda c: c.timestamp(날짜) / c.author.lower()(작성자).
  • 금지 규칙: sorted(), list.sort()를 쓰지 않았고, 자동 테스트가 소스를 읽어 검사합니다(test_no_builtin_sorting_api).

항목 3 · 5/5

역색인이 순회 검색보다 빠른 이유를 자료구조/시간복잡도 관점에서 설명할 수 있는가?

핵심 답역색인은 “단어 → 커밋 목록”을 미리 dict에 만들어 두기 때문에 검색이 해시 조회 평균 O(1) + 결과 개수(K)입니다. 순회 검색은 모든 커밋 메시지를 열어 봐야 해서 O(N)(메시지 길이까지 치면 O(N·L))입니다. 대신 COMMIT 때 인덱스를 갱신하는 비용을 미리 냅니다.

순회 검색

c001 메시지 확인 → c002 확인 → … → cN 확인. 결과가 1개여도 전부 봄. O(N)

역색인 검색

index["login"] → [c002, c003]. 책 뒤의 “찾아보기”처럼 바로 펼침. 평균 O(1) + K

  • 자료구조 관점: dict는 해시 테이블 → 키로 칸을 바로 계산해 접근. 리스트처럼 처음부터 비교하지 않습니다.
  • 교환(trade-off): 읽기(검색)를 빠르게 하려고 쓰기(COMMIT)와 메모리를 더 씁니다. 커밋은 한 번 쓰고 검색은 여러 번 하므로 이득.
  • 여러 단어("add login")는 단어별 후보를 교집합(AND)합니다.
  • 자동 테스트: 500개 커밋 중 결과 1개를 찾을 때 그래프에서 커밋을 1번만 꺼내는지 확인(test_search_uses_index_not_scan) — 전체를 훑지 않는다는 증명.

항목 4 · 1/4

커밋 수가 10배 늘어났을 때 병목이 될 지점을 예측하고, 개선 방향(자료구조/알고리즘)을 설명할 수 있는가?

핵심 답병목은 호출할 때마다 커밋 전체를 훑는 연산입니다 — 특히 LOG --sort-by(정렬)와 PATH(BFS가 끝까지 돎). 검색과 COMMIT은 10배가 되어도 거의 그대로입니다. 개선은 ① PATH 조기 종료/양방향 BFS ② 위상 순서 캐시·페이징 ③ 정렬 생략입니다.

실제 측정 (직선 히스토리, 이 PC에서 한 번 잰 대략값):

연산10,000개100,000개배율복잡도
COMMIT (평균 1개당)7.8 µs8.5 µs≈ 1배단어 수에 비례 (N 무관)
SEARCH 희귀 단어0.019 ms0.033 ms≈ 1.7배평균 O(1) + K
LOG (위상 정렬)10.7 ms184 ms≈ 17배O(V+E)
LOG --sort-by=date51 ms782 ms≈ 15배O(V log V) + 위상 정렬

PATH 바로 인접한 2개16 ms175 ms≈ 11배가까워도 전체 BFS

※ 파이썬 실행 환경에 따라 값은 달라집니다. 핵심은 “선형 연산은 ~10배, 정렬은 그보다 조금 더, 검색은 거의 불변”이라는 비례 관계입니다. 여전히 100,000개에서 1초 안쪽이라 “느려지지만 동작은 한다”가 정확한 표현입니다.

개선 방향 (우선순위 순)

  • PATH — 조기 종료 / 양방향 BFS: 지금은 도착점에서 그래프 전체의 거리표를 만들어서 인접한 두 커밋도 전부 돕니다. 출발점을 만나면 BFS를 멈추게 하거나, 양쪽에서 동시에 퍼지는 양방향 BFS로 탐색 범위를 줄입니다.
  • LOG — 위상 순서를 캐시/증분 유지 + 페이징: 커밋은 부모가 먼저 있어야 추가되므로 추가되는 순서 자체가 이미 위상 순서입니다. 새 커밋을 뒤에 붙이기만 하면 매번 다시 계산할 필요가 없습니다. 출력도 “최근 20개만(-n)”처럼 끊어서 보여 줍니다.
  • 정렬 — 불필요하면 생략: 날짜순은 이미 시간 순서로 쌓이므로 “이미 정렬됨”을 감지하면 건너뛸 수 있습니다(실제 파이썬 정렬이 쓰는 아이디어). 작성자순은 작성자별로 묶어 두는 방법도 있습니다.
  • SEARCH — 흔한 단어는 결과가 큼(100,000개 중 25,000개 → 11.6 ms): 페이징/상위 N개. 인덱스 메모리는 전체 단어 수에 비례하므로 더 커지면 디스크(DB)로.
“그럼 처음부터 캐시하면 되는 거 아닌가요? 왜 Kahn을 구현했죠?”

Kahn은 “생성 순서가 위상 순서”라는 가정에 의존하지 않고 화살표만으로 순서를 만듭니다. 그래서 어떤 DAG에서도 맞고, 순환이 있으면 감지까지 합니다. 과제도 위상 정렬 성격의 출력을 요구했습니다. 규모가 커지면 그 가정을 이용한 최적화를 더하는 것이 개선 방향이라고 답하면 됩니다.

“재귀 한계(recursion limit)는 괜찮나요?”

그래프 탐색은 전부 반복문(큐)이라 아주 긴 직선 히스토리에서도 재귀 깊이 문제가 없습니다. 병합 정렬의 재귀 깊이는 log n 정도뿐입니다. 5,000개 직선 히스토리 테스트와 100,000개 측정에서 확인했습니다.

항목 4 · 2/4

PATH의 간선 정의를 “부모 방향만 허용”으로 바꾸면 결과가 어떻게 달라지고, 구현은 무엇을 바꿔야 하는지 설명할 수 있는가?

핵심 답“출발 커밋에서 부모 쪽으로만 걸어서 도착할 수 있는가”가 되어, 갈라진 브랜치 사이는 전부 No path가 되고 PATH a b 와 PATH b a 의 결과가 달라집니다(대칭이 깨짐). 구현은 neighbors()를 부모만 돌려주게 바꾸고, 도착점에서의 BFS는 거꾸로(자식 방향) 돌려야 합니다.
입력 (시연 그래프)지금 (무방향)변경 후 (부모 방향만)
path c003 c004c003 → c002 → c001 → c004No path
path c004 c003c004 → c001 → c002 → c003No path
path c003 c001c003 → c002 → c001c003 → c002 → c001 (같음, 부모 방향)
path c001 c003c001 → c002 → c003No path (자식 방향은 막힘)
  • 결과 변화 ① 갈라진 브랜치(c003↔c004)는 서로 조상이 아니라 길이 끊김 → No path.
  • ② 비대칭: path c003 c001은 되는데 path c001 c003은 안 됨 (지금은 항상 대칭).
  • ③ 기능의 성격이 바뀜: 사실상 “도착 커밋이 내 조상인가?” 확인이 되어 ANCESTORS와 비슷해집니다.

구현에서 바꿀 곳

  • neighbors() (걸어갈 때): parents + children → parents만.
  • _distances_from(end) (거리표): 걸어가는 방향이 “출발 → 부모 → …→ 도착”이므로 도착점에서 자식 방향(화살표 거꾸로)으로 BFS를 해야 “도착까지의 거리”가 맞게 나옵니다. 이걸 빼먹으면 틀린 값이 나오는 것이 함정.
  • “거리가 1 작은 이웃 중 hash가 작은 쪽” 규칙과 No path 처리, CLI·Repository는 그대로.
  • 기존 테스트 중 “브랜치 사이 경로(공통 조상 경유)”와 “경로 길이 대칭” 테스트는 기대값을 바꿔야 합니다.

항목 4 · 3/4

LOG --sort-by=author 요구사항이 “부모-자식 선후도 유지”로 강화된다면, 어떤 전략으로 해결할지 설명할 수 있는가?

핵심 답그냥 정렬로는 안 되고, Kahn(위상 정렬)에서 “지금 꺼낼 수 있는 커밋 중 작성자가 가장 작은 것”을 매번 고르게 바꿉니다. 큐(선입선출) 대신 우선순위 선택을 쓰는 것이 핵심입니다.

왜 정렬만으로는 깨지나 (직접 확인한 예)

시연 그래프에서 feature 브랜치에 Alice가 한 커밋을 더 만든다고 합시다(c005, 부모는 Bob의 c003).

지금의 작성자 정렬

c005Alice
c003Bob

c005가 부모 c003보다 먼저 나옴 → 위반

c002Alice
c004Alice
c003Bob
c005Alice

모든 부모가 자식보다 먼저 → 만족

전략 (아이디어 3줄)

  • ① Kahn처럼 “대기 부모 수”를 센다 → 대기 0개인 커밋만 ready 목록에 둔다.
  • ② 매번 ready 중 작성자가 가장 작은 것(동률이면 먼저 ready가 된 것)을 하나 꺼내 출력한다. (대기 수가 0이 된 자식을 ready에 추가)
  • ③ 결과는 “작성자순에 최대한 가깝되 부모-자식 순서는 지킨 순서”입니다. 두 조건이 충돌하면 부모 먼저가 우선(위 예의 c005).
# 설명용 스케치 (제출 코드에는 없음)
ready = [뿌리 커밋들]
while ready:
    best = ready 중 author.lower()가 가장 작은 것 (동률이면 먼저 들어온 것)
    ready.remove(best);  출력.append(best)
    for child in 자식들[best]:
        기다리는_부모[child] -= 1
        if 기다리는_부모[child] == 0:  ready.append(child)
  • 복잡도: 최소를 고르는 방법에 따라 달라집니다. 선형 탐색이면 최악 O(V²), 힙(우선순위 큐)이면 O((V+E) log V).
  • 우리 프로젝트의 제약: sorted()/.sort()는 물론 heapq도 소스 검사 테스트가 금지하고 있어서, 실제로 적용한다면 직접 만든 힙이나 병합 정렬로 ready를 유지해야 합니다.
  • 이 스케치는 따로 실행해 위 예의 결과(c001, c002, c004, c003, c005)가 나오는 것과 모든 부모가 자식보다 앞에 오는 것을 확인했습니다.

항목 4 · 4/4

해시 생성 방식을 카운터 기반 ↔ 난수 기반으로 바꿀 때 테스트/재현/디버깅에 미치는 영향을 설명할 수 있는가?

핵심 답카운터는 결과가 항상 같아서(결정적) 테스트·재현·디버깅이 쉽고, 난수는 매번 달라서 모두 어려워집니다. 난수로 바꾸면 테스트에서 정확한 hash 값을 비교할 수 없어 시드 고정이나 가짜 발급기 주입이 필요하고, 충돌 검사도 직접 해야 합니다.
관점카운터 (현재)난수
테스트정확한 값(c001)을 그대로 비교 가능값이 매번 다름 → 형식·길이만 검사, 또는 시드 고정/가짜 발급기 주입
재현같은 명령 순서 → 같은 hash·같은 로그같은 명령도 매번 다른 hash → 시드를 기록해 둬야 재현
디버깅짧고 읽기 쉬움, 번호로 생성 순서가 보임길고 무작위 → 복사해야 하고 순서 단서가 없음
유일성줄지 않는 카운터라 100% 보장충돌 확률이 아주 작지만 0은 아님 → 중복 검사 + 재발급 필요
약점여러 곳에서 따로 만들면 겹침(분산 환경 부적합)여러 곳에서 만들어도 겹칠 확률이 매우 낮음
  • 우리 코드에서 가장 먼저 깨지는 곳: 테스트. "[main c001] Initial commit"처럼 hash 값을 글자 그대로 비교하는 테스트가 많기 때문입니다.

  • 테스트를 쉽게 만드는 방법: 시계(clock)를 Repository에 주입하는 것처럼 발급기도 주입하면 됩니다. 지금은 Repository.__init__에서 직접 만들고 있어서 인자 하나를 추가해야 합니다 — 시드를 고정한 random.Random(seed) 발급기를 테스트에서 넘기면 재현이 가능해집니다.

  • (참고) 진짜 Git은 둘 다 아니고 커밋 내용을 SHA-1로 계산해서 같은 내용이면 같은 hash, 다르면 사실상 다른 hash입니다 — 결정적이면서 분산 환경에도 안전.

시연할 때 함정 3가지

“병합(merge) 커밋은 만들 수 있나요?”

CLI에는 merge 명령이 없고(보너스 과제 범위 밖, README에 “포함 안 함” 명시), 커밋마다 부모는 1개라 그래프가 트리 모양으로 나옵니다. 다만 Commit.parents가 리스트이고 그래프 알고리즘은 부모가 여러 개인 경우를 처리하며, 단위 테스트에서 병합 커밋이 있는 그래프로 검증했습니다.
