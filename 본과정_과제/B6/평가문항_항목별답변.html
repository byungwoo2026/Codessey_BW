2-1. 테이블을 왜 이렇게 나눴고, 각 테이블의 역할은?

질문: 테이블을 왜 이렇게 나눴는지, 각 테이블의 역할을 말할 수 있는가?

원칙은 “같은 정보는 한 곳에만 저장” 입니다. 정보의 성격에 따라 분류(category) · 사람(member) · 물건(book) · 사건(rental) 으로 나누고, 번호(FK)로 연결했습니다.
테이블성격역할들어 있는 것행
category분류도서 분류 이름 목록소설 · 시 · IT · 역사 … 10개10
member사람도서관 회원 정보이름 · 이메일 · 전화 · 가입일12
book물건도서 정보 (어느 분류인지 포함)제목 · 저자 · ISBN · 가격 · 출간년도 · category_id24
rental사건“누가 어떤 책을 언제 빌렸나” 기록. 회원과 도서를 잇는 다리대여일 · 반납예정일 · 반납일 · 상태 · 연체료 · member_id · book_id38

나눈 이유 3가지

  • 중복 제거 · 수정은 한 곳에서 — 한 시트에 몰아 적으면 회원이 책을 빌릴 때마다 이름 · 이메일 · 전화가 반복됩니다. 김민준 회원은 대여가 4건이라 4번 반복됩니다. 나누면 member 에 1행만 있고, 이메일이 바뀌어도 1곳만 고치면 됩니다. 분류 이름(‘IT’)도 책 5권에 반복하지 않고 category 에 1번만 적습니다.
  • 회원 ↔ 도서는 N:M → rental 로 1:N 두 개로 풀기 — 한 회원이 여러 책을 빌리고, 한 책을 여러 회원이 빌립니다. 이 관계는 칸 하나에 담을 수 없어서 “대여 1건 = 회원 1명 + 책 1권” 인 rental 을 사이에 두고 1:N 두 개로 만들었습니다.
  • 정보의 주인이 다르다 — 반납일 · 연체료 · 상태는 회원의 속성도, 도서의 속성도 아니고 “대여 1건”의 속성입니다. 그래서 rental 에 둡니다.

30초 대본

같은 정보를 여러 번 적지 않으려고 4개로 나눴습니다. category 는 분류 이름, member 는 회원 정보, book 은 도서 정보이고, rental 은 누가 어떤 책을 언제 빌렸는지 기록하는 테이블입니다. 회원과 도서는 서로 여러 개씩 연결되는 관계라서 그 사이에 rental 을 두어 1 대 N 두 개로 풀었습니다. 한 시트에 다 적으면 김민준 회원의 이름과 이메일이 대여 4건마다 반복되는데, 나누면 member 에 한 번만 있습니다.

2-2. FK 로 연결한 1:N 이 실제 도메인에서 어떤 의미인지

질문: FK로 연결한 1:N 관계가 실제 도메인에서 어떤 의미인지 예시를 들어 보여줄 수 있는가?

1쪽 한 행에 N쪽 여러 행이 번호로 매달리는 관계입니다. FK 는 항상 N쪽 테이블에 있습니다.
관계도서관에서의 뜻FK 위치실제 값 (출처)
category 1 : book N한 분류에 여러 권의 책이 속한다book.category_idIT 분류 1개 ↔ 책 5권 (Q9)
member 1 : rental N한 회원이 여러 번 빌린다rental.member_id김민준 1명 ↔ 대여 4건 (Q8)
book 1 : rental N한 책이 여러 번 빌려진다rental.book_id혼자 공부하는 파이썬 1권 ↔ 대여 5건 (Q10)

번호를 따라가 보기 — rental 31번은 누가 무엇을 빌렸나

rental 31번member_id = 1
book_id = 11
→
member 1번김민준
+
book 11번점프 투 파이썬
category_id = 5
→
category 5번IT

결론: 31번 기록 = 김민준 회원이 IT 분류의 점프 투 파이썬을 2026-09-30 에 빌림. (results/Q06.txt 의 31번 행, Q05.txt 의 11번 도서와 같음) 이 번호 따라가기를 SQL 한 문장으로 하는 것이 JOIN 입니다.

FK 가 지켜 주는 두 가지

  • 없는 번호는 참조 불가 — 존재하지 않는 회원 999번의 대여 기록 INSERT → 거부
  • 참조당하는 행은 삭제 불가 (ON DELETE RESTRICT) — 대여 기록이 남은 회원 · 도서 DELETE → 거부. 지우면 기록이 “주인 없는 번호”가 되기 때문입니다.
N 은 0 이어도 됩니다 — 대여 기록이 0건인 회원은 2명(오세훈 · 신나래, Q8 · Q12), 한 번도 안 빌려진 책은 24권 중 5권(Q7)입니다. 1쪽은 N쪽 없이도 존재할 수 있어서 이런 행을 찾을 때 LEFT JOIN 이나 서브쿼리를 씁니다.

30초 대본

예를 들어 회원 1 대 대여 N 은 ‘한 회원이 여러 번 빌린다’는 뜻입니다. 김민준 회원 1명에게 대여 기록이 4건 붙어 있습니다. 이때 FK 는 N 쪽인 rental 테이블의 member_id 에 있습니다. 31번 대여 기록을 보면 member_id 1, book_id 11 이라서, 1번 회원 김민준이 11번 도서 점프 투 파이썬을 빌렸다는 걸 번호로 따라갈 수 있습니다. FK 덕분에 없는 회원 번호는 넣을 수 없고, 대여 기록이 있는 회원은 삭제할 수 없습니다.

2-3. 컬럼 타입을 왜 그렇게 골랐는지

질문: 컬럼 타입(TEXT, INTEGER, DATE 등)을 왜 그렇게 선택했는지 설명할 수 있는가?

기준은 하나입니다. “그 값으로 계산이나 비교를 하는가?” 숫자로 계산하면 INTEGER, 이름·코드처럼 글자면 VARCHAR(TEXT), 날짜는 DATE 로 골랐습니다.
타입컬럼고른 이유
INTEGER*_id (PK · FK)번호로 대소 비교 · JOIN 하고 AUTOINCREMENT 로 자동 증가
INTEGERprice · late_fee원 단위라 소수점이 필요 없고, 합계(SUM) · 평균(AVG) · 하루 300원 곱셈 같은 계산을 함 (Q9, Q11, Q13)
INTEGERpublished_year연도 숫자 하나. 정렬 · 범위 비교용
VARCHAR (TEXT 계열)name · title · author · email글자 값. 길이 제한(50, 200 등)으로 의도를 표시
VARCHARphone · isbn숫자처럼 보여도 더하거나 빼지 않는 식별 코드. 010-1000-0001 처럼 하이픈이 있고 맨 앞 0 이 사라지면 안 됨
VARCHARstatus'RENTED' / 'RETURNED' / 'OVERDUE' 글자 값. SQLite 에는 ENUM 이 없어 CHECK (status IN (…)) 로 허용 값을 제한
DATEjoined_at · rented_at · due_date · returned_at날짜 의미를 이름과 타입으로 드러냄. returned_at 은 NULL 허용 = “아직 안 돌려줌”
SQLite 에서 실제로 저장된 타입 (직접 typeof() 로 확인) — joined_at · rented_at → text ('YYYY-MM-DD'), returned_at → text 또는 null(12건), price · late_fee → integer. SQLite 에는 진짜 DATE 타입이 없어 날짜가 문자열로 저장됩니다. 그래도 'YYYY-MM-DD' 형식이라 문자열 비교만으로 날짜 순서가 맞아서 due_date < '2026-10-08' (Q13) 같은 비교가 정상 동작합니다. 다른 DB 에서는 진짜 DATE 타입을 씁니다.
솔직한 단서 — SQLite 는 VARCHAR(50) 의 50 을 강제하지 않습니다(길이를 넘는 값도 들어감). 다른 DB(MySQL · PostgreSQL)로 옮길 때를 고려해 의도를 적어 둔 것입니다.

30초 대본

값으로 계산을 하는지를 기준으로 골랐습니다. 번호와 가격, 연체료처럼 더하고 비교하는 값은 INTEGER 입니다. 원 단위라 소수점이 필요 없습니다. 이름과 이메일, 제목은 글자라서 VARCHAR 이고, 전화번호와 ISBN 은 숫자처럼 보여도 계산하지 않는 코드라서 글자로 저장했습니다. 하이픈과 맨 앞 0 을 지키기 위해서이기도 합니다. 날짜는 DATE 로 선언했는데, SQLite 에는 진짜 날짜 타입이 없어서 실제로는 ‘연-월-일’ 글자로 저장됩니다. 그래도 이 형식은 글자 비교만으로 날짜 순서가 맞습니다.

2-4. 인덱스를 어떤 컬럼에 걸었고, 왜 그 컬럼인지

질문: 인덱스를 어떤 컬럼에 걸었고, 왜 그 컬럼이어야 하는지 이유를 대답할 수 있는가?

rental.member_id 에 걸었습니다. 계속 쌓이는 테이블이고 “특정 회원의 대여 기록”을 자주 찾는데, FK 컬럼은 자동으로 색인이 만들어지지 않기 때문입니다.
-- (1) 인덱스 만들기 전 : 3번 회원의 대여 기록 찾기
EXPLAIN QUERY PLAN SELECT * FROM rental WHERE member_id = 3;
--> SCAN rental                                                   ← 전체 행을 처음부터 읽음

-- (2) 인덱스 생성
CREATE INDEX idx_rental_member_id ON rental (member_id);

-- (3) 같은 쿼리
--> SEARCH rental USING INDEX idx_rental_member_id (member_id=?)  ← 색인으로 바로 찾음
컬럼판정이유
rental.member_id만듦 (Q15)“회원별 대여 기록” 조회·JOIN 에 쓰임. 인덱스 생성 후 실행 계획에서 Q8 · Q11 의 rental 접근도 SEARCH … idx_rental_member_id (색인 사용)로 나타나는 것을 확인 (Q6 은 rental 을 먼저 훑는 순서라 색인을 안 씀)
rental.book_id후보Q7 · Q10 에서 같은 방식으로 쓰이지만, 과제 요구가 1개 이상이라 member_id 하나만 만듦
*_id (PK) · member.email · book.isbn이미 있음PK 와 UNIQUE 는 DB 가 자동으로 색인을 만듦
rental.status비추천값이 3종류뿐이라 색인으로 걸러지는 양이 적음 (38건 중 26건이 RETURNED)
book.title (LIKE '%파이썬%')효과 없음앞에 % 가 붙은 검색은 색인을 못 탐 (Q2)
솔직한 단서 — 지금은 38행뿐이라 속도 차이는 체감되지 않습니다. 이 과제에서 확인한 것은 “실행 방식이 SCAN → SEARCH 로 바뀐다”는 것이고, 대여 기록이 수십만 건 쌓이는 서비스에서 의미가 커집니다. 인덱스는 INSERT · UPDATE 때 같이 갱신되므로 무작정 많이 만들지 않습니다.

30초 대본

rental 테이블의 member_id 에 인덱스를 걸었습니다. 대여 기록은 계속 쌓이는 테이블이고, 특정 회원의 기록을 찾거나 회원 테이블과 JOIN 할 때 member_id 를 자주 쓰기 때문입니다. 인덱스를 만들기 전에는 실행 계획이 SCAN rental, 즉 전체 읽기였는데, 만든 뒤에는 SEARCH USING INDEX 로 바뀌었습니다. PK 나 UNIQUE 컬럼은 자동으로 색인이 있어서 따로 만들지 않았고, status 처럼 값 종류가 3개뿐인 컬럼은 효과가 작아서 만들지 않았습니다. 지금은 38행이라 속도 차이는 못 느끼지만, 데이터가 늘수록 효과가 커집니다.

예상 꼬리질문

category 와 book 을 합쳐서 book 하나로 두면 안 되나요?

합치면 책마다 ‘IT’ 같은 분류 이름이 반복되고, 분류 이름을 바꾸면 해당 책을 모두 고쳐야 합니다. 또 “책이 아직 없는 분류”를 저장할 곳이 없어집니다. 분류는 따로 두고 번호만 참조하는 쪽이 한 곳만 고치면 됩니다.

rental 에 회원 이름이나 책 제목을 같이 적으면 JOIN 이 필요 없지 않나요?

빠르긴 하지만 이름이 바뀌면 기록 전부를 고쳐야 하고, 고치다 빠뜨리면 같은 사람이 서로 다른 이름으로 남습니다. 번호만 적어 두고 필요할 때 JOIN 으로 붙이는 것이 정확합니다.

전화번호를 INTEGER 로 하면 안 되나요?

숫자로 저장하면 맨 앞 0 이 사라지고(010 → 10) 하이픈도 못 넣습니다. 전화번호는 더하거나 빼지 않으므로 글자로 둡니다.

엑셀은 한 시트에 다 적기 때문에 김민준 회원이 4번 빌리면 이름과 이메일이 4번 반복되고, 이메일이 바뀌면 4곳을 다 고쳐야 합니다. DB 는 member, book, rental 로 나누고 번호로 연결해서 회원 정보를 한 곳에만 저장합니다. 그리고 NOT NULL, UNIQUE, FK 같은 규칙이 잘못된 입력을 막아 줍니다. 실제로 없는 회원 999번으로 대여 기록을 넣으려고 하니 FOREIGN KEY constraint failed 로 거부됐습니다. 그래서 엑셀과 DB 의 차이는 양이 아니라 관계와 규칙이라고 생각합니다.

엑셀도 VLOOKUP 으로 시트끼리 연결되지 않나요?

연결은 되지만 연결을 사람이 수식으로 유지해야 하고, 없는 값을 입력하는 것은 막지 못합니다. DB 는 FK 가 연결 자체를 규칙으로 강제합니다. 소량 · 개인용 집계에는 엑셀이 더 편합니다.

3-2. PK 와 FK 의 역할 구분, 1:N 이 데이터를 어떻게 연결하는가

질문: PK와 FK의 역할을 구분하고, 1:N 관계가 데이터를 어떻게 연결하는지 본인 스키마 기준으로 보여줄 수 있는가?

PK = 그 행의 자기 번호 (겹치지도 비지도 않음). FK = 다른 테이블 행의 번호를 빌려 적은 칸 (겹쳐도 되지만 부모에 있는 번호여야 함).
PK (기본키)FK (외래키)
역할행 하나를 구분하는 고유 번호다른 테이블의 행을 가리키는 연결 번호
중복불가가능 — rental.member_id 에 1 이 4번 나옴
NULL불가가능하지만 우리 스키마는 NOT NULL 로 막음 (대여는 반드시 회원 · 책이 있어야 하므로)
우리 스키마member.member_idrental.member_id → member.member_id
비유학번출석부에 이름 대신 적어 둔 학번
CREATE TABLE rental (
    rental_id INTEGER PRIMARY KEY AUTOINCREMENT,  -- PK : 대여 기록 1건마다 붙는 고유 번호
    member_id INTEGER NOT NULL,                   -- FK : 누가 빌렸나 (member 의 번호)
    book_id   INTEGER NOT NULL,                   -- FK : 어떤 책인가 (book 의 번호)
    ...
    FOREIGN KEY (member_id) REFERENCES member (member_id) ON DELETE RESTRICT,
    FOREIGN KEY (book_id)   REFERENCES book   (book_id)   ON DELETE RESTRICT
);

1:N 으로 연결되는 모습 — 김민준(member 1번) 한 행에 대여 N건

1 쪽 member 에는 김민준이 1행, N 쪽 rental 에는 member_id = 1 인 행이 4행 있습니다 (Q8: 김민준 4건). rental 의 member_id 칸을 보면 번호 1 이 여러 줄에 반복되고, 그 번호가 가리키는 곳이 member 의 1번 행입니다. 그래서 FK 는 항상 N 쪽에 있습니다. 1쪽의 칸 하나에 “빌린 책 1, 10, 12, 11” 처럼 번호를 여럿 적을 수 없기 때문입니다.

rental 31번member_id = 1
→ FK = PK →
member 1번김민준

30초 대본

PK 는 한 행을 구분하는 자기 번호라서 중복되거나 비어 있을 수 없습니다. 학번 같은 것입니다. FK 는 다른 테이블의 PK 번호를 가져와 적어 둔 칸으로, ‘이 대여 기록은 몇 번 회원의 것이다’ 처럼 가리키는 역할을 합니다. 제 스키마에서는 member 의 member_id 가 PK 이고, rental 의 member_id 가 그걸 가리키는 FK 입니다. 김민준 회원은 member 에 1행이고 rental 에는 member_id 가 1 인 행이 4건 있는데, 이게 1 대 N 입니다.

PK 로 이름이나 이메일을 쓰면 안 되나요?

이름은 동명이인이 있고 개명으로 바뀔 수 있습니다. 이메일은 UNIQUE 지만 바뀔 수 있습니다. 번호 PK 는 바뀌지 않아서 다른 테이블이 안전하게 가리킬 수 있습니다. 이메일에는 UNIQUE 를 따로 걸었습니다.

3-3. INNER JOIN 과 LEFT JOIN 의 차이를 실행 결과로

30초 대본

INNER JOIN 은 양쪽에 짝이 있는 행만 남기고, LEFT JOIN 은 왼쪽 테이블은 전부 남깁니다. 짝이 없으면 오른쪽 칸이 NULL 이 됩니다. 제 Q8 은 회원별 대여 횟수인데 member 를 왼쪽에 두고 LEFT JOIN 했더니 대여가 0건인 오세훈 회원과 신나래 회원까지 12명이 모두 나옵니다. 같은 쿼리를 INNER JOIN 으로 바꾸면 이 두 명이 결과에서 사라져 10명만 나옵니다. 그래서 ‘없는 것’을 찾을 때, 예를 들어 한 번도 안 빌려진 책 5권을 찾는 Q7 은 LEFT JOIN 과 IS NULL 을 씁니다.

LEFT JOIN 에서 COUNT(*) 가 아니라 COUNT(r.rental_id) 를 쓴 이유는요?

0건 회원도 결과에 1줄은 생깁니다(오른쪽이 NULL). COUNT(*) 는 그 줄을 1건으로 세어 “0건 회원이 1건”이 되고, COUNT(r.rental_id) 는 NULL 을 빼고 세어 정확히 0 이 나옵니다.

3-4. GROUP BY 와 집계 함수가 어떻게 동작하는가

질문: GROUP BY와 집계 함수(COUNT, SUM, AVG)가 어떻게 동작하는지 쿼리 결과를 보며 이야기할 수 있는가?

Q9 — 분류별 도서 수와 평균 가격 (COUNT · AVG)

SELECT c.name AS category,
       COUNT(b.book_id)                     AS book_count,   -- 묶음 안의 행 수
       CAST(ROUND(AVG(b.price)) AS INTEGER) AS avg_price     -- 묶음 안 price 의 평균
FROM category AS c
INNER JOIN book AS b ON b.category_id = c.category_id
GROUP BY c.category_id, c.name                               -- 분류별로 묶기
ORDER BY book_count DESC, avg_price DESC;

규칙 한 줄 — SELECT 에 집계 함수가 아닌 컬럼을 쓰면 반드시 GROUP BY 에도 있어야 합니다. (Q9 : c.name 은 GROUP BY 에 있음)

30초 대본

GROUP BY 는 같은 값끼리 행을 한 묶음으로 만들고, COUNT 나 SUM, AVG 는 그 묶음마다 값 하나를 계산합니다. 제 Q9 는 책 24권을 분류별로 묶어서 COUNT 로 권수를, AVG 로 평균 가격을 구했습니다. IT 분류를 펼치면 책이 5권이고 가격 합이 132,800원이라 평균이 26,560원입니다. Q11 에서는 회원별로 묶어서 SUM 으로 연체료 합계를 구했습니다. 결과는 24행이 분류 10줄로 줄어드는 것이 핵심입니다.

WHERE 와 HAVING 의 차이는요?

WHERE 는 묶기 전에 개별 행을 거르고, HAVING 은 묶은 후에 합계 · 개수 같은 그룹 값을 거릅니다. 합계처럼 묶은 뒤에야 알 수 있는 값은 WHERE 에 쓸 수 없습니다. (Q11)

가장 복잡했던 쿼리와 가장 어려웠던 부분

4-1. 가장 복잡했던 쿼리를 골라 단계별로 설명

질문: 작성한 쿼리 중 가장 복잡했던 쿼리를 선택하고, 어떻게 풀었는지 단계별로 설명할 수 있는가?

선택: Q11 — 연체료 합계가 1,500원 이상인 회원. JOIN · WHERE · GROUP BY · HAVING · ORDER BY 가 한 문장에 모두 들어간 쿼리입니다.
SELECT m.member_id, m.name,
       COUNT(*)        AS late_count,
       SUM(r.late_fee) AS total_late_fee
FROM rental AS r
INNER JOIN member AS m ON m.member_id = r.member_id   -- ① 회원 이름 붙이기
WHERE r.late_fee > 0                                   -- ② 묶기 "전" : 연체료 있는 행만
GROUP BY m.member_id, m.name                           -- ③ 회원별로 묶기
HAVING SUM(r.late_fee) >= 1500                        -- ⑤ 묶은 "후" : 합계 1,500원 이상만
ORDER BY total_late_fee DESC;                          -- ⑥ 많은 순

요구사항 → 쿼리로 쪼개기

“연체료를 낸 적 있는”→ WHERE late_fee > 0
→
“회원별”→ GROUP BY 회원
→
“합계가 1,500원 이상”→ HAVING SUM ≥ 1500
→
“많은 순”→ ORDER BY DESC

실행되는 순서대로 따라가기 (실제 데이터)

단계하는 일남는 것
① FROM + JOINrental 에 member 이름을 번호(member_id)로 붙임38행
② WHERElate_fee > 0 인 행만 남김 (행 거르기)5행  (rental 6 · 10 · 11 · 17 · 27번)
③ GROUP BY같은 회원끼리 묶음4묶음  (강도윤 2건 · 박지호 · 김민준 · 최수빈 각 1건)
④ 집계묶음마다 COUNT · SUM 계산강도윤 4,800 / 박지호 2,100 / 김민준 1,500 / 최수빈 1,200
⑤ HAVINGSUM ≥ 1500 인 묶음만 남김 (그룹 거르기)3묶음  (최수빈 1,200 탈락)
⑥ ORDER BY합계 큰 순서로 정렬강도윤 4,800 → 박지호 2,100 → 김민준 1,500

최종 결과는 results/Q11.txt 와 같습니다. ②·③·⑤ 의 중간 값은 같은 데이터에서 단계별로 직접 실행해 확인했습니다.

어디가 어려웠나 (쿼리를 풀면서 짚은 지점)

  • 쓰는 순서 ≠ 실행 순서 — SQL 은 SELECT 부터 쓰지만 실제로는 FROM → JOIN → WHERE → GROUP BY → HAVING → SELECT → ORDER BY 순으로 처리됩니다.
  • WHERE 와 HAVING 의 구분 — “연체료가 있는 기록”은 행 하나만 보면 알 수 있어서 WHERE, “합계가 1,500원 이상”은 묶은 뒤에야 알 수 있어서 HAVING. 합계 조건을 WHERE 에 쓰면 에러가 납니다.
  • 경계값 — 김민준의 합계가 정확히 1,500원이라 >= 여서 포함됩니다. > 였다면 빠집니다.
  • 실행 순서가 결과에 영향 — Q11 은 Q13(UPDATE)보다 먼저 실행해 “갱신 전 연체료” 기준입니다. Q13 이후에 실행하면 새로 OVERDUE 가 된 3건의 연체료가 합쳐져 결과가 달라집니다.

30초 대본

가장 복잡했던 쿼리는 Q11, 연체료 합계가 1,500원 이상인 회원 찾기입니다. 먼저 대여 기록에 회원 이름을 JOIN 으로 붙이고, WHERE 로 연체료가 있는 기록 5건만 남겼습니다. 그다음 회원별로 GROUP BY 해서 4개 묶음을 만들고 SUM 으로 합계를 구했습니다. 마지막으로 HAVING 으로 합계가 1,500원 이상인 묶음만 남기니 최수빈 회원 1,200원이 빠지고 3명이 남았습니다. 이 쿼리에서 어려웠던 점은 WHERE 는 묶기 전에 행을 거르고 HAVING 은 묶은 뒤에 합계를 거른다는 구분이었습니다.

다른 쿼리를 골라야 한다면? — Q13 (UPDATE)

목표 : 반납 예정일이 지났는데 아직 ‘대여 중’인 기록을 ‘연체’로 바꾸고 연체료(하루 300원) 계산. ① 변경 전 확인 : GROUP BY status → RENTED 11 · OVERDUE 1 · RETURNED 26. ② UPDATE : WHERE status = 'RENTED' AND due_date < '2026-10-08' 로 대상을 좁히고, late_fee = (기준일 − due_date 일수) × 300 을 계산 (julianday(), SQLite 전용) → 3행 변경. ③ 변경 후 확인 : RENTED 8 · OVERDUE 4 · RETURNED 26. ④ 값 확인 : 28번 6일 × 300 = 1,800 · 29번 4일 × 300 = 1,200 · 30번 2일 × 300 = 600. WHERE 를 빼면 38행 전부가 바뀌므로, 전 · 후 SELECT 로 확인하는 것이 핵심입니다.

HAVING 없이 WHERE 만으로 풀 수 있나요?

합계 조건은 묶은 뒤에야 계산되므로 WHERE 만으로는 안 됩니다. 서브쿼리로 “회원별 합계”를 먼저 만든 뒤 바깥에서 WHERE total >= 1500 으로 거르는 방법은 있지만 HAVING 이 더 짧고 읽기 쉽습니다.

후보 A. FK 를 켜야 동작한다 (가장 추천)

문제 : 없는 회원 999번으로 대여 기록을 넣었더니 FK 를 걸었는데도 에러 없이 들어갔다.
원인 : SQLite 는 FK 검사가 기본 OFF 라서 접속(연결)마다 PRAGMA foreign_keys = ON 을 켜야 한다.
해결 : 01 · 02 · 03 SQL 파일 맨 위와 run_all.py 에 켜고, 일부러 끄고 같은 INSERT 를 해 보는 대조 실험으로 확인했다. (00_verify.txt 맨 아래)

후보 A 를 고른 경우의 30초 대본

가장 어려웠던 건 FK 가 실제로 동작하게 만드는 것이었습니다. 테이블에 FOREIGN KEY 를 선언했는데, 존재하지 않는 회원 999번으로 대여 기록을 넣었더니 에러 없이 들어갔습니다. 찾아보니 SQLite 는 FK 검사가 기본으로 꺼져 있어서 접속할 때마다 PRAGMA foreign_keys = ON 을 실행해야 했습니다. 그래서 SQL 파일 맨 위와 실행 스크립트에 켜 두었고, 일부러 끄고 같은 입력을 해서 에러 없이 들어간다는 것도 확인했습니다. 지금은 같은 입력이 FOREIGN KEY constraint failed 로 막힙니다.

FK 검사가 꺼져 있으면 어떻게 알아챌 수 있나요?
