QUESTION 1

데이터베이스와 엑셀의 차이점

왜 파일이나 엑셀이 아니라 DB 에 테이블로 나눠 저장할까?

엑셀과 DB 의 차이는 “데이터가 얼마나 많냐”가 아닙니다. 테이블 사이의 관계를 표현하고, 입력 규칙을 DB 가 대신 지켜 준다는 점이 다릅니다.
비유 — 엑셀은 “영수증을 한 장에 몰아 적은 공책”, DB 는 “회원 서랍 · 책 서랍 · 대여기록 서랍을 따로 두고 번호 쪽지로 연결한 서랍장”입니다.

① 엑셀식으로 한 시트에 적으면 — 김민준 회원의 대여 4건

이름이메일전화책 제목분류대여일
김민준minjun.kim@example.com010-1000-0001아몬드소설2026-07-03
김민준minjun.kim@example.com010-1000-0001혼자 공부하는 파이썬IT2026-07-22
김민준minjun.kim@example.com010-1000-0001클린 코드IT2026-08-10
김민준minjun.kim@example.com010-1000-0001점프 투 파이썬IT2026-09-30

빨간 칸처럼 같은 회원 정보가 대여할 때마다 반복됩니다. 이메일이 바뀌면 4곳을 다 고쳐야 하고, 하나라도 놓치면 “같은 사람인데 이메일이 다른” 데이터가 생깁니다.

② DB 는 나눠서 한 번만 저장하고 번호로 연결

회원 정보는 member 에 1번만 저장하고, rental 에는 회원 번호(member_id = 1)만 적습니다. 이메일을 바꿀 때는 member 의 1행만 고치면 모든 대여 기록에 반영됩니다.

③ 비교표

항목엑셀DB (우리 프로젝트)
저장 방식한 시트에 한 줄로 몰아 적음테이블 4개로 나누고 번호(PK/FK)로 연결
중복회원 정보가 대여마다 반복member 에 1번만

30초 대본

엑셀과 DB 의 가장 큰 차이는 데이터가 얼마나 많냐가 아니라 ‘관계’를 표현할 수 있느냐입니다. 엑셀은 한 시트에 회원 이름과 이메일을 대여할 때마다 반복해서 적어야 하고, 잘못 입력해도 막아 주지 않습니다. DB 는 회원·도서·대여 기록을 테이블로 나누고 번호로 연결해서 정보를 한 곳에만 저장합니다. 그리고 NOT NULL, UNIQUE, FK 같은 규칙이 잘못된 입력을 거부합니다. 실제로 제 DB 에 없는 회원 번호 999번으로 대여 기록을 넣으려고 하니 FOREIGN KEY constraint failed 에러로 막혔습니다.

예상 꼬리질문

엑셀도 VLOOKUP 으로 시트끼리 연결할 수 있지 않나요?

연결은 되지만 그 연결을 사람이 수식으로 유지해야 하고, “없는 값을 입력하는 것”은 막지 못합니다. DB 는 FK 가 연결 자체를 규칙으로 강제합니다.

그럼 엑셀은 쓰면 안 되나요?

아닙니다. 소량·개인용 집계에는 엑셀이 더 편합니다. 여러 테이블이 관계를 맺고, 규칙을 지켜야 하고, 여러 사람이 함께 쓰는 서비스 데이터에는 DB 가 맞습니다.

FK 검사를 끄면 어떻게 되나요?

SQLite 는 PRAGMA foreign_keys = ON 을 켜야 FK 가 동작합니다. 대조 실험으로 끄고 같은 INSERT(999번 회원)를 했더니 에러 없이 들어갔습니다(시도 후 롤백). 규칙은 “켜져 있어야” 지켜집니다. (results/00_verify.txt 하단)

QUESTION 2

PK / FK 가 뭐고, 1:N 이 어떻게 연결되는지

PK 는 행마다 붙는 “겹치지도 비지도 않는 고유 번호”, FK 는 그 번호를 다른 테이블에 적어 둔 연결 번호입니다. 1쪽의 한 행에 N쪽의 여러 행이 번호로 매달리는 것이 1:N 이고, FK 는 항상 N쪽 테이블에 있습니다.
비유 — PK 는 학번(한 사람에게만 붙고 겹치지 않음), FK 는 출석부에 이름 대신 적어 둔 학번입니다. 이름은 동명이인·개명이 있지만 번호는 변하지 않습니다.

우리 DB 의 4개 테이블과 1:N 관계 3개

  • category 1 : book N — 한 분류에 여러 도서 (book.category_id)
  • member 1 : rental N — 한 회원이 여러 번 대여 (rental.member_id)
  • book 1 : rental N — 한 도서가 여러 번 대여됨 (rental.book_id)

코드로 보면 — PK/FK 선언 (sql/01_schema.sql 일부)

CREATE TABLE rental (
    rental_id INTEGER PRIMARY KEY AUTOINCREMENT,  -- PK : 대여 기록 1건마다 붙는 고유 번호
    member_id INTEGER NOT NULL,                   -- FK 컬럼 : 누가 빌렸나 (member 의 번호)
    book_id   INTEGER NOT NULL,                   -- FK 컬럼 : 어떤 책인가 (book 의 번호)
    -- ... (대여일 · 반납예정일 · 상태 · 연체료 컬럼 생략)
    CONSTRAINT fk_rental_member
        FOREIGN KEY (member_id) REFERENCES member (member_id)
        ON DELETE RESTRICT,                       -- 대여 기록이 있는 회원은 삭제 불가
    CONSTRAINT fk_rental_book
        FOREIGN KEY (book_id)   REFERENCES book (book_id)
        ON DELETE RESTRICT                        -- 대여 기록이 있는 책은 삭제 불가
);

FK 가 지켜 주는 것 두 가지 — ① 없는 번호는 참조 불가 (999번 회원 INSERT → 거부), ② 참조당하는 행은 삭제 불가 (대여 기록이 있는 1번 회원·1번 도서 DELETE → 거부). 둘 다 results/00_verify.txt 에 기록되어 있습니다.

30초 대본

PK 는 한 행을 구분하는 고유 번호로, 중복되거나 비어 있을 수 없습니다. 학번 같은 것입니다. FK 는 다른 테이블의 PK 번호를 가져와 적어 둔 컬럼으로, ‘이 대여 기록은 몇 번 회원의 것이다’처럼 가리키는 역할을 합니다. 1:N 은 한 쪽의 한 행에 다른 쪽 여러 행이 연결되는 관계입니다. 제 DB 에서는 김민준 회원 1명에게 대여 기록이 4건 연결되고, 이때 FK 는 항상 N 쪽인 rental 테이블에 있습니다. 31번 대여 기록의 member_id 1 과 book_id 11 을 따라가면 김민준이 점프 투 파이썬을 빌렸다는 걸 알 수 있습니다.

예상 꼬리질문

PK 로 이름을 쓰면 안 되나요?

이름은 동명이인이 있고 개명으로 바뀔 수 있습니다. PK 는 겹치지 않고 변하지 않아야 하므로 의미 없는 번호(member_id)를 씁니다.

FK 는 왜 항상 N 쪽에 있나요?

1 쪽의 한 칸에 번호를 여러 개 적을 수 없기 때문입니다. 회원 칸에 “대여한 책 1, 10, 12, 11” 처럼 적는 대신, 대여 1건마다 한 줄(rental)을 만들고 거기에 member_id 를 적습니다.

회원과 도서는 서로 여러 개씩 연결되는데(N:M) 왜 1:N 만 있나요?

rental 이 둘 사이의 “다리” 역할을 합니다. 대여 1건 = 회원 1명 + 책 1권이므로, 회원→대여, 도서→대여 두 개의 1:N 으로 풀어서 표현합니다.

30초 대본

SELECT 는 읽기, INSERT 는 새 데이터 추가, UPDATE 는 있는 데이터 수정, DELETE 는 삭제입니다. 도서관으로 보면 회원 가입이 INSERT, 책 검색이 SELECT, 기한이 지난 대여를 연체로 바꾸는 게 UPDATE, 탈퇴가 DELETE 입니다. UPDATE 와 DELETE 는 WHERE 를 빼면 전체 행이 바뀌거나 지워지기 때문에 조건을 꼭 확인합니다. 제 Q13 에서는 기한이 지난 3건만 OVERDUE 로 바꿨고, Q14 에서는 대여 기록이 없는 회원 1명만 삭제했습니다.

예상 꼬리질문

UPDATE 에서 WHERE 를 빼먹으면 어떻게 되나요?

조건이 없으므로 rental 38행 전부의 status 와 late_fee 가 바뀝니다. 그래서 실행 전에 같은 WHERE 로 SELECT 를 먼저 돌려 대상 행을 확인합니다. (Q13 · Q14 도 전·후 SELECT 를 붙였습니다)

대여 기록이 있는 회원을 DELETE 하면요?

FOREIGN KEY constraint failed 로 거부됩니다. (results/00_verify.txt (5)) 기록이 주인 없는 번호가 되는 것을 FK 가 막아 줍니다.

INSERT 를 자식 테이블부터 하면요?

부모에 그 번호가 없으므로 FK 검사에서 실패합니다. 그래서 부모 → 자식 순서로 입력합니다.

QUESTION 4

JOIN 과 GROUP BY 로 연결된 데이터를 한 번에 뽑는 방법

JOIN 은 FK = PK 번호가 같은 행끼리 옆으로 붙여 흩어진 테이블을 한 표로 만들고, GROUP BY 는 같은 값끼리 묶어서 개수·합계·평균을 구합니다. 둘을 합치면 “누가 무엇을 몇 번” 같은 질문이 SQL 한 문장으로 풀립니다.
비유 — JOIN 은 “번호표를 맞춰 서류 3장을 클립으로 묶기”, GROUP BY 는 “대여 카드 38장을 책 제목별 상자에 나눠 담고 장수 세기”입니다.

① JOIN — 번호만 있는 표에 이름을 붙이기 (Q6)

rental 만 보면 member_id = 1, book_id = 11 같은 번호뿐이라 사람이 읽을 수 없습니다. 번호를 맞춰 member, book 을 붙입니다.

SELECT r.rental_id, m.name AS member_name, b.title, r.rented_at, r.due_date
FROM rental AS r                                   -- 기준 테이블 : 대여 기록
INNER JOIN member AS m ON m.member_id = r.member_id  -- 회원 번호가 같은 행을 붙임
INNER JOIN book   AS b ON b.book_id   = r.book_id    -- 책 번호가 같은 행을 붙임
WHERE r.status = 'RENTED'                          -- 대여 중인 것만

③ WHERE 와 HAVING — 묶기 “전”과 “후” (Q11)

SELECT m.name, COUNT(*) AS late_count, SUM(r.late_fee) AS total_late_fee
FROM rental AS r
INNER JOIN member AS m ON m.member_id = r.member_id
WHERE r.late_fee > 0                  -- 묶기 "전" : 연체료가 있는 기록만 남김 (행을 거름)

ORDER BY total_late_fee DESC;

30초 대본

대여 기록 테이블에는 회원 번호와 책 번호만 있어서 그것만으로는 누가 무엇을 빌렸는지 알기 어렵습니다. JOIN 은 FK 와 PK 가 같은 값끼리 연결해서 회원 이름과 책 제목을 한 줄로 붙여 줍니다. GROUP BY 는 같은 값끼리 묶어서 개수나 합계를 구합니다. 예를 들어 Q10 은 대여 기록에 책 제목을 JOIN 한 뒤 책별로 GROUP BY 해서 가장 많이 대여된 책 TOP 5 를 뽑았고, 1위는 ‘혼자 공부하는 파이썬’ 5회였습니다. 대여가 한 번도 없는 회원까지 보고 싶을 때는 INNER JOIN 대신 LEFT JOIN 을 씁니다.

예상 꼬리질문

WHERE 와 HAVING 의 차이는요?

WHERE 는 묶기 전에 개별 행을 거르고, HAVING 은 묶은 후에 그룹(합계·개수)을 거릅니다. 합계처럼 묶은 뒤에야 알 수 있는 값은 WHERE 에 쓸 수 없습니다. (Q11)

LEFT JOIN 에서 왜 COUNT(*) 가 아니라 COUNT(r.rental_id) 를 썼나요?

대여가 없는 회원도 결과에 1줄은 생깁니다(오른쪽이 NULL). COUNT(*) 는 그 줄을 1건으로 세어 “0건 회원이 1건”이 되고, COUNT(r.rental_id) 는 NULL 을 빼고 세어 정확히 0 이 나옵니다. (Q8)

JOIN 대신 서브쿼리로도 풀 수 있나요?

“대여 기록이 없는 회원”처럼 있다/없다만 판단할 때는 서브쿼리(Q12 의 NOT IN (SELECT …))도 됩니다. 반면 회원 이름과 책 제목을 함께 보여 줘야 할 때는 JOIN 이 필요합니다.

QUESTION 5

인덱스가 왜 필요하고, 어떤 컬럼에 적용하면 좋은지

인덱스는 책 뒤의 색인입니다. 없으면 DB 가 모든 행을 처음부터 끝까지 읽고(SCAN), 있으면 색인으로 바로 찾아갑니다(SEARCH). 자주 검색·JOIN 하고 값이 다양한 컬럼에 만들면 효과가 큽니다.
비유 — 두꺼운 책에서 “파이썬”이 나온 쪽을 찾을 때, 1쪽부터 넘기는 것(SCAN) vs 뒤쪽 색인을 보고 바로 펴는 것(SEARCH).

우리 DB 에서의 변화 (Q15)

-- (1) 인덱스 만들기 전 : 3번 회원의 대여 기록 찾기
EXPLAIN QUERY PLAN SELECT * FROM rental WHERE member_id = 3;
--> SCAN rental                                   ← 38행을 처음부터 끝까지 읽음

-- (2) 인덱스 생성
CREATE INDEX idx_rental_member_id ON rental (member_id);

-- (3) 같은 쿼리를 다시
EXPLAIN QUERY PLAN SELECT * FROM rental WHERE member_id = 3;
--> SEARCH rental USING INDEX idx_rental_member_id (member_id=?)   ← 색인으로 바로 찾음
솔직한 단서 — 지금은 38행뿐이라 속도 차이를 체감할 수는 없습니다. 그래도 “실행 방식이 SCAN → SEARCH 로 바뀐다”는 것이 핵심이고, 대여 기록이 수십만 건 쌓이는 실제 서비스에서는 이 차이가 커집니다.

좋은 컬럼 · 나쁜 컬럼 체크리스트

만들면 좋은 컬럼피하는 편이 좋은 경우
  • WHERE 로 자주 검색하는 컬럼
  • JOIN … ON 에 쓰는 FK 컬럼
  • ORDER BY 로 자주 정렬하는 컬럼
  • 값이 다양한 컬럼 (이메일 · 회원번호 · 날짜)
  • 값 종류가 적은 컬럼 (상태 · 성별)
  • 거의 조회 조건에 안 쓰는 컬럼
  • INSERT / UPDATE 가 매우 잦은 테이블
  • 행이 몇십 건뿐인 작은 테이블

왜 무작정 다 만들지 않나? 인덱스는 데이터를 넣고 고칠 때마다 색인도 함께 갱신해야 해서 쓰기가 느려지고 저장 공간도 더 씁니다. 읽기 이득과 쓰기 비용을 저울질해서 만듭니다.

30초 대본

인덱스는 책 뒤의 색인과 같습니다. 인덱스가 없으면 DB 가 모든 행을 처음부터 끝까지 읽어야 하지만, 있으면 색인으로 바로 찾아갑니다. 저는 rental 의 member_id 에 인덱스를 만들었더니 실행 계획이 SCAN 에서 SEARCH USING INDEX 로 바뀌었습니다. 인덱스는 WHERE 나 JOIN 에 자주 쓰이고 값이 다양한 컬럼, 예를 들어 FK 나 이메일에 만들면 좋습니다. 반대로 status 처럼 값 종류가 적거나 쓰기가 잦은 테이블에서는 오히려 부담이 됩니다. 지금은 데이터가 38행뿐이라 속도 차이를 체감하긴 어렵지만, 데이터가 커질수록 효과가 커집니다.

예상 꼬리질문

인덱스는 많이 만들수록 좋은가요?

아닙니다. 인덱스마다 INSERT · UPDATE · DELETE 때 같이 갱신되어 쓰기가 느려지고 용량도 늘어납니다. 자주 쓰는 조회에만 만듭니다.

38행인데 인덱스가 의미가 있나요?

이 크기에서는 속도 차이가 없습니다. 과제에서는 “대여 기록이 계속 쌓이는 테이블”을 가정하고, 실행 계획이 SCAN → SEARCH 로 바뀌는 것을 눈으로 확인하는 데 의미가 있습니다.

PK 컬럼에는 인덱스를 따로 만들어야 하나요?

아니요. PK 와 UNIQUE 컬럼은 DB 가 자동으로 빠르게 찾을 수 있게 관리합니다. 그래서 직접 만드는 인덱스는 FK 컬럼처럼 “자동으로 안 만들어지는데 자주 쓰는 컬럼”에 합니다.

발표 직전 5문장 요약 카드

  1. DB vs 엑셀 — 양이 아니라 관계와 규칙. 테이블로 나눠 번호로 잇고, 잘못된 입력은 DB 가 거부한다. (999번 회원 → FK 에러)
  2. PK/FK/1:N — PK 는 고유 번호, FK 는 그 번호를 N쪽에 적어 둔 연결 번호. 김민준 1 : 대여 4.
  3. CRUD — SELECT 읽기 · INSERT 추가(부모 먼저) · UPDATE 수정 · DELETE 삭제. UPDATE/DELETE 는 WHERE 확인.
  4. JOIN/GROUP BY — JOIN 으로 번호를 맞춰 붙이고, GROUP BY 로 묶어 센다. 0건까지 보려면 LEFT JOIN + COUNT(컬럼).
  5. 인덱스 — 책 뒤 색인. SCAN → SEARCH. 자주 검색·JOIN 하고 값이 다양한 컬럼에, 대신 쓰기 비용이 든다.
