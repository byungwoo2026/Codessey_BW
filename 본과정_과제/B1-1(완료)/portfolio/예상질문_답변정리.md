## 항목 1 — 기능 동작 확인

### 문항 1. 브라우저 창 크기를 줄였을 때 레이아웃이 모바일에 맞게 변경되는가?

**구현 위치**: `css/style.css` — 모바일 퍼스트로 작성 후 `@media (min-width: 768px)`, `@media (min-width: 1024px)`에서 레이아웃을 확장.
`.nav-menu`는 기본이 세로 오버레이 메뉴이고 768px 이상에서 가로 배치로, `.about-grid`는 기본이 세로 스택이고 768px 이상에서 사진+글이 가로로 나란히 배치됨.

**확인 방법 / 결과**: 뷰포트 390px로 축소해 실제로 확인 — 햄버거 버튼이 노출되고(`display: flex`), 클릭 시 전체 메뉴 오버레이가 정상적으로 열림. ✅ 확인 완료

### 문항 2. 테마 토글 버튼 클릭 시 다크/라이트 모드가 전환되고, 새로고침 후에도 유지되는가?

**구현 위치**: `js/main.js` — `applyTheme()`이 `<html>`에 `data-theme="dark"` 속성을 토글하고, `localStorage.setItem(THEME_STORAGE_KEY, currentTheme)`으로 상태를 저장. 페이지 로드 시 `getPreferredTheme()`이 저장된 값을 먼저 읽고, 없으면 `prefers-color-scheme`로 시스템 설정을 따름.

**확인 방법 / 결과**: 토글 클릭 → 배경색이 `rgb(246,247,245)`에서 `rgb(11,15,20)`으로 전환됨을 확인. 새로고침(F5) 후에도 `data-theme="dark"`가 그대로 유지됨을 확인. ✅ 확인 완료

### 문항 3. 햄버거 메뉴, 스크롤 애니메이션, 맨 위로 가기 버튼 등이 정상 동작하는가?

**구현 위치**: `js/main.js` — `hamburgerBtn`(메뉴 토글), `IntersectionObserver` + `.reveal`(등장 애니메이션), `scrollTopBtn`(맨 위로 가기).

**확인 방법 / 결과**:
- 헤더: `scrollY > 60`에서 `is-scrolled` 클래스가 붙어 배경/그림자 생김 — 확인 완료
- 등장 애니메이션: `.reveal` 대상 12개가 각 섹션에 스크롤해 들어갈 때마다 `is-visible`이 순차적으로 부여됨 — 확인 완료
- 맨 위로 가기 버튼: `scrollY > 300`에서 노출, 클릭 시 `scrollTo({ top: 0, behavior: "smooth" })`로 부드럽게 이동 — 확인 완료
✅ 확인 완료

### 문항 4. GitHub API에서 데이터를 불러와 화면에 표시되고, 로딩/에러/빈 상태가 구분되는가?

**구현 위치**: `js/github.js`의 `loadProjects()` — `renderLoading()` / `renderError()` / `renderEmpty()` / `renderProjects()` 4가지 렌더링 함수가 상태별로 분리되어 있음.

**확인 방법 / 결과**: 정상 상태에서는 저장소 카드 6개가 언어 필터(전체/Python/HTML/CSS)와 함께 로딩됨을 확인. 실제로 GitHub API 시간당 요청 한도(60회)를 초과했을 때는 `response.status === 403`을 감지해 "GitHub API 요청 한도를 초과했습니다" 메시지와 **다시 시도 버튼**이 정확히 표시되는 것도 직접 경험함 — 로딩/성공/에러 3가지 상태 전환이 실제로 코드 의도대로 동작함을 확인. ✅ 확인 완료

### 문항 5. 필수 입력값 누락, 이메일 형식 오류 시 즉각적인 피드백이 표시되는가?

**구현 위치**: `js/form.js` — 필드별 `validate` 함수와 `input`/`submit` 이벤트 리스너로 실시간·제출 시 검증.

**확인 방법 / 결과**: 빈 값으로 제출 시 이름/이메일/메시지 3개 필드 아래 각각 에러 문구 표시, `abc` 같은 잘못된 형식 입력 시 "이메일 형식이 올바르지 않습니다." 표시, 값을 올바르게 채운 뒤 제출하면 "메시지가 성공적으로 전송되었습니다. 감사합니다!" 성공 메시지로 전환됨을 순서대로 확인. ✅ 확인 완료

## 항목 2 — 구조와 설계 근거

### 문항 1. HTML, CSS, JavaScript가 각각의 파일로 분리되어 있고, 분리한 이유와 각 파일의 역할을 구분하여 답변할 수 있는가?

**관심사 분리(Separation of Concerns)** 원칙에 따라 나눴습니다.

- `index.html` — 콘텐츠와 구조(시맨틱 마크업)만 담당. 스타일이나 동작 로직은 전혀 포함하지 않음.
- `css/style.css` — 색상·폰트·레이아웃·반응형·애니메이션 등 **모양(presentation)**만 담당.
- `js/main.js` — 다크모드, 헤더 스크롤 스타일, 햄버거 메뉴, 스무스 스크롤, 스크롤 등장 애니메이션 등 **페이지 전역 UI 상호작용**.
- `js/github.js` — GitHub API 호출과 Projects 렌더링 등 **외부 데이터 연동**.
- `js/form.js` — Contact 폼 **유효성 검사**.

JS를 한 파일에 몰아넣지 않고 역할별로 3개 파일로 나눈 이유는, 예를 들어 폼 검증 로직만 수정할 때 다른 기능(다크모드, API)의 코드를 열어볼 필요가 없게 하기 위해서입니다. 즉 **한 파일 = 한 책임**이 되도록 구성했습니다.

### 문항 2. header, nav, main, section, footer 등 시맨틱 태그를 사용했고, 어떤 기준으로 태그를 선택했는지 설명할 수 있는가?

"이 블록이 사라지거나 다른 곳으로 옮겨져도 문서 구조상 의미가 통하는가"를 기준으로 선택했습니다.

- `<header>` — 사이트 상단의 정체성 영역(로고 + 내비게이션)
- `<nav>` — 페이지 내 주요 이동 링크 묶음
- `<main>` — 문서의 핵심 콘텐츠 전체(문서당 1개만 사용)
- `<section>` — Hero/About/Skills/Projects/Contact처럼 **주제가 뚜렷하게 구분되는 콘텐츠 블록**
- `<article>` — GitHub 저장소 카드 하나하나(`js/github.js`의 `buildProjectCard`에서 생성). 저장소 정보는 그 자체로 독립적으로 떼어내 재사용해도 의미가 통하는 단위이므로 `article`을 사용
- `<footer>` — 저작권/소셜 링크 등 부가 정보

반대로 순수하게 레이아웃 정렬 목적(예: `.container`, `.hero-inner`)에는 의미 없는 `<div>`를 그대로 사용했습니다.

### 문항 3. CSS 변수(`:root`)로 색상, 폰트 등을 정의했고, 변수로 관리하면 어떤 이점이 있는지 구체적으로 답변할 수 있는가?

1. **일관성** — 색상·폰트·간격 값을 한 곳에서 정의하므로, 디자인을 바꿀 때 값 하나만 고치면 전체에 반영됨.
2. **다크모드 구현이 단순해짐** — `[data-theme="dark"] { --color-bg: ...; ... }` 처럼 **같은 변수 이름을 다른 값으로 재정의**하는 것만으로 전체 UI 색상이 자동 전환됨. 버튼, 카드, 폼 등 각 컴포넌트의 CSS는 `var(--color-bg)`처럼 변수만 참조하기 때문에 컴포넌트 코드를 전혀 건드릴 필요가 없음.
3. **하드코딩 방지** — `#2fbf71` 같은 색상 값이 CSS 전체에 흩어져 있으면 나중에 색을 바꿀 때 빠짐없이 찾아 고쳐야 하지만, 변수로 관리하면 실수 가능성이 줄어듦.

### 문항 4. `onclick` 인라인 속성 대신 `addEventListener`를 사용한 이유를 두 방식의 차이를 비교하여 제시할 수 있는가?

| 구분 | `onclick="fn()"` (인라인) | `addEventListener` |
|---|---|---|
| 관심사 분리 | HTML 안에 JS 로직이 섞임 | HTML은 구조만, JS 파일에서 동작 선언 |
| 핸들러 개수 | 같은 요소에 하나만 지정 가능(덮어씀) | 같은 요소에 여러 핸들러 동시 등록 가능 |
| 제거 | 사실상 어려움 | `removeEventListener`로 제거 가능 |
| 이벤트 단계 제어 | 불가능 | 캡처/버블 단계 지정 가능(3번째 인자) |

과제 요구사항 자체가 "HTML/CSS/JS 파일 분리"이기 때문에, `onclick` 인라인 속성을 쓰면 그 원칙이 깨집니다. 실제로 `index.html`에는 클릭 동작이 전혀 적혀 있지 않고, `js/main.js`의 `hamburgerBtn.addEventListener("click", ...)`처럼 JS 파일에서만 이벤트를 연결했습니다.

## 항목 3 — 코드 흐름 설명

### 문항 1. 다크 모드, API 호출, 폼 유효성 검사 중 하나를 예시로 들어, "이벤트 → 상태 변경 → 화면 업데이트" 흐름이 코드에서 어떻게 이어지는지 따라가며 짚어줄 수 있는가?

**예시: 다크모드**

1. 사용자가 `#theme-toggle` 버튼 클릭 → **이벤트** 발생 (`js/main.js`의 `click` 리스너)
2. 리스너 안에서 `currentTheme`을 `"light"` ↔ `"dark"`로 토글 → **상태 변경**
3. `applyTheme(currentTheme)` 호출 → `document.documentElement`에 `data-theme="dark"` 속성을 추가/제거
4. CSS의 `[data-theme="dark"] { ... }` 규칙이 `:root` 변수를 재정의해뒀기 때문에, 속성이 바뀌는 즉시 배경색·글자색·포인트 컬러가 전부 다시 계산되어 **화면 업데이트**
5. 동시에 `localStorage.setItem(...)`으로 상태를 저장 → 새로고침 시 `getPreferredTheme()`이 저장된 값을 읽어 초기 상태를 복원 (상태 유지)
6. 같은 함수 안에서 푸터의 `#status-theme` 텍스트, 토글 아이콘(🌙/☀️)도 함께 갱신 — **하나의 상태 변경이 여러 화면 요소에 동시에 반영되는 예**

### 문항 2. `async/await`와 `try/catch`를 사용하여 API 호출 성공과 실패를 어떻게 분기 처리했는지 코드 흐름을 따라 답변할 수 있는가?

**`js/github.js`의 `loadProjects()
1. `renderLoading()`을 먼저 호출해 스켈레톤 카드로 **로딩 상태** 표시
2. `try` 블록에서 `await fetch(GITHUB_API_URL)` — 콜백 중첩 없이 순차적인 코드처럼 응답을 기다림
3. `response.ok`가 `false`면 상태 코드별로 분기: `403`은 레이트 리밋, `404`는 사용자 없음, 그 외는 일반 에러 → 각각 다른 메시지로 `throw new Error(...)`
4. 정상이면 `await response.json()`으로 파싱 → 배열이 비어 있으면 `renderEmpty()` 호출 (**빈 상태**)
5. 데이터가 있으면 `allRepos`에 저장하고 `renderFilters` + `renderProjects` 호출 (**성공 상태**)
6. `catch` 블록이 3번에서 던진 에러뿐 아니라 네트워크 자체 실패(오프라인 등)까지 한 번에 잡아서 `renderError(error.message)` 호출 → 에러 메시지 + "다시 시도" 버튼 렌더링 (**에러 상태**)
7. "다시 시도" 버튼 클릭 시 `loadProjects()`를 다시 호출해 1번부터 흐름이 반복됨

→ 4가지 상태(로딩/성공/에러/빈)가 하나의 함수 안에서 분기되고, 각 분기가 정확히 하나의 렌더링 함수와 대응되도록 짰습니다.

### 문항 3. `map`, `filter` 등 배열 메서드를 활용하여 GitHub 데이터를 카드 UI로 변환하는 과정을 단계별로 정리할 수 있는가?

1. `fetch`로 받은 원본 배열(`repos`)은 GitHub API가 주는 저장소 객체 배열(수십 개 필드 포함)
2. `buildProjectCard`에서 **구조분해 할당**으로 필요한 필드만 추출: `{ name, description, html_url, stargazers_count, language }`
3. `repos.map(buildProjectCard)` — 저장소 객체를 카드 HTML 문자열(템플릿 리터럴)로 1:1 변환 → 문자열 배열 생성
4. `.join("")`으로 문자열 배열을 하나의 HTML 문자열로 합쳐 `projectsGrid.innerHTML`에 한 번에 대입
5. 필터 목록 생성: `repos.map(repo => repo.language)`로 언어 값만 뽑고 → `.filter(Boolean)`으로 `null`/`undefined`(언어 정보 없는 저장소) 제외 → `new Set(...)`으로 중복 제거
6. 필터 버튼 클릭 시 `allRepos.filter(repo => repo.language === activeLanguage)`로 원본 데이터에서 다시 추려 `renderProjects`를 재호출 — API를 다시 호출하지 않고 메모리에 있는 데이터만 재사용

### 문항 4. Flexbox와 Grid를 각각 어디에 적용했는지 확인하고 해당 상황에서 그 방식을 선택한 이유를 비교하여 설명할 수 있는가?

| 사용처 | 방식 | 이유 |
|---|---|---|
| `.navbar` (로고-메뉴 좌우 배치), `.hero-cta`, `.skill-tags`, `.status-bar` | **Flexbox** | 한 방향(가로 또는 세로)으로 아이템을 정렬·분배하면 되는 **1차원 레이아웃** |
| `.projects-grid` (`repeat(auto-fit, minmax(260px, 1fr))`), `.skills-grid`(데스크톱 3열) | **Grid** | 화면 너비에 따라 **행과 열을 함께 고려**해 자동으로 열 개수를 조절해야 하는 **2차원 레이아웃** |

Flexbox는 아이템 개수가 가변적이어도 한 줄(또는 한 방향) 정렬에는 간단하지만, 여러 행에 걸친 정렬을 세밀하게 통제하기는 어렵습니다. 반면 Grid는 `auto-fit`/`minmax()`처럼 "이 너비 이상이면 카드를 한 줄에 몇 개 배치할지 자동 계산"하는 것에 최적화되어 있어서, 필터링으로 카드 개수가 실시간으로 바뀌는 Projects 섹션에 더 적합했습니다.

## 항목 4 — 설계 판단

### 문항 1. 상태(STATE) 객체를 따로 만들어서 관리한 이유는 무엇이며, 그냥 변수로 처리하면 안 되는지 설명할 수 있는가?

프로젝트에는 `currentTheme`(main.js), `allRepos` / `activeLanguage`(github.js) 같은 상태 변수가 있습니다. 이걸 별도 변수로 유지하지 않고 그때그때 DOM에서 읽어오는 방식과 비교하면:

- `allRepos`를 변수로 저장해두지 않으면, 언어 필터 버튼을 클릭할 때마다 "원본 전체 목록"을 어디서도 가져올 수 없습니다. 화면에는 이미 필터링된 일부 카드만 남아있기 때문입니다. → **상태를 변수로 보관해야 "필터 해제(전체 보기)"가 가능**합니다.
- DOM은 "현재 상태를 반영한 결과물"이지 상태의 원본(source of truth)이 아닙니다. `classList.contains('active')`처럼 DOM을 상태 판단 기준으로 삼으면, 여러 요소의 클래스를 매번 순회하며 확인해야 하고 화면과 상태가 어긋났을 때 원인 추적이 어려워집니다.
- 변수로 상태를 명시하면 "지금 이 앱이 어떤 상태인가"를 코드 몇 줄만 보고도 파악할 수 있어 유지보수와 디버깅이 쉬워집니다.
- 부수 효과로, `allRepos`를 캐싱해뒀기 때문에 필터를 바꿀 때마다 GitHub API를 다시 호출하지 않아도 됩니다(불필요한 네트워크 요청 방지).

### 문항 2. 반응형 디자인에서 "모바일 퍼스트"로 작성한 이유를 이야기할 수 있는가?

`css/style.css`는 미디어 쿼리가 없는 기본 상태를 **모바일 레이아웃**으로 작성하고, `@media (min-width: 768px)`, `@media (min-width: 1024px)`처럼 화면이 커질수록 스타일을 **추가**하는 방식으로 짰습니다. (예: `.nav-menu`는 기본이 숨김 상태의 세로 메뉴이고, 768px 이상에서 가로 배치로 바뀝니다.)

이유:

1. 제약이 가장 큰 환경(작은 화면, 터치 인터랙션)을 기준으로 먼저 설계하면 "정말 필요한 콘텐츠가 무엇인지" 우선순위를 명확히 정하게 됩니다.
2. `min-width` 미디어 쿼리는 "화면이 커지면 여유 공간을 활용해 확장한다"는 자연스러운 방향이라 CSS 규칙끼리 충돌이 적습니다. 반대로 데스크톱을 기본으로 짜고 `max-width`로 축소하는 방식은, 작은 화면을 위한 예외 처리(override)가 점점 누적되어 코드가 복잡해지기 쉽습니다.
3. 불필요하게 무거운 데스크톱 전용 스타일을 모바일 기기가 먼저 해석할 필요가 없어 성능 면에서도 유리합니다.

## 항목 5 — 보너스 문제 해결에 따른 크레딧 부여

### 문항 1. 시스템 다크모드 감지

**구현 위치**: `js/main.js`의 `getPreferredTheme()` — `localStorage`에 저장된 값이 없을 때 `window.matchMedia("(prefers-color-scheme: dark)")`로 시스템 설정을 읽어 초기 테마로 사용합니다. 즉 사용자가 한 번도 토글을 누른 적이 없어도, OS/브라우저가 다크모드라면 첫 방문부터 다크모드로 보여줍니다.

### 문항 2. GitHub 프로젝트 언어별 필터링

**구현 위치**: `js/github.js`의 `renderFilters()` — 저장소 배열에서 `array.map`으로 언어만 뽑고 `array.filter(Boolean)`으로 언어 정보가 없는 저장소를 제외한 뒤 `Set`으로 중복을 제거해 필터 버튼 목록을 만듭니다. 버튼 클릭 시 `allRepos.filter(repo => repo.language === activeLanguage)`로 원본 데이터를 다시 걸러 `renderProjects`만 재호출하므로, API를 다시 호출하지 않고도 즉시 필터링됩니다.
