전체 흐름은 이 한 줄입니다. 로그의 [INFO] 순서가 그대로 이 흐름입니다.

cd C:\Users\user\codyssey\본과정_과제\B3-2\ai-gitgen

$env:AI_API_KEY = "<본인 키>"

$env:AI_API_BASE_URL = "https://api.groq.com/openai/v1/chat/completions"

# ① 변경 사항 없음 (깨끗한 상태에서 먼저)
git status
python main.py commit

# ② 시연용 변경 만들기
Add-Content README.md "demo line"

# ③ API Key 없음  (키를 변수에 잠깐 보관했다가 복구)

python main.py commit ; $LASTEXITCODE        # 1 이 나와야 함
$env:AI_API_KEY = $k

# ④ 정상 실행
python main.py commit

# ⑤ 옵션 비교 (항목 1의 6번 표 참고)

주의 ① 변경 사항 검사가 Key 검사보다 먼저 — 변경이 없으면 키가 없어도 “변경 사항이 없습니다”로 먼저 끝납니다. 그래서 Key 누락 시연은 반드시 ② 이후(변경이 있는 상태)에서 합니다. (직접 실행해서 확인한 순서입니다.)
주의 ② 프로젝트 루트에서 실행 — 하위 폴더나 다른 폴더에서 실행하면 오류로 끝납니다(항목 2의 4번 표). 명령 앞의 python main.py는 루트에서 입력합니다.
주의 ③ pr은 “아직 커밋 안 한 변경”이 있으면 그대로 동작합니다. 이미 커밋을 끝낸 feature 브랜치라면 python main.py pr --base main처럼 기준 브랜치를 줘야 합니다. 안 주면 변경 사항이 없습니다. PR 초안을 생성하지 않고 종료합니다.가 나옵니다(확인함).

[INFO] Git status 수집 완료: 1개 파일 변경 감지

--- PR Title -----------------------------------------------

------------------------------------------------------------

--- PR Body ------------------------------------------------
## Why
- 클론 주소가 템플릿 값이라 수정이 필요함

## What
- README.md 의 git clone URL 을 실제 주소로 교체

항목 1 · 3/7

AI API Key가 설정되지 않은 상태에서 실행하면 오류 메시지가 출력되고 종료되는가?

핵심 답네. AI_API_KEY 환경변수가 없으면 API를 부르기 전에 오류 메시지를 출력하고 종료 코드 1로 끝납니다. 호출 횟수는 0회입니다.

1

항목 1 · 4/7

핵심 답네. 변경이 없으면 변경 사항이 없습니다를 출력하고 AI를 부르지 않고 정상 종료(종료 코드 0)합니다.

nothing to commit, working tree clean
PS> python main.py commit
[INFO] Git status 수집 완료: 0개 파일 변경 감지

...
[INFO] 변경 사항이 없습니다. PR 초안을 생성하지 않고 종료합니다.

항목 1 · 5/7

출력된 PR 본문에 Why/What/How to Test 구조가 포함되고, 각 섹션에 최소 1개 불릿이 포함되는가?

핵심 답네. AI에게는 내용만 JSON 리스트로 받고, ## Why / ## What / ## How to Test 틀과 - 불릿은 코드가 만들기 때문에 섹션이 빠질 수 없습니다. 비어 있으면 안내 불릿을 넣고, 완성된 본문을 정규식으로 한 번 더 검사합니다.
[CHECK] 형식 검증 결과
  [OK  ] PR 제목 21자 (최대 80자 이내)
  [OK  ] 'Why' 섹션 불릿 1개
  [OK  ] 'What' 섹션 불릿 1개
  [OK  ] 'How to Test' 섹션 불릿 1개
  [OK  ] PR 본문 템플릿 검증 통과 (Why/What/How to Test + 각 섹션 불릿 1개 이상)

AI가 why를 빈 리스트로 줬을 때(가짜 서버로 일부러 재현):

## Why
- (AI가 내용을 생성하지 않았습니다 — 직접 작성하세요)      <- 코드가 채움
...
  [FIX ] 'Why' 섹션이 비어 있어 안내 불릿 삽입
  [OK  ] PR 본문 템플릿 검증 통과 (Why/What/How to Test + 각 섹션 불릿 1개 이상)
  • [OK] = 문제없음 / [WARN] = 주의 / [FIX] = 코드가 고쳤음. 어떤 조치를 했는지 숨기지 않고 보여 줍니다.
  • 마지막 줄 검증은 독립 검사입니다 — 만들 때 쓴 로직이 아니라, 완성된 문자열을 다시 정규식으로 읽어 확인합니다.

항목 1 · 6/7

-temperature 또는 -max-tokens 값을 변경해 실행했을 때 출력 길이/디테일 차이가 재현되는가?

핵심 답값은 요청에 그대로 실려 로그에 찍힙니다. temperature는 문구의 다양성, max-tokens는 “여기서 자름” 기준이라, 낮은 값·작은 값으로 바꿔 실행하면 차이를 보여 줄 수 있습니다. 단일 대시(-temperature)와 이중 대시(--temperature) 둘 다 됩니다.
보여줄 것명령기대하는 모습
temperature 낮음python main.py commit -temperature 0.0 (2~3번)실행해도 거의 같은 문구
temperature 높음python main.py commit -temperature 1.5 (2~3번)실행마다 표현이 달라짐
max-tokens 작음python main.py commit -max-tokens 100[WARN] 응답이 max_tokens 한도에서 잘렸습니다 후 JSON 해석 실패
max-tokens 충분python main.py commit -max-tokens 2000정상 출력

직접 확인한 것 — 값이 로그와 요청 본문에 반영되는지, 작은 max-tokens에서 잘릴 때의 동작 (잘림은 가짜 서버가 일부러 잘라 보낸 응답):

$ python main.py commit -temperature 0.0 -max-tokens 2000
[INFO] AI API 요청 중... (provider=openai, model=gpt-4o-mini, temperature=0.0, max_tokens=2000)

$ python main.py commit -max-tokens 100
[INFO] AI API 요청 중... (provider=openai, model=gpt-4o-mini, temperature=0.3, max_tokens=100)
[INFO] AI API 호출 횟수: 1회 / 토큰 사용: 입력 321, 출력 100
[WARN] 응답이 max_tokens 한도에서 잘렸습니다. --max-tokens 값을 늘려 보세요.
[ERROR] AI 응답을 JSON 으로 해석하지 못했습니다. --max-tokens 를 늘리거나 --temperature 를 낮춰 다시 시도하세요.
        원본 응답 앞부분: '{"summary": "README 의 클론 주소를 수정했습니다.", "title": "d'

$ python main.py commit -max-tokens 20
[ERROR] --max-tokens 는 50 이상이어야 합니다 (JSON 응답이 잘릴 수 있음).      (종료 코드 2)
$ python main.py commit --temperature 3
[ERROR] --temperature 는 0.0 ~ 2.0 사이여야 합니다.                          (종료 코드 2)
당황하지 않는 법
  • max-tokens는 상한이라서, 실제로 필요한 길이보다 크게 줘도 결과는 같습니다(800 vs 2000이 똑같이 나와도 정상). 필요한 길이보다 작을 때만 잘립니다.
  • 실제 AI에서의 문구 차이는 이 문서에서 직접 확인한 값이 아닙니다. 모델마다 다르니 시연 전에 한 번 돌려 보세요. 차이가 작게 나오면 “이 모델에서는 이렇게 나왔다”고 그대로 설명하는 것이 안전합니다.
  • README에 적은 대로 gpt-oss-120b 같은 추론형 모델은 답하기 전에 내부 추론에 토큰을 먼저 써서, 작은 값이면 응답이 잘릴 수 있습니다(그래서 --max-tokens 2000). 일부 추론형 모델은 temperature 자체를 거부해 HTTP 400이 날 수도 있습니다.

  • 하한 50: 그보다 작으면 JSON 구조 자체가 완성될 수 없어서 호출 전에 막습니다.

항목 4 · 2/3

git diff에 민감정보(API Key, 개인정보 등)가 포함될 수 있는 상황과 이를 방지하기 위한 방안을 설명할 수 있는가?

핵심 답diff는 AI 서버로 전송되므로, 코드에 박아 둔 키·.env 같은 파일·비밀번호·개인정보가 섞이면 그대로 외부로 나갑니다. 그래서 전송 전에 safe-mode(기본 ON)가 ① 패턴 마스킹 ② 민감 파일 내용 제외 ③ 전송량 제한을 합니다.
민감정보가 섞이는 상황safe-mode의 대응
코드에 API Key를 직접 적음 (sk-…, AWS AKIA…, Google AIza…, GitHub ghp_…, JWT)패턴을 찾아 [MASKED_API_KEY] 등으로 치환
password = "…", token, secret 대입문값 부분만 [MASKED_SECRET]
테스트 데이터·문서의 이메일, 휴대폰, 주민번호[MASKED_EMAIL], [MASKED_PHONE], [MASKED_RRN]
.env, *.pem, *.key, id_rsa*, *secret* 등을 실수로 git add파일 내용 자체를 보내지 않고 “민감 파일로 판단되어 내용 전송 제외”만 전달
diff가 너무 커서 많은 정보가 한꺼번에 나감최대 10개 파일 / 200줄로 제한(--max-files, --max-lines)

직접 실행한 결과 — 키·이메일·전화번호·비밀번호가 든 settings.py와 .env를 스테이징하고 --dry-run(실제 전송될 프롬프트 확인):

# safe-mode ON (기본)
[INFO] safe-mode ON (최대 10개 파일 / 200줄): 17줄 -> 12줄 전송
[INFO] 민감정보 마스킹 4건: OPENAI/ANTHROPIC_KEY 1건, EMAIL 1건, PHONE(KR) 1건, SECRET_ASSIGNMENT 1건
[INFO] 민감 파일 내용 제외: .env
  diff --git a/.env b/.env
  [safe-mode] 민감 파일로 판단되어 내용 전송 제외
  +OPENAI_KEY = "[MASKED_API_KEY]"
  +admin = "[MASKED_EMAIL]"
  +phone = "[MASKED_PHONE]"
  +password = "[MASKED_SECRET]"

# --no-safe-mode
[WARN] safe-mode OFF: diff 원문이 그대로 AI API 로 전송됩니다.
  +AI_API_KEY=abc123secret
  +OPENAI_KEY = "sk-proj-abcdefghijklmnopqrstuvwxyz123456"
  +admin = "hong@example.com"
  +phone = "010-1234-5678"
  +password = "hunter2pass"

실제 API 요청 본문(가짜 서버가 받은 값)에서도 sk-proj-…, 이메일, 전화번호, hunter2pass, .env의 값 5개가 모두 들어 있지 않음을 확인했습니다.

그 밖의 방지책

  • 키 관리: API Key는 코드·README에 적지 않고 환경변수로만 받습니다. 실수로 올렸다면 즉시 폐기(재발급).
  • 미리 보기: --dry-run으로 전송 내용을 먼저 확인할 수 있습니다.
  • 저장소 관리: .env·키 파일은 .gitignore에 넣어 애초에 스테이징되지 않게 합니다.
  • safe-mode를 꺼도 경고를 보여 주고, 2000줄 상한은 유지합니다.
한계 (직접 확인한 것) — 이것까지 말하면 이해도가 높게 보입니다
  • 정규식 기반이라 모든 민감정보를 잡는다고 보장할 수 없습니다. 예: password = "mysecretpw"처럼 숫자 없는 소문자 값은 “변수 이름처럼 보인다”고 판단해 마스킹되지 않았고, 한글에 바로 붙은 전화번호(연락처010-1234-5678입니다)도 마스킹되지 않았습니다. (과잉 마스킹을 피하려는 설계의 부작용입니다)
  • git add 하지 않은 신규 파일은 diff에 내용이 없어 파일 이름만 전달됩니다.
  • 이미 커밋된 과거 내용은 pr --base를 쓸 때만 diff에 포함됩니다. 민감정보가 과거 커밋에 있었다면 그 경우에도 같은 마스킹이 적용됩니다.

“왜 SDK(openai, anthropic 패키지)를 안 쓰고 requests로 직접 호출했나요?”

요청 구성 → 전송 → 응답 파싱 → 예외 처리의 흐름을 코드로 그대로 보이게 하려고 했습니다(ai_client.py 상단 설명). 또 OpenAI 호환 서버(Groq 등)는 주소만 바꿔서 쓸 수 있습니다. 대신 SDK가 해 주는 재시도·스트리밍 같은 편의 기능은 직접 안 만들었습니다.

“--safe-mode 옵션을 줘도 아무 변화가 없던데요?”

맞습니다. --safe-mode는 기본값이 이미 ON이라 켜도 동작이 바뀌지 않는 옵션입니다. 실제로 동작을 바꾸는 것은 끄는 --no-safe-mode입니다. 정리 대상 개선점으로 알고 있다고 답하면 됩니다.

“테스트는 어떻게 돌리나요?”

python -m unittest discover -s tests -v → 10개가 통과합니다(마스킹 4, 후처리 4, JSON 해석 2). API 키·인터넷이 필요 없습니다. 반대로 HTTP 호출·git 수집·전체 흐름은 자동 테스트가 없다는 점이 한계입니다(항목 4의 3번).

  • “현재 구현은 ~입니다.”
  • “한계는 ~입니다.” (예: 정규식이라 놓치는 패턴이 있음, 큰 diff는 잘림)
  • “개선한다면 ~를 바꾸겠습니다.” (예: 전송 전 확인 단계, 파일별 요약)
