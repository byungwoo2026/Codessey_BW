1. 큰 그림 — 이 프로그램은 무엇인가?

30초 소개 (먼저 이것부터 외우세요)

“코드를 고친 뒤 ‘커밋 메시지’와 ‘PR 설명’을 쓰는 건 번거롭습니다. 이 프로그램은 git에서 무엇이 바뀌었는지 모으고, 비밀 정보는 가린 다음, AI에게 글 초안을 부탁하고, 돌아온 글이 규칙에 맞는지 검수해서 화면에 보여 줍니다. 커밋이나 push는 하지 않고 초안만 보여 주기 때문에 마지막 결정은 사람이 합니다.”

데이터가 흘러가는 길

“글자 덩어리가 단계마다 어떤 모양으로 바뀌는가”만 따라가면 됩니다.

  1. git 수집받는 것: 없음 → 내보내는 것: 변경 파일 목록 + diff(바뀐 줄이 적힌 긴 글)
  2. safe-modediff 속 비밀을 [MASKED_…]로 바꾸고, 너무 길면 잘라냄 → 안전한 diff
  3. 프롬프트 조립규칙(system) + 오늘의 자료(user)를 합쳐 AI에게 보낼 쪽지 두 장
  4. AI API 호출 — 딱 1번쪽지를 인터넷으로 보내고 AI가 쓴 글(JSON 모양)을 받음
  5. JSON 해석받은 글자를 파이썬이 다룰 수 있는 “칸이 나뉜 데이터”로 바꿈
  6. 검증·후처리제목 길이 확인·자르기, 빈 섹션 채우기, 불릿 기호 정리 → 하고 난 일을 [CHECK]로 보고
  7. 출력Change Summary / Commit Message(또는 PR Title·Body) / [CHECK] / [NOTE]를 화면에 인쇄
모든 답의 뿌리가 되는 세 가지 사실
  1. AI는 회사 밖의 남이다. → 비밀을 그대로 보내면 안 됨 → safe_mode.py, --dry-run (항목 4-2)
  2. AI는 부탁을 100% 지키지 않는다. → 규칙은 “부탁”만 하지 말고 코드가 “확인·보정” → formatter.py (항목 2-2, 3-4)
  3. AI는 사진 한 장(diff)만 보고 글을 쓴다. → 왜 바꿨는지, 사실인지 모름 → 사람이 검토 (항목 4-1)

data = resp.json()                             # (3) 받았는데 이상? → 형식 오류

# main.py — 한 곳에서 받아서 안내
try:

except ai_client.AIError as e:

엽서에 칸이 30개뿐이면 하고 싶은 말이 30칸에서 뚝 끊깁니다. 칸이 200개라고 해서 200칸을 다 채워야 하는 건 아니고, 쓸 만큼만 쓰면 됩니다. max_tokens가 이 칸 수(상한)입니다. 칸의 단위가 “토큰”(글자 조각)이고, 요금도 토큰 수로 계산됩니다.

  • 너무 작으면: JSON이 중간에 잘려 해석 실패 → 3장·6번 화면의 오류.
  • 크게 잡으면: 쓴 만큼만 쓰므로 결과는 같고, 최대 비용 상한만 올라갑니다.
  • 잘림 감지: OpenAI 계열은 finish_reason == "length", Anthropic은 stop_reason == "max_tokens"일 때 [WARN] 응답이 max_tokens 한도에서 잘렸습니다를 띄웁니다.
  • 800을 고른 기준: 출력이 “요약 + 제목 + 불릿 몇 개”짜리 짧은 JSON이라 넉넉한 값. 다만 모델별로 측정해 정한 정밀값은 아니고 “짧은 JSON에 넉넉하다”는 기준입니다.
  • 추론형 모델은 2000: README의 실제 실행(Groq gpt-oss-120b)에서 출력이 커밋 593토큰, PR 1048토큰이었는데, 이 모델은 답하기 전 내부 추론에도 토큰을 써서 800이면 PR이 잘릴 수 있었기 때문입니다.
  • 하한 50: 그보다 작으면 JSON 한 덩어리가 완성될 수 없어 호출 전에 막습니다.
입력 토큰도 비용

로그의 입력 321, 출력 123처럼 둘 다 셉니다. 그래서 safe-mode의 전송 제한(10개 파일/200줄)이 보안뿐 아니라 비용 상한 역할도 합니다. safe-mode를 꺼도 2000줄 상한은 남아 있습니다.

git diff에 민감정보가 섞일 수 있는 상황과 방지 방안?

이 질문이 사실 묻는 것

“비밀이 AI 회사 서버로 나가는 사고를 어떻게 막았나요? 완벽한가요?”

쉽게 말하면 — 통장 비밀번호가 적힌 편지를 외국 우체국에 보내는 일

diff는 AI 서버(밖)로 전송됩니다. 코드에 박아 둔 키, 실수로 git add한 .env가 diff에 섞여 있으면 그대로 밖으로 나갑니다. 한 번 나간 정보는 되돌릴 수 없습니다. 그래서 편지를 보내기 전에 검은 펜으로 지웁니다(safe-mode).

다섯 겹의 방어

상황대응
코드에 키를 직접 적음(sk-…, AWS AKIA…, Google AIza…, GitHub ghp_…, JWT)① 마스킹: 모양을 찾아 [MASKED_API_KEY] 등으로 치환

diff가 너무 커서 많은 정보가 한꺼번에 나감③ 전송 제한: 최대 10개 파일/200줄(safe-mode를 꺼도 2000줄 상한)

키 자체 관리⑤ 관리 습관: API Key는 환경변수로만, .env는 .gitignore에, 노출되면 즉시 폐기·재발급

정규식이란? — 전화번호 예시로 이해하기

전화번호를 찾는 규칙은 \b01[016789]-?\d{3,4}-?\d{4}\b입니다. 글자 “모양”을 말로 풀면:

01          →  "01" 로 시작하고
[016789]    →  다음 숫자는 0,1,6,7,8,9 중 하나 (010, 011, 016 …)
-?          →  하이픈이 있어도 되고 없어도 되고
\d{3,4}     →  숫자 3~4개
-?\d{4}     →  (하이픈) 숫자 4개
\b          →  앞뒤가 "단어의 경계"일 것 (그래서 더 긴 숫자열의 일부는 안 잡음)

실제 실행 결과

# 마스킹 전(--no-safe-mode, AI에게 원문이 그대로 감)
+OPENAI_KEY = "sk-proj-abcdefghijklmnopqrstuvwxyz123456"
+admin = "hong@example.com"
+phone = "010-1234-5678"
+password = "hunter2pass"

# safe-mode ON (기본)
[INFO] 민감정보 마스킹 4건: OPENAI/ANTHROPIC_KEY 1건, EMAIL 1건, PHONE(KR) 1건, SECRET_ASSIGNMENT 1건
+OPENAI_KEY = "[MASKED_API_KEY]"
+admin = "[MASKED_EMAIL]"
+phone = "[MASKED_PHONE]"
+password = "[MASKED_SECRET]"

한계 — 이것까지 말하면 이해도가 높아 보입니다 (모두 직접 실행해 확인)

  • 그래서 정규식은 “모든 비밀을 잡는다”고 보장할 수 없습니다. 놓치는 것을 줄이려면 전문 시크릿 스캐너 연동이나 “전송 전 확인” 단계가 필요합니다(4-3).

우선순위를 정하는 간단한 잣대

“문제가 생겼을 때의 피해 크기 × 되돌리기 어려움”이 큰 것부터. 한 번 밖으로 나간 비밀은 되돌릴 수 없으니 1순위, 결과가 부분적일 뿐인 큰 diff는 그다음…

순위개선지금의 문제 (근거)
1민감정보 탐지 강화 + 전송 전 확인
시크릿 스캐너 연동, “이 내용이 전송됩니다. 계속할까요?” 확인		정규식의 한계를 직접 재현함(숫자 없는 비밀번호, 한글에 붙은 전화번호). 실수의 비용이 가장 크고 되돌릴 수 없음
2큰 diff 처리
파일별로 나눠 요약한 뒤 합치기		200줄·10개 파일을 넘으면 뒤를 버려서 요약이 부분적으로만 맞음(경고만 표시)
3테스트 확장 + CI

승인 후 git commit 실행, git hook 연동		1~3이 안정된 뒤에 붙여야 안전. 자동화할수록 “검토 없이 적용”될 위험도 커짐

8. 꼬리 질문 모음 — 클릭해서 펼치기

AI API는 한 번의 실행에서 몇 번 부르나요?

정확히 1번입니다(변경 없음·키 없음·dry-run이면 0번). 재생성 대신 후처리를 택해서 규칙을 어겨도 다시 부르지 않습니다. 로그의 AI API 호출 횟수: 1회가 증거입니다.

API Key는 어디에 저장하고, 화면에 찍히지는 않나요?

환경변수 AI_API_KEY에만 둡니다. 코드·README에는 없고, 요청에서도 Authorization 헤더로만 가며 오류 메시지에 값을 찍지 않습니다. 실수로 올렸다면 즉시 폐기하고 재발급해야 합니다.

왜 SDK(openai 패키지)를 안 쓰고 requests로 직접 호출했나요?

요청 구성 → 전송 → 응답 해석 → 오류 처리의 흐름을 코드로 그대로 보이게 하려고 했습니다(ai_client.py 상단 설명). OpenAI 호환 서버(Groq 등)는 주소만 바꿔 쓸 수 있다는 장점도 있습니다. 대신 SDK가 해 주는 자동 재시도 같은 편의 기능은 직접 만들지 않았습니다.

--safe-mode 옵션을 줘도 아무 변화가 없던데요?

맞습니다. 기본값이 이미 ON이라 켜도 동작이 안 바뀌는 옵션입니다. 실제 스위치는 끄는 --no-safe-mode입니다. 정리할 개선점으로 알고 있다고 답하세요.

push나 PR 생성까지 자동으로 하지 않는 이유는?

과제의 Git 연동 범위가 status, diff까지이고, AI가 쓴 글을 검토 없이 원격에 반영하면 위험하기 때문입니다. 초안 출력까지만 하고 적용은 사람이 합니다.

AI가 없는 내용을 지어내면(환각) 어떻게 막나요?

완전히 막진 못합니다. 줄이는 장치는 ① 프롬프트의 “diff에 없는 내용을 추측하지 말 것”, ② 낮은 temperature(0.3), ③ --context로 이유를 직접 알려 주기, ④ 마지막의 사람 검토입니다. 실제로 근거 없는 문장을 지운 사례가 있습니다(4-1).

AI가 JSON이 아닌 이상한 답을 주면요?

① 요청에 response_format: json_object로 JSON을 강제하고, ② 그래도 ```json 코드 상자로 감싸 오면 벗겨 내며(parse_json_response(), 테스트 있음), ③ 바깥에 설명이 붙어 있으면 {…} 부분만 찾아 해석하고, ④ 그래도 실패하면 원본 앞부분과 해결 힌트를 보여 주고 종료 코드 1로 끝납니다.

종료 코드를 왜 0/1/2/130으로 나눴나요?

다른 프로그램이 결과를 구별해 쓰게 하려고입니다. 0=성공(변경 없음 포함), 1=실행 중 오류(키·네트워크·git·JSON), 2=잘못된 옵션 값, 130=사용자가 Ctrl+C로 중단(유닉스 관례).

단위 테스트는 무엇을 검사하나요?

python -m unittest discover -s tests -v → 10개 통과(마스킹 4, 후처리 4, JSON 해석 2). API 키·인터넷이 필요 없습니다. 반대로 HTTP 호출·git 수집·전체 흐름은 자동 테스트가 없다는 점이 한계입니다(4-3).

이 프로젝트에서 가장 어려웠던 점·배운 점은?

정답이 하나가 아니라 본인이 겪은 것을 말하는 질문입니다. 틀로 정리하면 좋습니다: “[겪은 문제] → [원인] → [고친 방법] → [배운 점]”. 예를 들어 “PR이 영어로 생성됨 → 프롬프트에 언어 규칙이 없었음 → 한국어 작성 규칙 추가 → 프롬프트로 출력 품질을 제어할 수 있음을 배움”은 README에 실제 사례로 기록돼 있습니다.

  • 커밋 제목 50자 권장 / 72자 한도, PR 제목 80자
  • 커밋 본문 불릿 최대 3개
  • safe-mode: 10개 파일 / 200줄, 꺼도 2000줄 상한
  • temperature 기본 0.3 (0.0~2.0)
  • max-tokens 기본 800 (하한 50), 추론형은 2000
  • timeout 기본 60초
  • AI 호출 1회, 단위 테스트 10개

종료 코드

  • 0 정상(변경 없음 포함)
  • 1 실행 중 오류(키·네트워크·git·JSON)
  • 2 옵션 값 잘못
  • 130 Ctrl+C

[CHECK] 기호

  • OK 문제없음
  • WARN 주의(권장 초과 등)
  • FIX 코드가 고침(자르기·채우기)

한 줄 정리 4개

  • 프롬프트는 부탁, formatter는 보증
  • AI는 내용, 코드는 형식
  • 재생성 대신 후처리 → 호출 항상 1회
  • 형식 OK ≠ 내용 정확 → 사람이 검토

시연 함정 5개

  • 변경 없으면 키 오류가 안 나옴(변경 먼저 만들기)
  • 프로젝트 루트에서 실행
  • 커밋 끝난 브랜치의 pr은 --base main
  • Groq/추론형이면 --max-tokens 2000
  • 끝나면 git restore README.md
