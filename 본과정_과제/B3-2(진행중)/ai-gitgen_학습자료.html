ai-gitgen — git diff 를 AI 에게 읽혀 커밋 메시지와 PR 초안을 만드는 CLI

“AI 를 붙인다”는 건 API 를 한 번 호출하는 일이 아니라, 무엇을 입력으로 주고(Git 수집·마스킹), 어떻게 시키고(프롬프트), 나온 결과를 어떻게 믿을 수 있게 만드는가(검증·후처리) 를 설계하는 일입니다. 이 자료는 내가 만든 ai-gitgen 의 실제 코드를 한 줄씩 따라가며 그 설계를 공부하도록 정리했습니다.

1-3. 일부러 하지 않는 것 (제약 사항)

Git 은 “읽기만”

쓰는 Git 명령은 status, diff, 그리고 이를 보조하는 rev-parse, branch --show-current 뿐입니다. commit·push·PR 생성은 하지 않습니다. 도구는 초안 텍스트를 출력할 뿐이고, 검토 후 적용은 사람이 합니다.

비용·보안 안전장치

명령당 AI 호출은 정확히 1회, 키 누락·변경 없음·파라미터 오류는 호출 전에 0회로 종료. diff 는 보내기 전에 safe-mode 로 마스킹·제한합니다. 키는 환경변수 AI_API_KEY 로만 받습니다.

핵심 관점

AI 가 쓴 문장은 “정답”이 아니라 “초안”입니다. 그래서 이 도구의 가치는 AI 호출 자체보다 ① 좋은 입력을 만드는 앞단(수집·마스킹·프롬프트)과 ② 나쁜 출력을 걸러내는 뒷단(JSON 파싱·길이/템플릿 검증)에 있습니다.

3기초 개념 사전

코드를 읽다가 막히면 여기로 돌아오세요. 각 항목 끝에 이 프로젝트의 어느 코드에서 쓰는지 적어 두었습니다.

3-1. API 와 HTTP

REST API 호출 = “편지 보내고 답장 받기”

프로그램이 서버 주소(URL)로 HTTP 요청을 보내면 서버가 HTTP 응답을 돌려줍니다. AI API 도 똑같습니다. 우리는 “이 글을 요약해 줘” 라는 JSON 편지를 POST 로 보내고, 요약이 담긴 JSON 답장을 받습니다.

→ ai_client.call_ai() 안의 requests.post(url, headers=…, json=…)

요청의 네 부분

  1. URL: 어디로 (예: https://api.anthropic.com/v1/messages)
  2. 메서드: 무엇을 (데이터를 보내서 처리시키므로 POST)
  3. 헤더: 부가 정보 — 인증 키, 본문 형식(Content-Type: application/json)
  4. 본문(body): 실제 내용 — 모델명, 파라미터, 메시지

상태 코드 읽는 법

2xx 성공 · 4xx “요청한 쪽 잘못”(키 틀림 401, 권한 403, 없음 404, 한도 429, 형식 오류 400) · 5xx “서버 쪽 문제”. 코드를 보고 원인을 사람 말로 바꿔 알려주는 것이 오류 처리의 핵심입니다.

→ call_ai() 의 reason 딕셔너리 (5장)

JSON

key-value 를 문자열로 적는 형식. Python 의 dict ↔ JSON 문자열 변환이 json.dumps / json.loads. 이 프로젝트는 AI 에게 “반드시 JSON 으로만 답하라” 고 시키고, 받은 문자열을 json.loads 로 dict 로 바꿔 씁니다.

→ parse_json_response(), prompts.py 의 출력 형식

키가 노출되면 남이 내 요금으로 API 를 쓸 수 있습니다. 코드에 적으면 git 기록에 영원히 남으므로, 실행 환경의 환경변수로만 전달하고 코드는 os.environ.get("AI_API_KEY") 로 읽습니다.

3-3. AI 쪽 용어

토큰(token)

모델이 글을 읽고 쓰는 단위(단어 조각). 비용·길이 제한이 글자 수가 아니라 토큰 수로 계산됩니다. 보통 같은 내용이라도 영어보다 한국어가 토큰을 더 쓰는 경향이 있습니다(모델마다 다름).

system / user 프롬프트

system = 역할과 규칙(“너는 커밋 메시지 전문가, 이 형식으로만 답해”), user = 이번에 처리할 데이터(브랜치·파일·diff). 규칙과 데이터를 분리하면 재사용과 점검이 쉽습니다.

temperature · max_tokens

temperature: 다음 단어 선택의 무작위성(낮을수록 일관). max_tokens: 응답 길이의 상한. 자세한 효과는 6장에서 직접 만져 봅니다.

3-5. Python 도구

subprocess.run — 다른 프로그램 실행

파이썬이 git 같은 외부 명령을 실행하고 출력(stdout)·종료코드(returncode)를 받습니다. 명령을 문자열 한 줄이 아니라 리스트(["git","status"])로 넘기면 셸을 거치지 않아, 값에 특수문자가 있어도 셸 명령으로 해석되지 않습니다.

→ git_collector.run_git()

argparse — 명령줄 옵션 해석

commit/pr 같은 하위 명령(subparser)과 --temperature 같은 옵션을 선언하면 파싱·타입 변환·--help 가 자동으로 만들어집니다. 공통 옵션은 parents=[common] 으로 두 명령이 공유합니다.

→ main.build_parser()

@dataclass — 값 묶음 타입

필드만 선언하면 생성자 등을 자동으로 만들어 주는 “데이터 상자”. 모듈 사이에 값을 전달할 때 딕셔너리 대신 쓰면 필드 이름이 문서 역할을 합니다.

→ FileChange, GitChanges, AIResult, Checked, SafeModeReport

정규식(re)

문자열에서 “패턴”을 찾고 바꾸는 도구. 이 프로젝트에서는 ① API Key·이메일 같은 민감정보 마스킹, ② AI 응답의 코드펜스 제거·JSON 추출, ③ PR 본문 템플릿 검증에 씁니다.

→ safe_mode.MASK_RULES, parse_json_response, validate_pr_body

3-6. 종료 코드(exit code)

프로그램이 끝날 때 운영체제에 돌려주는 숫자입니다. 0 = 정상, 그 외 = 비정상이라는 관례 덕분에 스크립트·CI 가 “성공했나?” 를 판단할 수 있습니다. 이 프로젝트는 0(성공·변경 없음·dry-run), 1(Git/API/파싱 오류), 2(옵션 값 범위 오류), 130(Ctrl+C) 를 씁니다(10장).

4-2. Git 을 파이썬에서 실행하기 — run_git()

gitgen/git_collector.py50–66행
def run_git(args: list[str]) -> str:
    """git 명령 실행. 한글 파일명이 깨지지 않도록 core.quotepath=false, UTF-8 디코딩."""
    cmd = ["git", "-c", "core.quotepath=false", *args]
    try:
        result = subprocess.run(
            cmd,
            capture_output=True,
            text=True,
            encoding="utf-8",
            errors="replace",
        )
    except FileNotFoundError as e:
        raise GitError("git 명령을 찾을 수 없습니다. Git 설치 여부와 PATH 설정을 확인하세요.") from e

    if result.returncode != 0:
        raise GitError(f"'git {' '.join(args)}' 실행 실패: {result.stderr.strip()}")

def get_status_files() -> list[FileChange]:
    """git status --porcelain 결과를 파싱해 변경 파일 목록을 만든다."""
    out = run_git(["status", "--porcelain=v1"])
    files: list[FileChange] = []
    for line in out.splitlines():
        if not line.strip():
            continue
        xy, path = line[:2], line[3:]
        if xy == "??":
            code = "??"
        else:
            # 스테이징(X) 우선, 없으면 작업트리(Y) 상태 사용
            code = (xy[0] if xy[0] != " " else xy[1]).strip()
        if " -> " in path:  # rename: "old -> new"
            path = path.split(" -> ", 1)[1]
        files.append(FileChange(status=code, path=path.strip('"')))
    return files

def get_diff(base: str | None = None) -> str:
    """diff 텍스트 수집.

    - 기본: 스테이징된 변경(--cached) + 스테이징 안 된 변경
    - base 지정 시(pr 명령): base...HEAD 까지 커밋된 변경도 포함
    """
    parts: list[str] = []
    if base:
        committed = run_git(["diff", f"{base}...HEAD"])
        if committed.strip():
            parts.append(committed)
    staged = run_git(["diff", "--cached"])
    unstaged = run_git(["diff"])
    for chunk in (staged, unstaged):
        if chunk.strip():
            parts.append(chunk)
    return "\n".join(p.rstrip("\n") for p in parts)
  • 기본(commit): diff --cached(스테이징) + diff(미스테이징)를 이어 붙입니다. 그래서 “일부만 add 한 상태”도 모두 AI 에게 전달됩니다. 이어 붙이는 순서는 스테이징 먼저, 미스테이징 나중입니다(9장 dry-run 출력에서 .env·config.py 가 README.md 보다 앞에 나옵니다).

def parse_json_response(text: str) -> dict:
    """AI 응답에서 JSON 객체를 추출. ```json 코드블록으로 감싼 경우도 처리."""
    cleaned = re.sub(r"^```(?:json)?\s*|\s*```$", "", text.strip())
    try:
        return json.loads(cleaned)
    except json.JSONDecodeError:
        m = re.search(r"\{.*\}", cleaned, re.DOTALL)
        if m:
            try:
                return json.loads(m.group(0))
            except json.JSONDecodeError:
                pass
    raise AIError(
        "AI 응답을 JSON 으로 해석하지 못했습니다. --max-tokens 를 늘리거나 --temperature 를 낮춰 다시 시도하세요.\n"
        f"        원본 응답 앞부분: {text[:200]!r}"
    )

6-2. temperature — “다음 단어를 고를 때 얼마나 모험할까”

모델은 단어를 하나씩 이어 쓰는데, 매 순간 “다음에 올 단어 후보들의 점수” 를 계산합니다. temperature 는 그 점수를 확률로 바꿀 때의 ‘온도’ 입니다.

  • 낮으면(0~0.3): 1등 후보에 확률이 몰려 같은 입력에 거의 같은 문장이 나옵니다 → 요약·형식 준수·재현성에 유리.
  • 높으면(0.8~): 2·3등 후보도 자주 뽑혀 표현이 다양해지지만, 형식을 벗어나거나 diff 에 없는 내용을 지어낼 가능성이 커집니다 → 창작에 유리.

7-1. 네 가지 설계 원칙

① 역할(system)과 데이터(user)를 분리

system 에는 “너는 누구고 어떤 규칙으로 답하라” 를, user 에는 이번 실행의 브랜치·파일 목록·diff 를 담습니다. 규칙은 거의 고정이고 데이터는 매번 바뀌므로, 분리하면 규칙을 한곳에서 고치고 테스트할 수 있습니다.

② 출력을 JSON 스키마로 고정

마크다운 문서 전체를 쓰게 하지 않고 {summary, title, body_bullets} 처럼 내용만 채우게 합니다. 제목 줄 모양·## Why 같은 헤더·- 불릿은 코드가 렌더링하므로 섹션 누락이 구조적으로 불가능합니다.

③ 규칙을 숫자와 예시로 명시

“짧게” 대신 “50자 이내(최대 72자)”, “좋은 말투” 대신 “명사형 종결(예: ~ 추가)”, 금지는 “과장 표현(완벽한, 획기적인) 금지” 처럼 구체적으로 씁니다. 모호한 지시는 모호한 결과를 만듭니다.

④ “왜” 는 사람이 알려준다

diff 에는 무엇이 바뀌었는지만 있고 왜 바꿨는지는 없습니다. 그래서 --context 옵션과 팀 컨벤션 파일로 이유·규칙을 추가 컨텍스트로 주입합니다.

def build_user_prompt(changes: GitChanges, diff_for_ai: str, context: str | None,
                      convention: str | None, mode: str) -> str:
    parts = [
        f"## 현재 브랜치\n{changes.branch}",
        f"## 변경 파일 목록 (git status)\n{_file_list(changes)}",
    ]
    if context:
        parts.append(f"## 작성자가 알려준 변경 이유/요구사항\n{context}")
    if convention:
        parts.append(f"## 팀 컨벤션 (위 규칙보다 우선 적용)\n{convention}")
    untracked = [f.path for f in changes.files if f.status == "??"]
    if untracked:
        parts.append(
            "## 참고\n다음 신규 파일은 아직 git add 되지 않아 diff 에 내용이 없습니다: "
            + ", ".join(untracked)
        )
    parts.append(f"## 변경 내용 (git diff)\n```diff\n{diff_for_ai or '(diff 없음)'}\n```")
    target = "커밋 메시지" if mode == "commit" else "PR 제목과 본문"
    parts.append(f"위 정보를 바탕으로 {target}을(를) 지정된 JSON 형식으로 작성하세요.")
    return "\n\n".join(parts)

def load_convention(path: str | None) -> str | None:
    target = path or (DEFAULT_CONVENTION_FILE if os.path.exists(DEFAULT_CONVENTION_FILE) else None)
    if not target:
        return None
    try:
        with open(target, encoding="utf-8") as f:

8-1. 왜 검증이 필요한가

  • 프롬프트에 “50자 이내” 라고 써도 모델은 글자 수를 정확히 세지 못해 가끔 넘깁니다. 규칙은 지시(프롬프트)와 검증(코드) 두 겹으로 지켜야 합니다.
  • JSON 필드를 빠뜨리거나 비워서 줄 수 있습니다(예: why: []). 그대로 출력하면 “각 섹션에 최소 1개 불릿” 요구사항이 깨집니다.
  • AI 가 이미 붙인 - 불릿 기호, 따옴표, 여러 줄 제목, 끝의 마침표 같은 잡음이 섞일 수 있습니다.

9-1. 왜 필요한가 — 세 겹 방어

diff 는 “내가 방금 고친 코드 전부” 입니다. 급하게 키를 붙여 넣은 채로 실행하면 그 키가 외부 서버로 전송됩니다. 이 위험을 막으려고 세 가지를 합니다(과제의 (A)·(B) 요구를 모두 충족).

(A) 패턴 마스킹

키·토큰·이메일·전화·주민번호·password=값 을 [MASKED_…] 로 치환

(+) 민감 파일 제외

.env, *.pem, *secret* 등은 파일 내용 통째로 전송하지 않음

(B) 전송량 제한

기본 10개 파일 / 200줄까지만. 초과분은 생략하고 사실을 프롬프트에 표시

def is_sensitive_file(path: str) -> bool:
    name = path.replace("\\", "/").split("/")[-1].lower()

            chunks.append((path, [line]))
        elif chunks:

        else:

def apply_safe_mode(diff: str, max_files: int, max_lines: int) -> tuple[str, SafeModeReport]:
    report = SafeModeReport(enabled=True, lines_before=len(diff.splitlines()))
    kept: list[str] = []
    file_count = 0

    for path, chunk in split_diff_by_file(diff):
        if is_sensitive_file(path):
            report.excluded_files.append(path)
            kept.append(f"diff --git a/{path} b/{path}\n[safe-mode] 민감 파일로 판단되어 내용 전송 제외")
            continue
        if file_count >= max_files:
            report.dropped_files.append(path)
            continue
        kept.append(mask_text(chunk, report))
        file_count += 1

    lines = "\n".join(kept).splitlines()
    if len(lines) > max_lines:
        lines = lines[:max_lines]
        lines.append(f"[safe-mode] diff 가 {max_lines}줄을 초과하여 이후 내용은 생략됨")
        report.truncated_by_lines = True
    if report.dropped_files:
        lines.append(
            f"[safe-mode] 파일 수 제한({max_files}개) 초과로 제외된 파일: "
            + ", ".join(report.dropped_files)
        )

    result = "\n".join(lines)
    report.lines_after = len(result.splitlines())
    return result, report

"""
import os
import unittest
from unittest.mock import MagicMock, patch

from gitgen import ai_client
from gitgen.ai_client import AIError, call_ai


def fake_response(status, payload):
    resp = MagicMock()
    resp.status_code = status
    resp.json.return_value = payload
    resp.text = str(payload)
    return resp


@patch.dict(os.environ, {"AI_API_KEY": "test-key"})
class TestCallAI(unittest.TestCase):
    @patch("gitgen.ai_client.requests.post")
    def test_openai_success_parses_text_and_tokens(self, post):
        post.return_value = fake_response(200, {
            "choices": [{"message": {"content": "{\"title\": \"t\"}"}, "finish_reason": "stop"}],
            "usage": {"prompt_tokens": 10, "completion_tokens": 5}})
        r = call_ai("openai", "m", "sys", "usr", 0.3, 800)
        self.assertEqual(r.text, '{"title": "t"}')
        self.assertFalse(r.truncated)
        self.assertEqual((r.input_tokens, r.output_tokens), (10, 5))
        sent = post.call_args.kwargs["json"]               # 실제로 보낸 요청 본문 검사
        self.assertEqual(sent["max_completion_tokens"], 800)
        self.assertEqual(post.call_args.kwargs["headers"]["Authorization"], "Bearer test-key")

    @patch("gitgen.ai_client.requests.post")
    def test_401_message_has_status_and_reason(self, post):

        with self.assertRaises(AIError) as cm:

        self.assertIn("HTTP 401", str(cm.exception))
        self.assertIn("bad key", str(cm.exception))

    @patch("gitgen.ai_client.requests.post", side_effect=ai_client.requests.exceptions.Timeout)
    def test_timeout_becomes_network_error(self, post):

AI_API_KEY 값에 따라 동작이 달라진다:  ok / bad(401) / limit(429) / boom(500)
"""
import json
from http.server import BaseHTTPRequestHandler, HTTPServer

COMMIT = {"summary": "로그인 실패 제한을 추가했습니다.",
          "title": "feat: 로그인 실패 횟수 제한 추가",
          "body_bullets": ["auth.py 의 login() 에 실패 5회 초과 시 잠금 처리를 추가했습니다."]}
PR = {"summary": "로그인 실패 제한 기능을 추가했습니다.",
      "title": "feat: 로그인 실패 횟수 제한 기능 추가",
      "why": ["무차별 대입 공격을 줄이기 위해 필요했습니다."],
      "what": ["auth.py 의 login() 에 실패 횟수 카운트 추가"],
      "how_to_test": ["python -c \"import auth\" 후 login() 을 6번 호출해 잠금 확인"]}
ERRORS = {"bad": 401, "limit": 429, "boom": 500}


class Handler(BaseHTTPRequestHandler):
    def do_POST(self):
        body = json.loads(self.rfile.read(int(self.headers["Content-Length"])))
        openai = self.path.endswith("/chat/completions")
        key = (self.headers.get("Authorization", "").removeprefix("Bearer ")
               if openai else self.headers.get("x-api-key", ""))
        if key in ERRORS:                                   # 오류 시나리오
            return self.reply(ERRORS[key], {"error": {"message": f"mock error for key={key}"}})
        system = body.get("system") or next(m["content"] for m in body["messages"] if m["role"] == "system")
        text = json.dumps(PR if "Pull Request" in system else COMMIT, ensure_ascii=False)
        if openai:
            self.reply(200, {"choices": [{"message": {"content": text}, "finish_reason": "stop"}],
                             "usage": {"prompt_tokens": 100, "completion_tokens": 50}})
        else:
            self.reply(200, {"content": [{"type": "text", "text": text}], "stop_reason": "end_turn",

설계 선택

Q. 왜 공식 SDK(openai, anthropic) 대신 requests 로 직접 호출했나요?

과제 목표가 “REST 로 연동하는 흐름(요청 구성 → 응답 처리 → 예외 대응)” 을 설명하는 것이었기 때문입니다. SDK 는 이 과정을 감춰 줘서 편하지만 학습 목적에는 흐름이 보이는 쪽이 낫습니다. 또 의존성이 requests 하나라 설치가 가볍고, 제공자 두 곳을 같은 방식으로 다룰 수 있습니다. 대신 재시도·스트리밍·타입 같은 SDK 의 편의 기능은 직접 구현하지 않았습니다. 실무에서는 SDK 를 쓰는 편이 유지보수에 유리한 경우가 많습니다.

Q. 왜 AI 에게 마크다운이 아니라 JSON 으로 답하게 했나요?

“내용” 과 “형식” 의 책임을 나누려는 것입니다. AI 는 요약·제목·불릿 같은 내용만 채우고, ## Why 헤더·- 불릿·제목 줄 모양은 코드가 렌더링합니다. 그러면 섹션 누락이 구조적으로 불가능하고, 길이 검증도 필드 단위로 쉽습니다. 대신 JSON 이 깨지거나 코드펜스로 감싸 오는 경우에 대비한 파서(parse_json_response)가 필요합니다.

Q. 검증 실패 시 재생성하지 않고 후처리를 택한 이유는?

재생성은 호출이 2회 이상으로 늘어 비용과 시간이 예측 불가하고 과제 권장(1~2회)과도 부딪힙니다. 후처리(자르기·빈 섹션 채우기)는 호출 1회를 보장합니다. 단점은 자르기가 의미를 모른다는 점이라, 고친 내용을 [CHECK] 에 FIX 로 알리고 사용자가 최종 문구를 다듬게 했습니다. 8-2 의 비교표를 참고하세요.

Q. temperature 를 0.3 으로 둔 이유는? 0 이면 더 좋은 것 아닌가요?

커밋/PR 은 창작이 아니라 정확한 요약이 목적이라 낮은 값이 맞습니다. 0 도 가능하지만(--temperature 0) 약간의 여유(0.3)는 표현이 지나치게 기계적이거나 반복적인 것을 완화하면서도 형식 이탈은 거의 일으키지 않는 절충입니다. 같은 입력에서 같은 결과가 꼭 필요하면 0 을 쓰되, 제공자 구현에 따라 완전한 동일성이 보장되지는 않습니다.

Q. 호출을 명령당 1회로 제한한 것은 어떻게 보장하나요?

구조로 보장합니다. call_ai() 를 부르는 곳이 run() 에 한 군데뿐이고 반복문·재시도가 없습니다. 호출 전에 끝낼 수 있는 모든 경우(변경 없음, 키 없음, 옵션 오류, --dry-run)는 0회로 종료하고, 실행마다 [INFO] AI API 호출 횟수 를 출력합니다. 단점은 일시적 오류(429, 5xx)에도 자동 재시도가 없다는 점입니다(15장).

Q. 새 AI 제공자(예: Gemini)를 추가하려면 어디를 고치나요?
  1. PROVIDERS 에 URL 과 기본 모델을 추가
  2. _build_request 에 해당 제공자의 헤더·본문 구성 분기를 추가
  3. call_ai 의 “응답 해석” 부분에 텍스트·잘림·토큰 경로 분기를 추가
  4. --provider 의 choices 는 PROVIDERS 키에서 자동 생성되므로 그대로 반영

이 세 곳이 모두 ai_client.py 안이라 수정 범위가 한 파일로 끝납니다. 다만 분기(if/else)가 늘면 제공자별 클래스로 나누는 리팩터링이 적절합니다. 정확한 요청 형식은 해당 제공자 문서로 확인해야 합니다.

Q. 왜 도구가 git commit / git push 까지 자동으로 하지 않나요?

과제 제약이기도 하지만 설계상으로도 옳습니다. AI 출력은 초안이고 틀릴 수 있습니다(7-6 의 “주석을 삽입” 오류). 되돌리기 어려운 동작(커밋 기록, 원격 반영)은 사람이 검토한 뒤 직접 수행하게 두는 것이 안전합니다. 도구는 “읽기 + 초안 출력” 으로 권한을 최소화했습니다.

보안 · 비용

Q. API 키를 코드에 쓰면 왜 안 되나요? 실수로 올렸다면?

코드는 git 기록에 남고 저장소가 공개되거나 복제되면 키가 함께 퍼집니다. 노출된 키로 남이 내 요금으로 API 를 쓸 수 있습니다. 그래서 환경변수로만 받습니다(os.environ.get). 이미 올렸다면 파일에서 지우는 것만으로는 기록에 남아 있으므로 즉시 제공자 콘솔에서 키를 폐기(재발급)해야 합니다.

Q. safe-mode 가 켜져 있으면 비밀이 절대 안 나가나요?

아닙니다. 정규식은 알려진 패턴만 잡습니다. 실험 결과 한글에 붙은 전화번호, 숫자 없는 소문자 값(token = 'abcd'), Bearer 토큰은 그대로 전송되었고, 반대로 os.environ['X'] 는 과잉 마스킹되었습니다(9-8). 또 파일 경로와 --context 문장은 마스킹 대상이 아닙니다. 그래서 파일 단위 제외(.env), .gitignore, 실행 전 --dry-run 확인을 함께 권장합니다.

Q. 비용을 어떻게 통제하나요?
  • 호출 1회 고정 + 호출 전 조기 종료(키 없음·변경 없음·옵션 오류)
  • 전송량 상한: safe-mode 10파일/200줄, OFF 여도 2,000줄
  • max_tokens 로 출력 상한 지정, 작은 모델 기본값
  • --dry-run 으로 프롬프트 설계 단계에서는 호출하지 않음
  • 로그에 입력·출력 토큰을 출력해 사용량 확인(요금 계산은 제공자의 현재 가격표 기준)
Q. 401 과 429 의 차이와 대응은?

401 은 “누구인지 확인 실패” — 키가 틀리거나 제공자와 키 종류가 다름, 즉 설정 문제라 재시도해도 소용없고 키를 고쳐야 합니다. 429 는 “너무 많이 요청했거나 한도/크레딧 부족” — 시간을 두고 재시도하거나 사용량·결제를 확인합니다. 도구는 둘을 구분된 문구로 알려 줍니다(5-3).

동작 · 한계

Q. 새로 만든 파일(untracked)은 어떻게 처리되나요?

git status 에는 ?? 로 나오지만 git diff 에는 내용이 없습니다. 그래서 파일 목록에는 포함하고, 프롬프트에 “다음 신규 파일은 아직 add 되지 않아 diff 에 내용이 없습니다” 라는 안내를 붙입니다. AI 는 파일 이름만 알기 때문에 요약이 빈약해질 수 있어, git add 후 실행을 권장합니다.

Q. commit 이 staged 와 unstaged 를 모두 보내는데, 실제 커밋과 어긋나지 않나요?

맞습니다. 현재 구현은 git diff --cached 와 git diff 를 모두 보내지만 git commit 은 기본적으로 staged 만 커밋합니다. 그래서 일부만 add 한 상태에서는 메시지가 실제 커밋 범위보다 넓을 수 있습니다. 개선안은 --staged 옵션(스테이징분만 수집)을 추가하는 것입니다(15장). 이처럼 한계를 알고 설명하는 것이 중요합니다.

Q. diff 가 아주 크면(수천 줄) 어떻게 되나요?

safe-mode ON 이면 10개 파일·200줄까지만 보내고 “이후 내용은 생략됨” 을 프롬프트와 [WARN] 로 알립니다. 따라서 큰 변경은 요약이 부분적이 됩니다. 커밋을 작게 쪼개는 것이 가장 좋은 대응이고, 기술적으로는 --max-lines 를 늘리거나 파일별 요약 후 합치는 방식(호출 증가)을 고려할 수 있습니다.

Q. AI 가 영어로 답하거나 규칙을 어기면요?

두 겹으로 대응합니다. 프롬프트 쪽은 규칙을 구체화해(실제로 “한국어로 작성” 규칙을 추가) 재실행하고, 코드 쪽은 길이·템플릿 같은 검증 가능한 규칙을 formatter 로 강제합니다. 언어처럼 코드로 검증하기 어려운 규칙은 프롬프트와 사람의 검토에 의존합니다.

Q. 단위 테스트가 API 키 없이 도는 이유는? 무엇을 테스트하고 무엇은 못 하나요?

테스트 대상(마스킹·길이 검증·JSON 파싱)이 문자열 입력 → 문자열 출력인 순수 함수라 외부 의존이 없기 때문입니다. 네트워크가 필요한 call_ai 와 Git 이 필요한 git_collector 는 아직 테스트가 없습니다. requests.post 를 mock 으로 바꾸면 테스트할 수 있고, 그 예제를 11-4 에 실제로 실행해 확인했습니다.

Q. 이 도구를 git commit 때 자동으로 부르게(훅) 할 수 있나요?

가능한 확장입니다. Git 의 prepare-commit-msg 훅에서 이 CLI 를 호출해 출력을 커밋 메시지 파일에 써 주는 방식입니다. 다만 모든 커밋마다 AI 가 호출돼 비용과 지연이 생기고, 민감정보 전송 위험도 커지므로 과제 범위(초안 출력까지)를 벗어나며 신중한 설계(옵트인, safe-mode 필수)가 필요합니다.

Q. --safe-mode 가 기본 ON 인데 옵션은 왜 있나요?

과제가 -safe-mode 같은 옵션 제공을 요구해서 이름을 맞춰 등록했습니다. 코드는 store_true + default=True 라 이 플래그를 줘도 동작이 달라지지 않고, 실질적으로 끄는 스위치는 --no-safe-mode 입니다. 솔직히 설계상 군더더기이며, 15장에 개선점으로 적었습니다.

16-4. 복습 퀴즈 — 먼저 답해 보고 펼치세요

1. 키를 환경변수로만 받는 이유 두 가지는?

① 코드·git 기록에 남지 않아 유출 위험이 줄어든다 ② 실행 환경마다(개발/배포) 코드 수정 없이 키를 바꿀 수 있다. 실수로 올렸다면 지우는 것으로는 부족하고 키를 폐기해야 한다.

2. python main.py --dry-run commit 은 왜 오류일까요?

공통 옵션이 commit/pr 하위 명령의 parents=[common] 에 등록돼 있어서, 옵션은 하위 명령 뒤(python main.py commit --dry-run)에 써야 한다.

3. 응답이 {"summary": "로그인 실 에서 끊겼다. 원인과 해결은?

max_tokens 한도에 걸려 JSON 이 잘렸다(finish_reason=length / stop_reason=max_tokens → [WARN]). --max-tokens 를 늘린다(추론형 모델은 2000+). 잘린 JSON 은 파싱이 불가능해 AIError.

4. git status --porcelain=v1 출력 A␣␣config.py, ␣M README.md 의 X, Y 는?

X=스테이징 상태, Y=작업 폴더 상태. 첫 줄은 X=A(스테이징에 신규), Y=공백. 둘째 줄은 X=공백, Y=M(스테이징 안 한 수정). 코드는 X 가 공백이 아니면 X, 아니면 Y 를 대표 상태로 쓴다.

5. PR 본문의 Why 섹션이 비어 와도 최종 출력에 항상 불릿이 있는 이유는?

check_pr 가 섹션 헤더를 코드로 직접 쓰고, 빈 섹션엔 안내 불릿을 넣으며(FIX), 마지막에 validate_pr_body 정규식으로 한 번 더 검사하기 때문이다.

6. 후처리 대신 재생성을 택하면 어떤 점이 달라지나요?

의미를 살려 다시 쓸 수 있지만 호출 횟수·비용·시간이 예측 불가가 되고 과제의 “1~2회” 권장과 충돌할 수 있다. 후처리는 호출 1회를 보장하지만 자르기는 의미를 모른다.

7. 마스킹 규칙을 “구체적인 것 먼저” 적용하는 이유는?

일반 규칙(대입문)이 먼저 걸리면 구체 규칙의 이름별 집계가 틀어지고 이중 처리될 수 있다. 구체 규칙이 먼저 치환하고, 대입문 규칙은 (?!\[MASKED) 로 이미 마스킹된 값을 건너뛴다.

8. API 키가 없는데 python main.py commit 을 실행하면 diff 는 어디로 전송되나요?

어디로도 전송되지 않는다. 키 확인이 safe-mode·프롬프트 조립·호출보다 앞(129~136행)이라 호출 횟수: 0회 로 종료한다.

9. 이 도구의 가장 큰 보안 한계는?

정규식 마스킹이 모든 비밀을 보장하지 못한다(한글에 붙은 번호·비표준 변수명 등 미탐지, 경로·--context 는 미적용). 그래서 파일 단위 제외, .gitignore, --dry-run 확인을 병행한다.
